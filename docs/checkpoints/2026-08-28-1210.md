## Decisions

- MCP `enabled_in_cli` semantics: absent/false → does NOT start in CLI mode (matches the user's literal spec exactly, a deliberate default-behavior change for everyone with MCP configured, not a soft/backward-compatible default) — interactive web UI is completely unaffected either way.
- `mcpAppOptions`' CLI-mode boundary is `cmd.Parent() == nil` (true only for the bare `rush` web-UI invocation) rather than special-casing just `rush run` — applies the same restriction to `sessions`/`ping`/`queue` etc. too, on the reasoning that "CLI mode" as the user described it is a single coherent boundary (interactive vs. everything else), not a `rush run`-specific carve-out.
- Checkpoint-ticker race: fixed the production `select`-priority bug at its root (structural elimination) rather than only making the test mock's channel-close idempotent — the latter alone would have silenced the panic without removing the actual (if currently benign-in-production) racy redundant-write behavior.
- DB migration: dropped the 3 old single-column indexes that the new composites made fully redundant, rather than leaving both — every future INSERT/UPDATE would otherwise maintain two indexes for one filter pattern, for zero read-side benefit.
- Did not chase a deterministic live reproduction of the checkpoint-ticker race beyond ~150 iterations + 2 full-package runs — judged further attempts (which would require re-creating the heavy machine load the user had just asked to avoid) as not worth the cost once the root-cause analysis was solid and matched the panic's exact stack trace.
- package.json "version" fields bumped by hand (source-of-truth for `forkBaseVersion` per the fork's own documented convention) even though the real npm publish version is independently derived from a `npm-v*` git tag at publish time — the checked-in value is not decorative, it's what `forkBaseVersion` must mirror.
