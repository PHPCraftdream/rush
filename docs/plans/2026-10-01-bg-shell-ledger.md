# R-BG-D: фоновые shell как строки `async_jobs` — дизайн

Статус: дизайн (реализация — R-BG-1, после R-ARB-2). Зона: пути SDK-фонового
shell, у которого сегодня нет строки в `async_jobs`; удержания завершения;
отдельный лимит bg-shell. Опирается на:
`docs/plans/2026-09-28-async-phase4-durable-core.md` (§3.1–3.8, ред. 7),
`docs/async-invariants.md` (ASYNC-01/02/09, DUR-1..11),
`docs/plans/2026-10-01-structural-refactor.md` §R-BG.

Принцип №1 фазы 4 — «одна правда»: итог задачи и долг (wake-строка, которую
сессия должна отреагировать) пишутся одной транзакцией через `Transition`
(CAS по running-строке, DUR-1). Сегодня это верно для CLI/web bash (они
обёрнуты в `asyncTool` и имеют строку), но НЕ для фоновых shell, запущенных
вне обёртки: их итог живёт в памяти `BackgroundShellManager`, а факт
завершения пишется позже отдельной строкой `session_notices`.

---

## 1. Текущее устройство

### 1.1. Пути, где появляется фоновый shell

Владелец всегда — `BackgroundShellManager` процесса
(`internal/shell/background.go:297`; один на App/клиент, `NewBackgroundShellManager`,
внедряется в инструменты в `internal/agent/coordinator_tools.go:684-697`).
Пути входа:

1. **CLI/web bash, обёрнутый в `asyncTool`** (главный путь). `asyncTool.run`
   для `bash` без `sync` принудительно ставит `run_in_background=true` и
   глушит внутренний callback (`internal/agent/async_tool.go:219-238`,
   `tools.WithoutBackgroundCallback`); внутренний bash-инструмент создаёт
   shell через `StartOwned(context.Background(), …)`
   (`internal/agent/tools/bash.go:193` — явный фон, `:261` — авто-фон после
   60 с/`auto_background_after`). Строка `async_jobs` (kind=`command`,
   tool_name=`bash`) уже существует; `awaitShell` привязывает shell к строке
   (`asyncJobs.setShellID`, `internal/agent/async_tool.go:299`) и блокируется
   на `sh.WaitContext` (`:312`); итог пишется обычным `finish` →
   `Transition`. **Этот путь уже «одна правда»** — не трогаем, кроме
   колонки `shell_id` (§2.4).
2. **Необёрнутый bash (SDK/синхронный вызов, ход вне реестра async-задач).**
   bash-инструмент вызывается напрямую (без обёртки `asyncTool`): фон по
   `run_in_background` (bash.go:193) или авто-фон (bash.go:261); после
   возврата ответа модели регистрируется callback `OnDone`
   (`internal/agent/tools/bash.go:242`, `:366`) →
   `coordinator.notifyBackgroundJobDone`
   (`internal/agent/coordinator_background.go:126`) →
   `persistBGShellCompletion` (`internal/agent/coordinator_bgshell_cap.go:58`)
   пишет строку `session_notices` (kind=`bg_shell_done`,
   `internal/session/notice_pull.go:55`) с wake=1 — **уже после того, как
   процесс завершился или ещё работает**. Это и есть вторая правда.
   Синхронный SDK-вызов, который дождался быстрого завершения в первые 1 с
   (bash.go:211-250), удаляет shell из таблицы без всякой строки — ок, итог
   и так в ответе инструмента.
3. **Дочерние Drain-ходы на `context.Background()`** — не отдельный путь
   создания, а те же 1–2, исполненные в ходe делегированного ребёнка:
   shell принадлежит child-сессии (`SessionID`), а запуск живёт дольше
   хода, потому что ctx у shell отсоединён. Обратная сторона: `Stop`/Rerun
   на ребёнке рвут ход, но shell-процесс продолжает жить (R8B-2, R8B-4).

### 1.2. Кто пишет итог и уведомление (путь 2)

- Итог (stdout/stderr/exit) — только в памяти:
  `BackgroundShell.stdout/stderr` (`internal/shell/background.go:277-278`),
  читается `GetOutput` по требованию (`job_output`).
- Факт завершения — `close(done)` в горутине старта
  (`internal/shell/background.go:467-488`): `completedAt` → `activeJobs-1` →
  `close(done)`.
- Уведомление —Later: `OnDone`-горутина (`internal/shell/background_shell.go:171-201`)
  ждёт `done`, затем callback пишет строку `session_notices` и делает
  `wakeSession` (`coordinator_background.go:131-186`).

### 1.3. Окна между шагами (найденные дефекты)

| Окно | Дефект |
|---|---|
| «процесс завершился» → «строка `bg_shell_done` записана» | R7B-1: re-check делегации отпускал ребёнка со старым текстом; закрыто удержанием (`PendingCompletionsOwned`), т.е. ещё одним куском памяти-правды (`internal/agent/work_ledger_delegation.go:213-251`) |
| «строка записана» → «слот лимита решён» | R3B-6/R4B-1/R5B-1/R5B-2: лимит автоходов — отдельный счётчик `consecutiveAutoResumes` + map `bgShellOverCap` в памяти (`internal/agent/coordinator.go:332-338`, `coordinator_bgshell_cap.go:83-152`); каждый раунд находил дыру на стыке «строка есть / слота нет / множество over-cap не синхронно с долгом» |
| «Kill вызван» → «процесс реально умер» (наследник держит pipe) | R8B-2: shell вне таблицы, `done` не закрывается, удержание текло бы вечно; лечено таймером от `detachedAt` (`internal/shell/background_completion.go:73-99`) — ещё одно состояние-компенсация |
| Stop попадает в 1-с паузу исполнителя | R8B-4: shell в таблице, но callback не зарегистрирован/исполнитель уже стейл — драйвер ребёнка не освобождается |

Общий механизм: **итог существует в трёх местах — память менеджера, строка
`session_notices`, счётчики лимита — и ни одно из них не меняется атомарно
с другим.**

### 1.4. Кто сегодня отвечает на «жива ли сессия из-за shell»

`childScopeDrained` (`work_ledger_delegation.go:213-251`): `ActiveOwned`
(память, `background.go:592-609`) + `PendingCompletionsOwned` (память,
`background_completion.go:73`) + `IsSessionBusy` + `CLIScope` (БД). Памятная
половина существует только потому, что строка появляется позже процесса.

## 2. Модель: одна строка на shell

### 2.1. Момент claim

Каждый shell, который **переживает ответ инструмента** (обе ветки: явный
`run_in_background` и авто-фон), получает строку `async_jobs`:

- kind: **`bg_shell`** (новый; см. §4 про миграцию CHECK).
- `tool_call_id`: идентификатор shell (`bgShell.ID`) для пути 2; для пути 1
  строка уже есть — новая строка НЕ создаётся, shell привязывается к ней.
- `owner_session_id`: сессия-владелец (как сегодня `SessionID` у shell).
- `result_summary` NULL, `delivery='none'`, `wake=0` — пока shell жив,
  строка «running» и есть единственный ответ на «есть работа»
  (ASYNC-02: `runningWorkOpen` уже читает running-строки из БД).

Claim происходит в `StartOwned`/сразу после него, до возврата ответа модели:
модель получает ShellID, а строка на него уже есть. Отказ claim (БД недоступна)
= отказ запуска фона (ошибка инструмента), как сегодня отказ по
`MaxBackgroundJobs` — не оставляем shell без строки.

Пути 1 и 2 различаются только тем, кто держит строку: у пути 1 она
инструментальная (awaitShell → `finish`), у пути 2 — собственно bg-shell
(§2.2). Для унификации путь 1 записывает `shell_id` в свою строку (§2.4),
путь 2 делает `tool_call_id = shell id`.

### 2.2. Завершение: итог + wake одной транзакцией

Единственный писатель терминального состояния строки — наблюдатель
завершения shell (горутина, ждущая `done`), который вызывает
`AsyncJobStore.Transition`:

- естественный выход: `state` = `completed`/`failed` (по `ExitCode`),
  `result_summary` = тот же текст, что сегодня строит `backgroundJobSummary`
  (`coordinator_background.go:104-113`), `delivery='pending'`, `wake` — по
  существующей таблице wake-политики (AutoResumeOnJobDone / делегированный
  ребёнок — как в `notifyBackgroundJobDone`; сама ПОЛИТИКА остаётся в
  drainPolicy/арбитре, строка честно пишет wake=1 и не решает, будет ли ход);
- `job_kill` / Stop / таймаут-terminate: `state='cancelled'`,
  `notice_kind='job_kill'`/`session_cancel`, `delivery='done'`, `wake=0`,
  `reacted=1` — тот же контракт, что у обычных задач сегодня (DUR-4,
  третий писатель reacted);
- «shell убит, но процесс не умер» (наследник держит pipe, R8B-2):
  терминальная транзакция пишется **по факту Kill-запроса**, а не по
  факту смерти процесса: Kill переводит строку в `cancelled` немедленно,
  процесс-менеджер дальше добивает дерево сам. Область сессии закрывается
  строкой, а не процессом — окно R8B-2 исчезает по построению.

Wake-уведомление модели строится при pull из строки (как для `command`:
`agent_notice_pull.go` восстанавливает текст из строки), отдельный форматтер
не нужен — `result_summary` уже в формате `backgroundJobSummary`.

Итог и долг (wake-строка) — **одна транзакция**: свойство «терминальный
переход и его долг коммитятся атомарно» (ASYNC-02) распространяется на
bg-shell без изменений механики.

### 2.3. Восстановление после падения хоста (DUR-6)

Running-строка `bg_shell` на хосте, чей lock-файл мёртв, обрабатывается
существующим sweep'ом мёртвых хостов: `Transition(interrupted, wake=…)`
по правилам DUR-6. Вывод не восстанавливаем (процесс умер вместе с
хостом, байтов больше нет): `result_summary` = «process lost with host».
Владелец получит факт прерывания решит перезапуск сам — так же, как
сегодня `interrupted` для обычных задач.

### 2.4. `shell_id` в `async_jobs`

Новая колонка `shell_id TEXT` (NULL для не-shell строк) + частичный индекс
`WHERE shell_id IS NOT NULL`. Назначение:

- `job_output`/`job_kill` разрешают job_id → строка → shell_id →
  процесс-менеджер. Сегодня связь строка↔shell держится в памяти
  (`asyncJobs.setShellID`, `job_shell_resolver.go`); колонка делает её
  чтение возможным из другого процесса (web-процесс видит shell CLI-сессии
  хотя бы как строку).
- `sessions jobs` и web «Команды» (`internal/server/handlers_livework.go:99`,
  `internal/cmd/sessions_jobs.go`) включают `bg_shell`-строки в вывод тем же
  запросом, что и `command`; running `bg_shell` виден как «выполняется»,
  терминальный — с итогом. Отдельного листинга фоновых shell больше нет:
  строки и есть листинг.

### 2.5. Лимит автоходов — интерфейс к арбитру (R-ARB)

Отдельный лимит bg-shell и вся его механика (карта over-cap, `bgArrival`,
`claimAutoResume`, `bgShellCapDeferred`, `coordinator_bgshell_cap.go`) не
переезжает, а удаляется; политика переезжает в арбитр (документ rarbd).
bg-shell обязуется давать арбитру только факты, без политики:

- по сессии: количество running-строк `bg_shell` (запросом),
- очередь фактов: pending-строки `bg_shell` (wake=1, reacted=0) с
  `updated_at` как моментом прибытия — тот же снимок, что арбитр и так
  читает для всего долга; при том, что прибытие теперь совпадает с
  терминальной транзакцией, «arrivals без строки» не существует,
  и вся пара «rowID запомнили / в долге не видно» (R5B-2) исчезает.

Ничего о слотах, человеческих сообщениях или решениях «давать ли ход»
строка не знает — это TurnFacts/Verdict арбитра.

### 2.6. Что видят наблюдатели после перехода

- `childScopeDrained`: убираются обе памятные проверки (`ActiveOwned`,
  `PendingCompletionsOwned`); «shell жив» = running-строка `bg_shell`
  (читается и в `CLIScope` через `runningWorkOpen`, и в
  `childScopeOpenAcrossProcesses` без отдельной ветки). Окно R7B-1
  закрыто атомарностью, а не удержанием.
- `job_output` во время работы: как сегодня, из памяти менеджера (живой
  процесс доступен только своему хосту — это свойство процесса, не правды).
- `sessions jobs` / web «Команды»: §2.4.

## 3. Что удаляется и что остаётся

**Удаляется:**

- удержания завершения: `holds`, `PendingCompletionsOwned`,
  `MarkCompletionRecorded`, `completionHoldMax`, `retentionMu`-логика
  callback-холдов (`internal/shell/background_completion.go` целиком,
  `OnDone`-регистрация холдов в `background_shell.go:171-201`);
  `ActiveOwned` остаётся только как счётчик конкурентного лимита процессов;
- отдельный путь уведомления: `notifyBackgroundJobDone` +
  `persistBGShellCompletion` + `bg_shell_done` как способ доставки
  (`coordinator_background.go:116-186`, `coordinator_bgshell_cap.go`);
  `InsertSessionNoticeReturningID` для этого вызова;
- память лимита: `consecutiveAutoResumes`-счётчики bg-shell, `bgShellOverCap`,
  `bgArrival`, seam-хуки (`coordinator_bgshell_cap.go:29-43`);
- памятная связь строка↔shell: `setShellID` в пользу колонки `shell_id`
  (маппинг в памяти менеджера остаётся только для живого процесса).

**Остаётся:**

- `BackgroundShellManager` как исполнитель процессов: старт, деревья-kill,
  bounded-буферы, ретеншн байтов, конкурентный лимит `MaxBackgroundJobs`
  (это про память/процессы, не про правду);
- путь 1 (async-обёрнутый bash) без изменений поведения;
- быстрые синхронные завершения в первые 1 с (bash.go:211-250): shell так и
  удаляется из таблицы без строки — итог вернулся в ответе инструмента;
  это единственный shell без строки, и он не переживает ответ.

## 4. Миграция

Новый файл `internal/db/migrations/<дата>000001_bg_shell_jobs.sql` (только
новый файл):

1. `shell_id TEXT` в `async_jobs` + частичный индекс. SQLite: колонка —
   обычный `ALTER TABLE ADD COLUMN`.
2. Новый kind `bg_shell`: CHECK-ограничение `kind` в SQLite нельзя
   расширить ALTER'ом — требуется rebuild таблицы (создать `async_jobs_new`
   с расширенным CHECK, `INSERT INTO … SELECT`, заменить). Альтернатива,
   если rebuild сочтут дорогим: не добавлять kind, а писать
   `kind='command', tool_name='bash', shell_id IS NOT NULL` — kind остаётся
   трёхзначным. Рекомендация: **rebuild с `bg_shell`** — таблица маленькая,
   а `sessions jobs`, purge-предикаты и recovery получают честный фильтр
   вместо тройного условия; операция одноразовая и вне горячего пути.
3. Уже записанные строки `session_notices` kind=`bg_shell_done` НЕ
   переносятся: код pull сохраняет отрисовку старого вида до их естественного
   дренирования (reacted/void), после чего строки уходят по существующему
   retention (`PurgeSessionNoticesOlderThan`). Переходный период возможен
   «гибридный shell» (запущен до, завершился после деплоя): его
   OnDone-callback сохраняется как совместимый путь ровно до обновления —
   на практике это один процесс веб-хоста, рекомендация: callback в новой
   версии, найдя shell без строки, дописывает строку и делает обычный
   `Transition` (код-мост ~15 строк, удаляется следующей минорной).
4. Откат: Down убирает колонку/индекс (rebuild) и восстанавливает прежний
   CHECK; строки `bg_shell` переводятся в `cancelled` перед дропом
   (Down не должен оставлять running-строки, которые старый код не увидит —
   старый код их просто не читает, но recovery DUR-6 для них тоже исчез бы).

## 5. Законы и тесты

**Строки реестра (`docs/async-invariants.md`):**

- ASYNC-02 — формулировка «shell считается работой, пока его `bg_shell_done`
  уведомление не стало durable» заменяется на «пока его строка `bg_shell`
  не терминальна»; упоминания `PendingCompletionsOwned`/удержаний удаляются.
- ASYNC-09 — «лимит bg-shell (веб, 5 на человеческое сообщение)» переносится
  в арбитр (строка факта та же); ссылка на `coordinator_bgshell_cap.go`
  снимается.
- DUR-1/DUR-4/DUR-6 — без изменений механики; в якорях добавляется `bg_shell`
  как обычный участник (пятый писатель reacted не появляется: job_kill/Stop
  пишут через те же три существующих писателя).
- Новая строка: **ASYNC-11** — «каждый фоновый shell, переживший ответ
  инструмента, имеет ровно одну строку `async_jobs`, и её терминальный
  переход — единственный факт его завершения; память процесса — только
  байты вывода». Якорь: claim в `StartOwned`, переход — единственный вызов
  `Transition` наблюдателем `done`.

**Тесты (реальная SQLite, `internal/session` + интеграционные в
`internal/agent`):**

| Сценарий | Что ловит |
|---|---|
| Claim: `StartOwned` → строка running; повторный claim того же shell | отсутствие второй правды; идемпотентность |
| Завершение: shell умер → ровно одна `Transition`, wake и итог в одной транзакции (fail середины транзакции — триггером) | атомарность ASYNC-02; регрессия R5B-2 (упавший insert больше не может рассинхронизировать лимит — лимита больше нет) |
| **R6B-1**: running-делегация на ребёнке + завершение его bg-shell → wake=1 в строке, drainPermitted запускает ребёнка | делигированный ребёнок не остаётся припаркованным |
| **R7B-1**: между смертью процесса и записью невозможно наблюдать «нет работы и нет долга» (зонд из re-check в обоих состояниях) | окно закрыто атомарностью, а не удержанием; тест на удержание переписывается на строковый |
| **R8B-2**: Kill по shell с неумирающим наследником → строка `cancelled` сразу, `childScopeDrained`=true, удержаний нет | утечка удержания и вечный park делегации |
| **R8B-4**: Stop в 1-с окне исполнителя → строка терминальна (cancelSession), stale-исполнитель не создаёт вторую запись (CAS проигрывает), драйвер освобождается re-check'ом | двойная правда «строка vs исполнитель» |
| DUR-6: running `bg_shell` на мёртвом хосте → sweep даёт `interrupted`, wake по правилам recovery, второй sweep — ноль фактов | восстановление, отсутствие дублей |
| Pull: текст уведомления из `result_summary` идентичен `backgroundJobSummary` (golden) | формат для модели не меняется |
| Старые `bg_shell_done`-строки: pending — дренируются и реагируют; done — видны в `sessions why` | совместимость миграции |
| `sessions jobs` / web «Команды» показывают running и терминальные `bg_shell` | наблюдаемость §2.4 |

Тесты, переписываемые с удаляемого состояния на наблюдаемое (перечислить в
отчёте R-BG-1): всё семейство `TestCompletionHold_*` (проверяли holds) и
`TestBGShellCap_*` (проверяли карту over-cap) — заменяются строковыми
аналогами выше; `drain_bgcap_*` — политикой арбитра, не этой работой.

## 6. Риски и открытые вопросы

1. **Rebuild `async_jobs` ради CHECK.** Риск: блокировка таблицы на время
   копирования (миллисекунды при текущих объёмах). Рекомендация: делать
   (см. §4.2); если оператор против — вариант «command+bash+shell_id»
   без rebuild, ценой тройного предиката в 4–5 запросах.
2. **Запуск фона требует БД.** Сегодня shell стартует при живой БД всё равно
   (сессия в БД), но отказ claim превращает «фон» в ошибку инструмента.
   Рекомендация: принять (fail-closed, как drainPolicy) — shell без строки
   и есть тот класс дефектов, который убираем.
3. **Гибридный период (§4.3).** Один код-мост в OnDone на один релиз.
   Рекомендация: оставить, удалив в следующей минорной; альтернатива
   «restart процесса перед деплоем» — операция проще, но хрупче для веб-хоста.
4. **Байты вывода остаются в памяти хоста-владельца.** Строка делает правду
   переносимой, но не вывод: `job_output` с другого хоста увидит итог из
   `result_summary`, а не живой поток. Сегодня это так же (shell вообще
   недоступен чужому хосту). Рекомендация: не менять (персист потока —
   отдельная работа, не цель).
5. **Порядок с R-ARB.** Реализация после R-ARB-2 (как в плане): лимитные
   факты нужны арбитру раньше, чем bg-shell перестанет их дублировать.
   Рекомендация: R-BG-1 не трогает политику лимита вовсе — только строки
   и удаление удержаний; карта over-cap удаляется рукой R-ARB-2.

## 7. Решения оркестратора (2026-10-01, обязательны для R-BG-1)

1. **Сначала полная инвентаризация, потом выбор модели.** R-BG-1 начинает с
   исчерпывающего списка мест, где bash/shell уходит в фон вне async-ветки
   `asyncTool` (sync-ветка `asyncTool` — SDK-вызовы и Drain-ходы на
   `context.Background()` без `WithCallOrigin`; прямые вызовы bash-инструмента
   без обёртки, если есть), с `путь:строка`, в отчёт.
2. **Предпочтительная модель — без нового kind.** Если каждый фоновый shell
   рождается из обёрнутого вызова (у которого уже есть строка `async_jobs`),
   уход в фон продолжает ЭТУ строку так же, как async-путь: ответ инструмента
   «ушло в фон» играет роль «started», строка остаётся `running`, `setShellID`
   + `awaitShell`, завершение — обычный `finish` → `Transition` с `wake=1`;
   callback `OnDone` для обёрнутых вызовов глушится всегда, а не только в
   async-ветке. Тогда не нужны ни kind `bg_shell`, ни rebuild таблицы (вопрос 1
   §6 снимается). Новый kind и rebuild — только если инвентаризация найдёт
   фоновые shell без строки; тогда rebuild принимается.
3. **Код-мост гибридного периода (§4.3, вопрос 3) не нужен:** shell — дочерний
   процесс rush; новая версия бинаря требует перезапуска процесса, вместе с
   которым его shell перестают принадлежать хосту, поэтому «запущен до деплоя,
   завершился после» не наблюдается. Старые строки `bg_shell_done` дренирует
   существующий код pull (остаётся только читающий путь).
4. **Вопросы 2, 4, 5 §6:** принять рекомендации документа (запуск фона требует
   БД — fail-closed; поток вывода не персистить; R-BG-1 после R-ARB-2 и без
   политики лимита).
