# Архитектура асинхронной работы: структурная конкурентность сессий

Статус: дизайн утверждён оператором 2026-09-27 (см. «Решения оператора»);
реализация не начата.
Связано: [план пробуждений](2026-09-24-agent-wakes-and-async-job-control.md),
[бэклог ревью 2026-09-25](2026-09-25-session-fixes-review-backlog.md) (BL-1…BL-7).

## Зачем

С 24.09 инструменты `bash`, `run_command`, `agent`, `agentic_fetch` в CLI и вебе
работают асинхронно: 8c98cdad, 2768d16a, 86259978, f8df9855 — около 5 тыс.
строк вместе с тестами за три дня. За те же три дня найдено восемь дефектов
потери управления: #1029, #1019/BL-1, #1032/BL-2, #1035, #1036, #1037, #1038 и
#1040. Симптомы разные, причины общие и структурные. Точечные исправления в
нынешней форме добавляют новые триггеры, опросы и охранники — та траектория,
которую CLAUDE.md описывает для `internal/agent/tools/mcp/init.go`. Код молодой,
а план пробуждений собирается добавить таймеры, остановку, inject и таймауты:
сейчас самый дешёвый момент поменять основу, а не наращивать её.

## Принцип (решение оператора, 2026-09-27)

> Процесс не завершается, пока не закончена работа потомков. Результат их
> работы приходит событием; что делать дальше — продолжать, остановить
> остальное или завершиться — решает корневой (старший) агент.

Это структурная конкурентность: у каждой единицы работы есть владелец; область
владельца не закрывается, пока живы её дети; результаты идут вверх событиями,
отмена — вниз.

Следствия:

- ожидание живой работы, в том числе долгоживущего процесса, — правильное
  поведение, а не зависание;
- зависание — только ожидание события, которое никогда не придёт; архитектура
  должна делать такое состояние невозможным, а не редким;
- чтобы корень мог решить «завершиться», у него должны быть средства увидеть и
  остановить свою работу (этапы 2–3 плана пробуждений);
- внешний предохранитель оператора (`--timeout`, Ctrl-C) остаётся и отменяет
  всю область целиком.

## Целевая модель

Пять основных частей: две новые (реестр работы, учёт областей) и три
существующие, которым оставляется одна роль. Пункты 6–7 — следствия и политика
поверх них.

### 1. Реестр работы — единственный владелец состояния задачи

Каждая длительная единица работы — одна запись:

```
Job {
  id             // стабильный: owner_session + tool_call_id (идемпотентный старт)
  owner          // сессия, которой сообщают результат
  kind           // command | agent | fetch | timer (план пробуждений) | …
  child_session  // для agent/fetch
  shell_id       // для command
  state          // running → completed|failed|cancelled|timed_out|interrupted → delivered
  announced      // tool result о старте сохранён (ack gate)
  deadline       // необязательный и только явный (#1037)
  result         // текст, is_error, причина
  host           // процесс-исполнитель (lease) — для восстановления
}
```

Правила:

- в терминальное состояние задача переходит ровно один раз (CAS): finish, stop,
  timeout, cancel и interrupted соревнуются за один переход, проигравшие —
  no-op;
- доставка — ровно один раз (CAS `delivered`), только при `terminal ∧ announced`;
- старт идемпотентен по ключу: повторный старт того же вызова возвращает
  существующую задачу (закрывает #1038 для делегаций);
- исполнители (`BackgroundShellManager`, запуск под-агента, будущий таймер) о
  доставке не знают: они только сообщают реестру «готово» или «ошибка».

Замещает `asyncJobRegistry`, хранилище `subAgentOutcomeRegistry` и учёт
`ActiveOwned` для целей доставки.

### 2. Доставка: сначала факт, потом будильник

Доставка = (а) записать уведомление в транскрипт владельца (как сейчас —
сообщение с флагом `BackgroundJobNotice`), затем (б) разбудить владельца.
Одинаково для корня и ребёнка, для CLI и веба.

- Факт долговечен раньше пробуждения. Если пробуждение не удалось (час пик,
  ошибка провайдера, остановка процесса), модель увидит уведомление на
  следующем ходу; ничего не теряется, а неудача становится видимым состоянием
  области (`sessions why`), а не строкой в Debug-логе.
- Пробуждение идемпотентно (ключ — id задачи). Уведомления, пришедшие, пока
  владелец занят, сливаются в один ход — это уже умеет mailbox
  (`drainOrReleaseMerged`).

### 3. Драйвер сессии — существующий mailbox как единственный инициатор хода

Mailbox с захватом и передачей владения и lock-файл не меняются. Меняется
другое: источники работы (уведомления о задачах, таймеры, inject, повтор из
долговечной очереди) не вызывают `c.Run` из своих горутин, а публикуют событие
для сессии; ход начинает только её драйвер.

«Поставлено в очередь» перестаёт быть `(nil, nil)`: вызывающий получает
дескриптор хода и ждёт его исхода, а fail-fast вызывающий — явную ошибку
«сессия занята».

### 4. Учёт областей — событие вместо опроса

Область — сессия и все её потомки. Для каждой сессии ведётся счётчик
незакрытого: незавершённые или недоставленные задачи (кроме `loop` и надзора) + идущий
ход + ожидающие события + открытые дочерние области. Счётчик меняется в тех же
точках и под тем же владельцем, что и состояние реестра и драйвера.

Когда счётчик области падает до нуля, публикуется одно событие «область
закрыта». Оно заменяет две нынешние механики:

- **делегация завершена**: область ребёнка закрыта → задача `agent` у родителя
  переходит в `completed` с итоговым ответом ребёнка → доставка родителю
  (п. 2). Четыре триггера и тикер `subagent_outcome.go` исчезают: триггер один
  и детерминированный;
- **CLI-хост завершается**: область корня закрыта → `rush run` печатает итог и
  выходит. Цикл опроса `descendantWorkPending` каждые 100 мс и BFS по БД
  исчезают.

Ожидания «события, которое не придёт», не бывает: область открыта, только пока
есть конкретная запись, которую `sessions why` может назвать, а у каждой записи
есть исполнитель или lease, по истечении которого она становится `interrupted`
и доставляется.

### 5. Долговечность и наблюдаемость

Реестр работы хранится в SQLite (миграция + sqlc), рядом с долговечной очередью
ходов:

- запись о задаче пишется в той же транзакции, что и tool result о её старте:
  ack gate становится свойством БД, а не флагом в памяти, и на горячем пути не
  появляется новых транзакций;
- `host` + lease: при старте процесса задачи мёртвых хостов переходят в
  `interrupted` и доставляются владельцам (#1040);
- `sessions why/list` и веб читают реестр и счётчики областей напрямую из любого
  процесса, без эвристик lock-файлов: BL-4 и BL-5 исчезают вместе с
  `descendant_liveness.go`;
- просмотр и остановка работы для человека (`rush jobs …` или расширение
  `sessions why`) и для агента (инструменты плана пробуждений) — одна модель.

### 6. Один путь исполнения

Инструмент всегда создаёт задачу. «Синхронный» режим (origin без асинхронности,
SDK) — это старт и ожидание той же задачи в пределах хода. Отмена, дедлайн и
доставка одинаковы в обоих режимах; ветка
`if origin != CLI && origin != Web { return inner.Run }` исчезает. Origin влияет
только на отображение.

### 7. Надзор: периодическое пробуждение корня

Предложение оператора (2026-09-27): раз в N минут (например, 5) будить корень,
чтобы он проверил под-агентов и запущенные команды. Это даёт старшему агенту
возможность действовать по принципу — заметить зависшего под-агента или
забытый процесс, остановить лишнее, завершиться — и страхует от ошибок в
доставке событий.

Место в модели: надзор — **политика поверх событий, а не замена им**. Если
полагаться на опрос вместо доставки, потерянное событие маскируется до
следующего тика, а каждый тик стоит хода модели. Поэтому ASYNC-04 остаётся
обязательным, а надзор реализуется как задача вида `timer`, владелец которой —
корень (тот же сервис сроков, что и у плана пробуждений).

Правила, чтобы тик был полезным и дешёвым:

- **Срабатывает только после тишины в чате корня (решение оператора):** 5 минут
  в сессии корня не появилось ни одного сообщения — ни один под-агент не
  завершил работу, ни одна команда не завершилась — при этом у области корня
  есть незакрытая работа и корень не выполняет ход. Любое новое сообщение в
  чате корня сбрасывает отсчёт; когда работы нет, тика нет.
- **Приходит со сводкой из реестра:** что запущено, сколько идёт, последняя
  строка вывода, давность последней активности каждого потомка. Модели не нужно
  тратить вызовы инструментов на осмотр; «всё в порядке, жду» — короткий ответ.
- **Отмечен как системное событие**, а не реплика пользователя (как уведомления
  о задачах).
- **Ограничен:** интервал растёт при подряд идущих тиках без изменений
  (например, 5 → 10 → 20 мин, с верхней границей), и есть предел подряд идущих
  тиков без прогресса (как `maxConsecutiveAutoResumes`); по пределу — видимое
  состояние области, а не молчаливое ожидание.
- **Не раздувает контекст:** устаревшие сводки надзора можно не передавать
  модели, когда пришла новая — актуальна только последняя.
- **Стоимость и кэш:** интервал стоит согласовать с TTL кэша промпта
  провайдера. Пока кэш тёплый, тик дешёвый; после истечения каждый тик заново
  читает весь контекст по полной цене.
- **Настраивается:** значение по умолчанию и отключение — в конфиге и флагом
  `rush run`; агент сам может сменить интервал или отключить тик (инструменты
  плана пробуждений).

Надзор за детьми: по умолчанию будится только корень — со сводкой по всему
дереву. Он может передать указание ребёнку (`inject_agent`) или остановить его.
Будить каждого потомка — кратно дороже; это отдельное решение.

## Что сохраняется и что удаляется

Сохраняется без изменения поведения: mailbox и передача владения; lock-файл и
heartbeat; долговечная очередь ходов с lease и at-most-once для промптов;
`BackgroundShellManager` как исполнитель команд; fantasy; формат уведомлений для
модели и веба.

Удаляется по мере фаз: `subagent_outcome.go` (742 строки: паркинг, четыре
триггера, тикер, BL-1, BL-2); двойной путь `asyncJobRegistry` (ready-очередь
против callback); цикл вытягивания в `app_run_async.go` и `descendantWorkPending`;
`descendant_liveness.go` с эвристиками; горутины `c.Run` в
`notifyAsyncCompletion` и `notifyBackgroundJobDone`; синхронная ветка
`asyncTool.Run`.

## Как ложится план пробуждений

Этапы 2–4 плана становятся возможностями ядра, а не новыми путями:

- таймер (`wakein`, `wakeon`, `loop`) — задача вида `timer` с общей доставкой
  (п. 2); дедлайны задач и сроки таймеров обслуживает один сервис сроков — одна
  горутина с ближайшим сроком;
- просмотр и остановка команд и под-агентов, таймаут делегации — операции
  реестра (`Inspect`, `Cancel`, `deadline`);
- `inject_agent` — событие для драйвера дочерней сессии;
- долговечность расписаний — та же таблица и тот же lease, что у задач.

Без ядра каждый пункт добавил бы ещё один путь доставки и ещё несколько
предикатов «ещё есть работа».

## Миграция: по шагам, каждый шаг — рабочая система

**Фаза 0 — законы и сетка.** `docs/async-invariants.md`; сценарные тесты
«чёрного ящика» на уровне `rush run` и транскрипта, которые переживут замену
механизма: результат `bash` ребёнку (#1029), внуки, отмена вниз, делегация
завершается после всей работы ребёнка, долгоживущий процесс держит корень, пока
корень его не остановит, прерывание хода не трогает задачи, отмена оставляет
терминальную запись. Белые тесты удаляемых реестров не переносятся — переносятся
их сценарии.

**Фаза 1 — реестр работы в памяти.** Одна машина состояний; `asyncJobRegistry`
и паркинг сливаются; исполнители сообщают только «готово». Класс BL-1/BL-2
исчезает вместе с `finishParked`.

**Фаза 2 — единая доставка и драйвер. РЕАЛИЗОВАНО** (2026-09-28,
`docs/plans/2026-09-27-async-phase2-spec.md`). «Факт, потом будильник»
(`coordinator.wakeSession`); все источники (`notifyAsyncCompletion`,
`notifyBackgroundJobDone`) публикуют через неё, не строят ход сами;
`runAwaitingAdmission` — дескриптор хода вместо `(nil, nil)` для
`runSubAgent`. Закрывает #1035, #1036, #1037, #1054; удаляет горутину
`runAutoResumeRecovered` и ветвление по origin в `asyncTool.Run` (единый
путь через реестр с явными таймаутами двух видов). `docs/async-invariants.md`
переанкерён (ASYNC-03/04/06/07/08/09).

**Фаза 3 — учёт областей.** Событие «область закрыта»; CLI-хост ждёт его;
делегация завершается по нему. Удаляет цикл опроса и BFS.

**Фаза 4 — долговечность.** Таблица задач и lease; восстановление →
`interrupted`; `sessions why/list` читают реестр. Закрывает #1040, BL-4, BL-5;
удаляет `descendant_liveness.go`.

**Фаза 5 — план пробуждений поверх ядра** (его этапы 2–5). Надзор (п. 7) —
первый потребитель сервиса сроков: ему нужны только таймер, сводка из реестра и
общая доставка, без новых инструментов. Поэтому его можно сделать сразу после
фазы 3, раньше остальных пунктов плана.

До рефакторинга исправлять только то, что стреляет сейчас и не будет выброшено:

- **#1029** — минимально и в сторону п. 2: цикл CLI-корня регистрируется как
  разборщик очереди своей сессии; уведомления любой сессии без разборщика идут
  тем же путём пробуждения, что у веба;
- **#1016, #1017, #1031** — слой lock-файлов и лимит размера файлов;
  рефакторинг их не касается.

Остальные находки (#1019, #1032, #1035, #1036, #1037, #1038, #1040) чинить в
нынешней архитектуре не стоит: фазы 1–4 закрывают их как класс, а заплатки
пришлось бы выбросить.

## Риски

- **Радиус изменений — ядро исполнения ходов.** Mailbox не трогаем; фазы
  независимы; сценарные тесты фазы 0 обязательны до фазы 1; каждая фаза — в
  отдельном worktree с полной проверкой.
- **Нагрузка на SQLite** (у оператора уже были простои БД дольше 45 с). Запись
  задачи идёт в той же транзакции, что и tool result; фаза 4 отделена и может
  подождать.
- **Меняется наблюдаемая семантика.** Делегация завершается, когда закончена
  вся работа ребёнка, а не его ход. Это желаемое поведение по принципу, но
  пользователь его заметит — отразить в CHANGELOG.
- **Лимит 1000 строк.** Реестр, доставка, области и восстановление — отдельные
  файлы одного пакета.

## Решения оператора

Приняты 2026-09-27:

1. Принцип и модель утверждены.
2. «Отсоединённой» (`detached`) работы нет: любая задача удерживает область до
   своего завершения.
3. `rush run` ждёт работу области, включая разовые таймеры. Периодический `loop`
   и надзор область **не удерживают**: главный агент не отменяет их отдельно — он
   просто обычным образом завершает работу, и когда другой открытой работы нет,
   `loop` и надзор снимаются автоматически.
4. Порядок: хотфиксы (#1016, #1029, #1017/#1031) → фаза 0 → фазы 1–5.
5. Надзор: включён по умолчанию, интервал 5 минут, срабатывает после 5 минут
   тишины в чате корня (ни один под-агент и ни одна команда не завершились),
   будится только корень; рост интервала и предел тиков без прогресса — как в
   п. 7, параметры настраиваются.
