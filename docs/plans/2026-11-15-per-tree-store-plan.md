# Хранилище по деревьям сессий: дизайн и план (2026-11-15)

- Статус: дизайн и план задач; исполнение — ПОСЛЕ приёмки спринта 0 (структура каталогов), по решению оператора. Задачи заведены с зависимостью от приёмки (#89). Кода в этом документе нет.
- Повод: в проекте shamir-db исполнитель упал с кодом 70, `batch runtime fault: jobbatch: commit failed: timeout`; общий файл `rush_store_v1.db` там 7,3 ГБ (рядом старый `rush.db` 5,5 ГБ). Идея оператора: отдельная БД на каждую корневую сессию (запущенную из web или CLI) вместе со всеми её под-сессиями, плюс малая общая БД; быстрый поиск корня по под-сессии, инструменты управления под-сессиями.
- Термины: **дерево** — корневая сессия и все её потомки (связь `sessions.parent_session_id`). Не путать с batch root: `root_id` в `batch_nodes` — корневой узел batch внутри дерева.

## 1. Факты о текущем хранилище

- Один файл на проект: `<data>/rush_store_v1.db`. WAL, `busy_timeout` 30 с (`internal/db/connect.go: BusyTimeout`), писатель — одно соединение на файл (`SetMaxOpenConns(1)`), читатели — отдельный пул. SQLite допускает одного писателя на файл, поэтому ВСЕ процессы проекта (web-сервер, каждый `rush run`, каждый агент) стоят в одной очереди на запись; ожидание дольше 30 с даёт `commit failed: timeout`, а чем больше файл и транзакции, тем дольше каждая фиксация.
- 26 таблиц, 22 SQL-файла, ~140 запросов. Почти все таблицы ссылаются на `sessions(id)` с `ON DELETE CASCADE` (внешние ключи включены): `files`, `messages`, `read_files`, `pending_injects`, `session_run_queue`, `orphan_call_outbox`, `session_drivers`, `session_notices`, `wake_schedules`, `batch_nodes`, `batch_control_requests`, `batch_timeout_checkins`, `session_agent_*`, `session_role_contracts`, `session_root_role_contracts`, `mcp_outputs`. Следствие: все они должны жить в одном файле с `sessions` своего дерева. Без внешнего ключа на сессию: `queue_tasks`, `async_hosts`, `session_permissions`, `batch_runner_checkpoints`.
- Размер на живом хранилище этого проекта (240 МБ, 141 сессия, 41 дерево, в среднем 3,4 сессии в дереве): `batch_nodes` 114 МБ (из них `response_envelope` 83 МБ), `messages` 79 МБ (`parts` 78 МБ), `files` 21 МБ (`content`), остальное мелочь. Объём — это содержимое сессий; координационные таблицы малы. Замер по shamir-db не делался (другой каталог, вне рабочей директории).
- Идентификаторы сессий — непрозрачные UUID; по id корень не определить.
- Девять мест открывают хранилище: `internal/app/app.go`, `internal/cmd/{batch_cli,root,sessions_batch_act,stats}.go`, `internal/server/r15bfixture/main.go`, `sdk/{library_mode,sdk}.go`.

## 2. Решение

1. **Файл дерева** `<data>/trees/<tree_id>.db` (`tree_id` = id корневой сессии): `sessions` дерева и все таблицы с внешним ключом на них, включая всё содержимое и всю batch-координацию дерева. Транзакции дерева (batch, финализация, долги реакций, уведомления, очередь запусков) остаются атомарными, как сегодня, потому что не выходят за дерево.
2. **Общая БД проекта** `<data>/rush_store_v1.db` (малая; имя сохраняется для совместимости): реестр деревьев, индекс «сессия → дерево», активность и общие очереди. Без внешних ключей на `sessions`; её таблицы — каталог ссылок, а не источник истины: пересобирается обходом файлов деревьев.
3. **Удаление дерева** — удаление файла (три файла WAL), без `VACUUM`; `purge` и `reap` работают по реестру.

## 3. Таблицы общей БД

| Таблица | Назначение | Кто пишет и как часто |
|---|---|---|
| `trees` | `tree_id`, путь файла, заголовок, статус (running/idle/ended/archived), `live_work`, время создания и обновления, суммарная стоимость, размер файла | при создании дерева, смене статуса и раз в N секунд (счётчики) |
| `session_index` | `session_id` → `tree_id`, `parent_session_id`, заголовок, статус, время | при создании сессии (редко относительно сообщений) |
| `async_hosts`, `session_drivers` (вариант А) | живые процессы и драйверы; их читает финализация («чужие живые драйверы», блок против поспешного завершения) и восстановление | heartbeat процесса, редко |
| `wake_due` | ближайшее время пробуждения на дерево (планировщик не открывает каждый файл) | при постановке и исполнении пробуждения |
| `queue_tasks` | очередь проекта (`rush queue`, `sessions pick`), не связана с сессиями внешним ключом | команды очереди |

Вариант Б для хостов и драйверов: хранить в файле дерева, а общая БД держит только «есть живая работа» в `trees.live_work`. Решение принимается в R0 после инвентаризации запросов (§4).

## 4. Межъядерные запросы: что нужно перенаправить

Запросы, которые сегодня видят все сессии сразу и после разделения идут через реестр: `ListSessions`/`ListAllSessions`/`ListSubSessions`, `ListLiveBatchRootsForHost`, `BatchRecoveryRoots`/`Elect`/`Interrupt` (восстановление после падения: обход деревьев с `live_work`), `ListAsyncHostRows`, `ListPendingRunQueueEntries`, `ListStaleLeasedRunQueueEntries`, `ListPendingOrphanOutboxEntries`, `ListCandidateInterruptedAssistantSessions`, `ListAllUserMessages`, `ListAllSessionPermissions`, запросы статистики и стоимости (`stats.sql`), `sessions grep/audit/cost/diff`, очереди пробуждений. Для каждого R0 фиксирует: остаётся в дереве (если принимает id сессии), идёт по реестру, или обходит файлы.
Единственная кодовая ссылка на «чужой корень» — `internal/agent/batch_install_adapters.go`.
Операции, пересекающие деревья (`sessions fork`, `inject` в чужое дерево): обычная запись в файл целевого дерева без общей транзакции; идемпотентность через идентификатор операции.

## 5. Поиск корня по под-сессии и инструменты управления

- Основной путь: `session_index` (одна строка на сессию, пишется при создании). Запасной: обход файлов деревьев (когда индекса нет или запись потеряна), результат кэшируется в индекс. Индекс — кэш: пересобирается командой `rush sessions reindex`.
- Необязательное дополнение: короткий префикс дерева в id новых сессий (`<tree8>-<uuid>`) — корень виден из id без запроса. Только для новых; старые id остаются непрозрачными. Решение в R0 (влияет на формат id во всех командах и web).
- Команда `rush sessions locate <id>`: дерево, файл, путь в дереве (цепочка родителей), статус.
- Команды управления поддеревом через корень: список детей, `show`/`kill`/`inject` по id под-сессии (поиск дерева автоматически), удаление дерева целиком. Часть уже есть (`sessions tree`, `kill`) — переводятся на поиск через индекс.

## 6. Маршрутизатор хранилища

Новый модуль `store/treestore` (после спринта 0 — в группе `store`): `Open(treeID)`, `Resolve(sessionID) → treeID`, `Create(rootSessionID)`, пул открытых файлов с вытеснением (LRU, предел по числу файлов, по умолчанию 32; предел дескрипторов Windows), закрытие простаивающих, общий жизненный цикл с `db.Release`. Код дерева (`session`, `jobbatch`, `message`) получает соединение дерева, а не проектное; код проекта (список, восстановление, очереди) — реестр. Миграции схемы: при открытии файла дерева применяется цепочка миграций (версия в самом файле); файл дерева и общая БД имеют отдельные цепочки.

## 7. Миграция и совместимость

- Режим по флагу `options.store.layout`: `single` (как сегодня, по умолчанию до приёмки) и `per_tree`.
- Команда `rush sessions split-store`: офлайн, возобновляемая, разбивает единый файл по деревьям (каждая корневая сессия и все потомки в `trees/<id>.db`), строит реестр и индекс, сверяет число строк по каждой таблице до и после, оставляет прежний файл как `rush_store_v1.db.pre-split` до явного удаления. Откат: вернуть файл и выключить флаг.
- Старый `rush.db` (форк до v1) в разбиение не входит; для него остаётся существующий импортёр.

## 9. Риски

- Транзакции через деревья (fork/inject): нет общей атомарности; нужна идемпотентность и порядок записей «сначала цель, потом источник».
- Дескрипторы и блокировки Windows: много открытых файлов; удаление открытого файла невозможно — закрыть перед удалением; три файла WAL на дерево.
- Восстановление после падения: обход всех деревьев с `live_work`; флаг в реестре должен быть надёжным (иначе потерянная работа), поэтому реестр пересобирается по запросу и при старте проверяется выборочно.
- Миграции схемы по N файлам: ленивое применение при открытии и отдельная версия.
- Дублирование и рассинхронизация индекса: индекс — кэш, источник истины — файлы деревьев.
- Нагрузка записи большими значениями: `batch_nodes.response_envelope` (83 из 114 МБ таблицы на этом хранилище) делает каждую фиксацию дорогой; отдельное улучшение — вынести его в боковую таблицу; решается в R0 по замерам, не входит в разделение.
- Порядок относительно других работ: разделение трогает `internal/db`, `internal/session`, `internal/jobbatch` — не вести одновременно со спринтом 0 и с задачей #70 (пересборка финализации).

## 11. Освобождение места после purge (замечание оператора, 2026-11-15)

Симптом: «Purge завершён: удалена 1368 сессий старше 7 дней… Место на диске пока не вернулось: 928,4 МБ из 1,4 ГБ в хранилище — свободные страницы. Нужен `rush sessions compact` (VACUUM). Запускать его?» Оператор хочет, чтобы занятое место не оставалось без ручных шагов.

Причина (проверено по коду): прагма `auto_vacuum` не задана (`internal/db/connect.go`, список `pragmas`), поэтому SQLite возвращает освобождённые страницы только в свой список свободных (`freelist`), а файл не уменьшается; `internal/db/compact.go` честно описывает, что `purge`/`gc` лишь передают страницы в freelist, а вернуть место файловой системе может только `VACUUM`; `sessions purge` печатает подсказку (`compactHint`) и ничего не делает. `VACUUM` требует исключительной блокировки и временного места порядка размера живых данных, поэтому его нельзя делать молча при работающих агентах.

Решение (двухступенчатое):
1. **Новые хранилища и файлы деревьев**: `PRAGMA auto_vacuum=INCREMENTAL` при создании; свободные страницы возвращаются порциями командой `PRAGMA incremental_vacuum(N)`, это обычная короткая транзакция записи, исключительная блокировка не нужна, работающим агентам не мешает.
2. **`purge`/`gc` сами возвращают место:** после удаления, если свободные страницы выше порога (по умолчанию более 20% файла или более 256 МБ), выполняют `incremental_vacuum` порциями (между порциями отдают блокировку) и `wal_checkpoint(TRUNCATE)`; прогресс и итог печатаются; флаг `--no-reclaim` отключает. Для хранилищ, созданных до изменения (режим `auto_vacuum=NONE`), разовое преобразование выполняет `rush sessions compact` (он задаёт режим и делает `VACUUM`) — только при отсутствии живой работы и достаточном свободном месте на диске (предварительная проверка «нужно X, свободно Y»); `purge` в этом случае печатает точную команду и оценку выигрыша, а не просто подсказку.
3. **После перехода на деревья** (R2–R5) проблема исчезает по построению: удаление дерева — удаление файла; в общей БД остаются малые таблицы, для неё действует п. 1–2.

Проверки: тест на хранилище с `auto_vacuum=NONE` (подсказка, без изменений), на хранилище с `INCREMENTAL` (файл уменьшается после `purge`), порционность (блокировка отдаётся между порциями, параллельный писатель не получает таймаут), WAL усечён, отказ при нехватке места, `sessions audit` показывает режим и долю свободных страниц. Побочная польза: короче окна записи, меньше таймаутов фиксации.
