## Decisions
- Каждый WORK-инструмент идёт батчем из одного элемента (OneItem); управляющие инструменты (await_tasks, batch_*, ask_question, wakein/wakeon/loop/wake_list/wake_cancel, inspect/inject/stop_agent) — не листья батча, но проходят политику (D1; подтверждено строгим ревьюером, оператор может переопределить). Отклонено: батч для await (взаимная блокировка слотов допуска).
- Новый путь инертен за `RUSH_BATCH_RUNTIME` до пакета R12, где старый путь удаляется целиком; никаких двух живых источников терминальной истины. Деструктивная миграция `async_jobs` без конвертации строк за проверкой живых хостов (OS host-lock probe).
- Commit-hook: `CommitHook func(context.Context, Transition) error` + обязательный `CommitTimeout`; ошибка/паника/таймаут = неизвестный исход → Runner faulted (`ErrCommitFailed`), независимое сдерживание, код выхода процесса 70 (D3/D4). Архитектура R4 — конвейер: один цикл владеет Engine и никогда не блокируется на хуке, один коммиттер вызывает хук по порядку и публикует внешние эффекты; решено вместо заплаток мини-цикла после трёх подряд P1.
- CLI-провайдер не исполнитель-семейство (это модельный провайдер); его retained Wait из R3 потребляет только агентский адаптер R7c.
- Автоматический reviewer внутри rush часто даёт FAIL по P2/покрытию; приёмку решаю сам: P0/P1 с воспроизводимым сценарием чиню в цикле, P2/P3 — в backlog (Review Stop Rule). Тесты агентов не принимаю на слово: перегоняю сам (race, lint, формат) и читаю ключевой код.
