## По каждому finding'у

### R5-1 — P0: scoped calls fail open to the shared unscoped toolset

**Коммит:** `a4361bb0` — `fix(agent): fail closed instead of widening to the shared toolset`

**Проблема:** `pinCallTools` возвращал `nil` при ошибке сборки инструментов или ready-gate,
и три вызывающих (`resolveSessionModelsInternal`, `applyModelOverrides`,
`resolveCredentialsModels`) сохраняли `nil` без сигнала ошибки. На старте хода
`nil` означало `a.tools.Copy()` — общий неограниченный набор инструментов процесса.
Для вызова с `FolderScope` или `DiskProvider` это возвращало `view`/`write`/`edit`/
`glob`/`grep`/`ls` и sub-agent инструменты, которые per-call сборка и удаляла.
SDK-вызовы auto-approve, так что никто другой не ловил бы расширенный набор.

**Исправление:** На всех трёх точках вызова добавлена проверка:
```go
if resolved.tools == nil && scopedCallToolsRequired(ctx) {
    return nil, ErrScopedCallToolsUnavailable
}
```
`scopedCallToolsRequired` проверяет `CallOptions.FolderScope != nil || DiskProvider != nil`.
Не-scoped legacy-вызовы сохраняют историческое падение на общий набор.

**Доказательство:** 7 регрессионных тестов в `r5_1_pincalltools_failclosed_test.go`:
- `buildTools` failure и ready-gate failure для `Run`, `RunWithCredentials`,
  и DiskProvider-only вызова — все fail closed
- unscoped вызовы — по-прежнему падают на общий набор (обратная совместимость)

**Статус:** ✅ Закрыто. Исправление точечное, логика ясная.

### R5-2 — P0: symlink resolution can bypass a nested deny carve-out

**Коммиты:** `e567dd48` — `fix(agent,app): canonicalize folder-scope roots` + 
`83ca7e83` фиксирует побочную регрессию ведущего слеша под реальным WorkingDir

**Проблема:** Корни scope'ов компилировались в лексической форме
(`filepath.Join + Clean`), а пути запросов — после `EvalSymlinks`. Симлинк
`/work/alias → /work/private` с deny carve-out на `/work/alias` переставал
совпадать после резолва, в то время как более широкий родительский grant на
`/work` всё ещё матчился.

**Исправление:**
1. Добавлен `tools.CanonicalizeFolderScopeSpec` — использует тот же алгоритм
   `resolveScopedPath` (longest-existing-prefix + `EvalSymlinks`) и тот же
   `DiskProvider` для разрешения `WorkingDir` и всех `Dir` записей перед
   `BuildFolderScope`.
2. Вызван в `ExecuteRun` (перед первичной компиляцией; сырой spec всё ещё
   сохраняется) и в `RebuildSessionAgentCall` (повторная каноникализация на
   каждый durable-рестарт, потому что симлинки на диске могли измениться).
3. Ошибка каноникализации → zero deny-everything `FolderScope` (fail closed).

**Побочная регрессия, пойманная во время обзора:** изменение R5-6 для
`resolveScopedPath` убрало `filepath.Abs` для уже-SmartIsAbs путей, но
`BuildFolderScope` тоже начал считать SmartIsAbs(dir) "уже разрешено" без
проверки на то, что `WorkingDir` находится в той же driveless-virtual namespace.
Under реальным `D:\project` ведущий слеш `{Dir: "/foo"}` переставал джойниться
и становился недостижимым корнем — выключая deny carve-out. Исправлено проверкой
`filepathext.SmartIsAbs(spec.WorkingDir) && !filepath.IsAbs(spec.WorkingDir)`.

**Доказательство:**
- `r5_2_canonicalize_folder_scope_test.go` — 303 строки, real symlink deny carve-out
  под широким grantом, как в обзоре
- `r5_2_rebuild_folderscope_symlink_test.go` — durable-перезапуск с симлинком
- `app_run_folder_scope_test.go` / `r5_2_symlink_carveout_test.go` — уровень приложения
- `r5_6_leading_slash_regression_test.go` — ведущий слеш под реальным WorkingDir
  всё ещё джойнится и deny'ит

**Статус:** ✅ Закрыто. Дополнительная регрессия поймана и закрыта на месте.

### R5-3 — P1: durable folder-scope replay drops the rest of CallOptions

**Коммит:** `54a98e2b` — `fix(agent,session): restore full CallOptions on durable replay`

**Проблема:** `RebuildSessionAgentCall` строил `CallOptions` только с `FolderScope`,
потеряя `DisableSubAgents`, `ModelRole`, `TimeoutOptionsSet`,
`TimeoutExtendsOnProgress`, `TimeoutHardCap`. Самый серьёзный эффект:
вызов с `--agents single` после рестарта неожиданно восстанавливал delegation
инструменты.

**Исправление:**
1. Добавлен `session.CallOptionsSpec` — JSON-сериализуемое зеркало replay-релевантных
   полей `CallOptions` (DisableSubAgents, ModelRole, три timeout-поля).
2. `toSessionCallOptionsSpec` / `fromSessionCallOptionsSpec` в `call_data_conversion.go`
   — парные конвертеры.
3. `SessionAgentCallData.CallOptionsSpec` носитель.
4. `RebuildSessionAgentCall` теперь вызывает `fromSessionCallOptionsSpec` и строит
   полные `CallOptions`.
5. Умышленно исключены: `MaxCost`/`MaxTokens` (уже отдельно на `SessionAgentCallData`),
   `FolderScope` (свой `FolderScopeSpec`), `AllowPeakHours`/`FailIfSessionBusy`
   (принимаются на этапе подачи, не релевантны при реплее),
   `DiskProvider` (не сериализуемо, refused перед durable-очередью).

**Доказательство:** `r5_3_calloptions_durable_roundtrip_test.go` — round-trip через
`ToSessionAgentCallData → JSON → RebuildSessionAgentCall` с FolderScope +
DisableSubAgents + явный all-zero timeout + не-default ModelRole, проверка что
каждое поле восстанавливается И вступает в силу downstream (pinned toolset,
watchdog, role).

**Статус:** ✅ Закрыто. Схема версионирования (`CallOptionsSpecVersion = 1`) добавлена.

### R5-4 — P1: documented SDK sentinel errors cannot be referenced externally

**Коммит:** `451f8f8c` — `feat(sdk): export ErrSessionBusy and ErrDiskProviderNotDurable`

**Проблема:** README и sdk.go рекомендовали `errors.Is(err, agent.ErrSessionBusy)`,

   отдельный модуль со своим `go.mod`, импортирует только `sdk`. revert-check
   подтвердил: удаление aliases → модуль не компилируется (undefined), не просто
   падает assertion.

**Доказательство:** Внешний модуль `rush-embedder-check` компилируется и проходит.

**Статус:** ✅ Закрыто.

### R5-5 — P1: fs_write overwrites after failing to read existing content

**Коммит:** `83ca7e83` — `fix(agent/tools): refuse fs_write when the pre-write content snapshot can't be read`

**Проблема:** При существующем файле `fs_write` игнорировал любую ошибку
`DiskProvider.ReadFile`, оставлял `oldContent = ""` и перезаписывал файл.
Дифф выглядел как "создание с нуля", история/undo baseline была сломана.
Транзиентная ошибка провайдера → молчаливая потеря данных.

**Исправление:** Ошибка `ReadFile` классифицируется через `osFailureIsFatal`
(та же split что и для `MkdirAll` выше в той же функции):
- фатальная → `FSBatchAbortError`, весь batch отменяется
- нефатальная → ошибка по этому элементу
В обоих случаях `WriteFile` и `commitFileChange` не вызываются без
доверенного старого значения.

**Доказательство:** `TestFSWriteFailedSnapshotReadBlocksWrite` в `fs_write_test.go` —
Stat говорит что файл существует, ReadFile падает, WriteFile НЕ вызывается,
записей истории ноль.

**Статус:** ✅ Закрыто. Исправление логично, повторно использует существующий
паттерн классификации ошибок.

### R5-6 — P1: ephemeral library mode has no logical filesystem root

**Коммиты:** `336b81c0` — `fix(sdk,agent,permission): synthesize a stable virtual root`

**Проблема:** `ModeLibrary` с пустым `WorkingDir` и in-memory БД оставлял
`ConfigStore.WorkingDir() = ""`. Относительный `FolderScopes` (`{Dir: "src"}`) 
hard-fail в `BuildFolderScope`. Абсолютный виртуальный scope всё ещё страдал от
того, что относительный путь модели (`scoped/virtual.txt`) джойнился на пустой
WorkingDir → `filepath.Abs` → silently резолвился против CWD хостового процесса.

**Исправление:**
1. `sdk.LibraryVirtualRoot = "/rush-library-mode-root"` — синтезированный логический
   корень, deliberately не реальный путь на любой ОС.
2. В `openLibrary`: если `workDir == ""`, `configWorkingDir = LibraryVirtualRoot`
   (persistence workDir остаётся пустым/in-memory, не затрагивается).
3. `resolveScopedPath` больше не вызывает `filepath.Abs` для уже-SmartIsAbs путей
   (на Windows `filepath.Abs` через `syscall.FullPath` пере-роутит driveless путь
   против текущего диска хоста). Относительный путь без WorkingDir → явная ошибка.

**Побочная регрессия, пойманная во время обзора** (та же что и в R5-2 выше):
изменение R5-6 для `resolveScopedPath` могло выключить ведущий-слеш deny carve-out
под реальным WorkingDir — исправлено проверкой namespace WorkingDir.

**Доказательство:**
- `r5_6_library_virtual_root_test.go` — ModeLibrary + пустой WorkingDir +
  относительный scope + относительный путь модели, ноль доступа к хостовому диску,
  положительный и отрицательный оракул (путь не может быть под реальным CWD)
- `r5_6_leading_slash_regression_test.go` — ведущий слеш под реальным WorkingDir
  всё ещё джойнится

**Статус:** ✅ Закрыто.

### R5-7 — P2: durable rebuild discards the persisted request origin

**Коммит:** `15976210` — `fix(agent): restore durable Origin on rebuild`

**Проблема:** `SessionAgentCallData.Origin` корректно сериализуется через
`ToSessionAgentCallData`/`FromSessionAgentCallData`, но `RebuildSessionAgentCall`
строит `SessionAgentCall{}` литерал прямо из `data`, не используя
`FromSessionAgentCallData`, и не копировал `Origin`. Перезапущенный вызов
получал `OriginUnspecified` независимо от того, что вошло в очередь —
несогласованность с аудит/транспорт метаданными.

**Исправление:** `Origin: data.Origin` добавлено в литерал в `coordinator_interrupt.go`.

**Доказательство:** `r5_7_rebuild_origin_test.go` — проверяет что cli, web, sdk
оригины восстанавливаются после durable-перезапуска.

**Статус:** ✅ Закрыто.
