# Ревью улучшений prompt-cache

Дата: 2026-08-26 07:14:27 (Europe/Berlin)

Проверены коммит `f6aa416d` и текущие незакоммиченные изменения. Исследование выполнено статически, без запуска тестов и без изменения исходного кода.

## Итог

Улучшение получилось частично, но набор изменений пока не готов для стабильного релиза. Стабильный префикс prompt стал лучше, однако в keep-alive остаётся race, а часть usage и cache-аналитики всё ещё может давать неверные результаты.

## Что улучшено

- Todo-reminder перенесён в конец истории, поэтому его изменения не должны ломать весь общий cache prefix: `internal/agent/agent_prompt.go:166`.
- Для OpenAI/Azure добавлен стабильный session-scoped `PromptCacheKey`: `internal/agent/coordinator_providers.go:149`.
- Добавлена нормализация inclusive input для Google/OpenRouter/Vercel: `internal/agent/usage_normalize.go:27`.
- Детектор invalidation больше не сбрасывает предыдущий assistant usage на user/tool-сообщениях: `internal/cmd/sessions_cache.go:241`.

## Найденные проблемы

### Высокий приоритет: race в keep-alive

`fireCacheKeepAlive` удаляет pending entry и отпускает mutex до регистрации in-flight cancel-функции (`internal/agent/agent_cache_keepalive.go:146`, `:182`).

Возможная последовательность:

1. Таймер удаляет entry.
2. Начинается настоящий turn и вызывает `cancelCacheKeepAlive`, но in-flight ещё не зарегистрирован.
3. Старый replay регистрируется и выполняется параллельно с настоящим turn.
4. После завершения replay при отсутствии map entry проходит проверка rearm (`internal/agent/agent_cache_keepalive.go:210`).

Это может запустить устаревший replay после начала нового turn, повторно заполнить старый prompt snapshot и увеличить расходы. Нужна единая per-session state machine с generation/canceled-состоянием. Простого `map[string]CancelFunc` недостаточно.

### Высокий приоритет: keep-alive отключён по умолчанию

Replay выполняется только при `RUSH_CACHE_KEEPALIVE=true` (`internal/agent/agent_cache_keepalive.go:102`). В обычной production-конфигурации эта часть не повышает cache hit. Если это rollout-флаг, его нужно документировать и включать только после исправления race.

### Высокий приоритет: replay не гарантированно повторяет форму исходного запроса

В начале turn копируется `agentTools` (`internal/agent/agent_turn.go:275`), но `PrepareStep` непосредственно перед запросом может заменить tools на другой snapshot (`internal/agent/agent_turn.go:1010`). В keep-alive передаётся старый список (`internal/agent/agent_turn.go:1432`). При обновлении MCP/SetTools внутри turn replay может иметь другой tool schema и не попасть в тот же cache prefix.

### Высокий приоритет для аналитики: cache support фактически всегда `native`

`providerCacheSupport` возвращает `CacheSupportNative` и при наличии, и при отсутствии cache counters (`internal/agent/usage_record.go:35`). Поэтому неизвестный или молчащий provider может показывать ложный `0%`, а `sessions cache` — ложные invalidation-сигналы. Новый `cacheProfiles` пока не подключён к классификации usage.

### Средний приоритет: title generation считает ненормализованный usage

В `internal/agent/agent_title.go:259` стоимость считается по исходному `resp.TotalUsage`. Для Google/OpenRouter/Vercel это может снова дважды учитывать cached input. Перед расчётом нужен `normalizeProviderUsage`.

### Средний приоритет: `MaxCost` не защищён от overspend

Проверка стоимости выполняется до replay (`internal/agent/agent_cache_keepalive.go:155`), а списание после него (`:274`). Параллельный настоящий turn может увеличить стоимость между этими операциями. Нужна атомарная reservation/check либо повторная проверка перед начислением.

### Средний приоритет: detector не отличает invalidation от истёкшего TTL

`sessions cache` трактует `warm → cold` как изменение prompt prefix (`internal/cmd/sessions_cache.go:218`), но не учитывает время между сообщениями и не знает cache key/prompt fingerprint. После обычного idle периода TTL истекает, и следующий turn выглядит точно так же.

### Code smell: keep-alive удерживает лишнее состояние и большие prompt history

Поля `tools`, `providerOptions` и `maxCost` в `cacheKeepAliveEntry` записываются, но фактически используются через closure (`internal/agent/agent_cache_keepalive.go:65`, `:119`). Closure также удерживает весь `messages` до срабатывания таймера. При большом числе idle-сессий это создаёт лишнее потребление памяти.

## Рекомендуемый порядок исправлений

1. Исправить keep-alive state machine и race между fire/cancel/schedule.
2. Определить production-политику для `RUSH_CACHE_KEEPALIVE`.
3. Передавать в replay фактический `prepared.Tools` и immutable snapshot options.
4. Подключить provider profile к `providerCacheSupport`.
5. Нормализовать usage в title generation.
6. Добавить cache-prefix fingerprint и учитывать TTL/idle time в `sessions cache`.

## Заключение

Стабильный prefix и OpenAI affinity сделаны в правильном направлении, но фактический прирост cache hit пока не подтверждён метриками. До исправления keep-alive race и ложной классификации usage эти изменения не следует считать готовыми для стабильного релиза.
