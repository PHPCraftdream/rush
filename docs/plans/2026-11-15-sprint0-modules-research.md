## 3. Разделить: горячие пакеты по смысловым границам

- **Batch размазан по пяти местам**: `agent/batch_*` (12 491 / 28 461, 174 файла), `session/batch_*` (6566 / 9035), `internal/jobbatch` (3822), `app/app_batch_*` (1731 / 4823), `cmd/batch_*`, обработчики `server`. Это один предметный контекст без своего дома.
- **Финализация** так же: `agent` (2344 / 4501), `session` (2757 / 4735), `app`, `server`.
- **`session` расслаивается**: внизу процессы и локи (§2), в середине базовое хранилище сессий (4814) и записи запусков `run_*` (4374), сверху ledger batch и финализации (9323). Мешает обратная связь: `session_*` берёт 13 идентификаторов из `finalization_*` и 6 из `batch_*`.
- **`cmd` sessions** (12 229 / 16 694, 122 файла, 108 коммитов за 90 дней) — самостоятельная подсистема CLI; тянет `internal/app` в 43 файлах, поэтому её тесты сейчас идут на любое изменение `agent`.
- **`app`**: конвейер запуска `app_run_*` (8150 / 22 693) против жизненного цикла, batch и настройки.
- **`config`**: база (типы, загрузка, каталоги данных) против каталога провайдеров (`load_providers*`, `model_*`, `catalog`) против хранилищ (`store_*`: OAuth, MCP, настройки).

## 4. Декомпозировать: циклы и «божественные» объекты

- **Ядро `agent` — один сильно связанный ком** ~45 тыс. строк: `coordinator` (12 822) берёт 63 идентификатора из `batch`, `batch` (12 491) — 14 из `coordinator`, `agent` (11 234) — 23 из `coordinator` и 20 из `turn`, плюс `call`, `delegation`, `disk`. Интерфейс `Coordinator` — 34 метода, проводка через сеттеры после конструирования. Разрезать пакет до разрыва этих циклов нельзя; первый шаг — типизированные наборы возможностей при конструировании (wave3 #2).
- **Цикл `session` ↔ `finalization` ↔ `batch`** (§3) разрывается портом: базовое хранилище не знает о финализации, финализация подписывается на него.
- **Тесты по номерам задач**: около 42 тыс. строк в файлах вида `p348_*`, `task1314_*`, `r5_*` (`agent` 61 файл, `session` 47, `server` 33, `app` 12). Они организованы по истории, а не по модулям: при переносе кода их нужно раскладывать по поведению, иначе тест останется в горячем пакете.

## 5. Абстрагировать: развернуть зависимости

- **`config` импортирует верхние слои**: `agent/cliprovider`, `agent/hyper` (`load_providers.go`, `hyper.go`, `provider.go`, `store_oauth_provider.go`), `discover`, `oauth/*` (`store_oauth.go`), `shell` (`config_mcp.go`, `resolve.go`). Ядро зависит от реализаций провайдеров. Разворот: каталог провайдеров как узкий лист без зависимостей (wave3 #3), резолвер значений `$(...)` как внедряемый интерфейс вместо `shell`. Выигрыш для CI мал (−13 с на коммит), выигрыш для архитектуры — ядро перестаёт меняться из-за провайдеров.
- **`cmd` sessions → `app`**: команды сессий открывают хранилище через `App`. Узкий «открыватель хранилища» (`session` + `db`) вместо `App` отрезает 16,7 тыс. строк их тестов от `agent`, `app` и провайдеров.
- **Возможности координатора** — типизированные наборы при конструировании (wave3 #2).
- **Порт batch-ledger** между runtime в `agent` и хранилищем в `session`.

## 9. Раскладка по каталогам: не более 7 модулей в каталоге, у каждого модуля свои тесты

Требование оператора (дополнение 2026-11-15): репозиторий должен быть красивым. В каталогах кода не более 7 элементов, в каждом файле кода не более 1000 строк, каждый модуль — со своими отдельными тестами; под это — автоматические линтеры и CI. Корневую папку репозитория не трогаем; лимит относится только к каталогам кода (§10.1). Первая редакция раскладки (§9.2–§9.3) считала только дочерние каталоги; требование «элементов» (каталоги и файлы) охватывает и пухлые пакеты — см. §9.7.

### 9.1. Что сейчас

Тесты, которые тянут вверх по графу: 5 файлов `session` (`package session_test`) импортируют весь `agent` (`p575_background_outcome_handoff_test.go`, `p588_partial_drain_test.go`, `p592_cross_row_identity_test.go`, `p624_drain_visibility_test.go`, `run_queue_round2_test.go`); тест `agent` (`supervision_notice_binding_app_test.go`) импортирует весь `app`; тест `permission` (`r14_5_current_virtual_root_regression_test.go`) — `agent/tools`; два теста `config` — `hooks` и `agent/codexprovider`. ### 9.3. Проверка слоёв: целевой порядок нарушают всего пять рёбер графа импортов

- `config` → `agent/cliprovider`, `agent/hyper`, `oauth/hyper` → `agent/hyper` (три ребра): известное — справочник провайдеров как лист без зависимостей (wave3 #3).

- Ребро `agent` → `nettransport` решается размещением: `nettransport` импортирует только `agent`, переезжает в `agent/provider/net`.

### 9.4. Правила для каталогов и тестов (предлагается закрепить проверками в CI)

1. **Не более 7 элементов в каталоге кода.** Элемент — подкаталог, содержащий код ниже по дереву, или рукописный файл кода (`.go`, `.ts`, `.tsx`). Не считаются: сгенерированные файлы (по маркеру, как в `check_file_size.sh`), `testdata`, некодовые ресурсы, корень репозитория. Скрипт `.githooks/check_dir_entries.sh` и список-храповик `.githooks/dir_entries_allowlist.txt` («<каталог> <число>», число может только падать; каталог, дошедший до 7, обязан выйти из списка), selftest, шаги в `pre-push`, `pre-push-fast.sh` и в `checks` job `ci.yml` (как у `check_file_size.sh`). Путь `.githooks/` уже входит в `always_run` политики CI. Считать ли тестовые файлы — вопрос В5 (§10.2); скрипт получает это параметром.
2. **Слои**: пакет не импортирует пакет из группы выше (проверка по `go list -deps`); исключения — только в списке-храповике, как `file_size_allowlist.txt`: можно убирать, нельзя добавлять.
3. **Тесты модуля — внутри модуля.** Тестовое замыкание модуля (`go list -test`) входит в его производное замыкание плюс список общих помощников (`kit/dev/testguard`, `store/db/dbtest`). Сценарии, которым нужны несколько модулей сразу, живут в отдельном пакете `internal/app/itest`: он единственный, кому разрешено импортировать всё, и гоняется отдельной полосой полного прогона.
4. **Перенос тестов по поведению, а не по истории.** ~42 тыс. строк в файлах `p348_*`, `task1314_*`, `r5_*` раскладываются по модулям, чьё поведение они проверяют; сценарные — в `itest`.

### 9.5. Что это даёт матрице

После раскладки каждый модуль запускает свои тесты только при изменении самого себя или его зависимостей; тесты `session` и `agent` перестают зависеть от верхних слоёв (§9.1). Оценка эффекта на секунды тестов отложена вместе с измерителем (§8): отображение «старый пакет → новые» лежит в скрипте раскладки и годится как вход, когда понадобится.
