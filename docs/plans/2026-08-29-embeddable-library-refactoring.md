# Rush как встраиваемая библиотека: проект рефакторинга

Дата: 2026-08-29. Статус: проект, код не написан.

Цель: код можно подключить как Go-библиотеку (`go get` + `import`), при
этом бинарник `rush` продолжает собираться и вести себя ровно так же.

Каждое утверждение ниже проверено чтением кода этого репозитория, а не
предположением. Ссылки `файл:строка` приведены, чтобы будущий читатель
мог перепроверить, а не поверить.

---

## 1. Посылка, которая оказалась неверной

Естественное первое предположение — «весь код под `internal/`, значит
для библиотеки надо вынести 35 пакетов наружу». Это неверно, и из этого
следует, что объём работы на порядок меньше ожидаемого.

**Правило `internal/` в Go — модульное, а не глобальное.** Импорт пути,
содержащего элемент `internal`, запрещён только коду вне дерева с корнем
в *родителе* каталога `internal`. Родитель здесь — корень модуля
`github.com/PHPCraftdream/rush`, поэтому **любой пакет внутри этого
модуля уже сегодня может импортировать `internal/...`**.

Доказательство лежит в репозитории: `main.go:16` — пакет в корне модуля —
импортирует `github.com/PHPCraftdream/rush/internal/cmd` и собирается.

Следствие: **ни один файл переносить не нужно.** Нужен тонкий публичный
пакет-фасад внутри того же модуля. `internal/` при этом остаётся
приватным — и это не компромисс, а защита: мы не берём на себя
обязательство поддерживать 35 пакетов как публичный API.

## 2. Что реально мешает

Ранжировано по тому, насколько блокирует встраивание.

### B1. Конверт результата неэкспортируемый

`runResult` (`internal/app/app_run_result.go:21`) и все пять вложенных
типов — `usageInfo`, `sessionUsageInfo`, `toolCallStat`,
`subAgentOutput`, `recoveredPartial` — с маленькой буквы.

Структура помечена «Wire-stable: fields here are part of the public
contract for wrapper scripts» (`app_run_result.go:19-20`) — то есть она
уже объявлена публичным контрактом, но по-настоящему публична только в
виде JSON-байтов. Встраивающий не может объявить переменную этого типа,
поле структуры или сигнатуру функции.

Стоимость исправления: механическое переименование. **JSON-теги не
меняются**, поэтому проводной формат не двигается ни на байт.

### B2. `RunNonInteractive` смешивает вычисление и рендеринг

`internal/app/app_run.go:409`:

```go
func (app *App) RunNonInteractive(ctx, output io.Writer, prompt string,
    overrides RunOverrides, hideSpinner bool, mode RunMode,
    continueSessionID string, useLast bool) error
```

Возвращает `error`, а результат отдаёт байтами в `output`
(`json.NewEncoder(output).Encode(summary)`, строка 796-799). Встраивающий
в том же процессе вынужден был бы сериализовать в JSON и тут же
распарсить обратно.

Хуже: `os.Stderr` захардкожен в пяти местах (строки 679, 818, 830, 886,
969) — эхо вызовов инструментов, прогресс-бар и guidance-сообщения нельзя
перенаправить **даже из CLI**. Это самостоятельный дефект, который
встраивание просто делает заметным.

Шов для расщепления уже существует: замыкание `finish`
(`app_run.go:697`) собирает полный `summary` и лишь потом его кодирует.

### B3. MCP — процессный синглтон

`internal/agent/tools/mcp/init.go:56-62`:

```go
var (
    sessions = csync.NewMap[string, *ClientSession]()
    states   = csync.NewMap[string, ClientInfo]()
    broker   = pubsub.NewBroker[Event]()
    initOnce sync.Once
    initDone = make(chan struct{})
)
```

`initOnce` означает: **один `Initialize` на процесс**. Два независимых
экземпляра приложения в одном процессе — второй не поднимет свои MCP
-серверы. Это единственный настоящий блокер мульти-инстанса, и он же
самый дорогой в починке.

### B4. `rushlog.Setup` перехватывает логгер хоста

`internal/log/log.go:76` вызывает `slog.SetDefault(...)`. Для CLI это
верно, для библиотеки — недопустимо: хост теряет свой логгер молча.

Дополнительно `internal/cmd/run.go:732` и
`internal/cmd/update_providers.go:40` тоже зовут `slog.SetDefault` — но
обе точки в CLI-слое, куда библиотека не заходит.

### B5. `os.Chdir` в резолвинге рабочего каталога

`internal/cmd/root.go:709` — `ResolveCwd` меняет рабочий каталог
**процесса**. Хорошая новость: это уже в CLI-слое, а не в `internal/app`.
Библиотека просто не должна этот путь звать.

Риск, который отсюда следует, — см. R1.

### B6. `os.Exit` — 15+ вызовов, все в `internal/cmd`

`login.go:227`, `models_preset.go:19`, `models_set.go:25`, `ping.go`
(×5), `providers_ping.go:78`, `root.go:272`, `run.go:629,661,692`.
Все — в CLI-слое. Библиотека не должна их достигать; это проверяемо
тестом-запретом, а не обещанием.

### B7. Процессные синглтоны второго порядка

| Место | Что |
|---|---|
| `internal/shell/background.go:329-331` | `backgroundManagerOnce` — общий менеджер фоновых задач |
| `internal/shell/expand.go:34` | `NoUnset atomic.Bool` |
| `internal/agent/cliprovider/provider_detection.go:20,85` | `AvailableFunc`, `detectAvailableCache` |
| `internal/config/docker_mcp.go:21,34` | кэш доступности + singleflight |
| `internal/config/load_worktree.go:48` | `worktreeRootCache sync.Map` |

Большинство — кэши внешних фактов (что установлено на машине), они
безвредны при общем использовании. Мутабельны по-настоящему только
`AvailableFunc` и `NoUnset`.

### Что, наоборот, уже готово

Два места, где ожидался блокер, а его нет — их стоит зафиксировать,
чтобы не «чинить» работающее:

- **`config.Init` не синглтон.** `internal/config/init.go:21-27`
  возвращает свежий `*ConfigStore` на каждый вызов. Несколько
  независимых конфигураций в одном процессе — уже возможны.
- **Пул БД считает ссылки по `dataDir`.** `internal/db/connect.go`:
  `Connect`/`ConnectRead`/`Release` с refcount. Два экземпляра на один
  `dataDir` корректно разделят пул, а не подерутся за файл.

## 3. Целевая архитектура

Три слоя, снизу вверх.

```
┌─────────────────────────────────────────────────┐
│ L3  internal/cmd  — CLI (cobra, os.Exit, Chdir) │
│     internal/server — web/WS (вне контракта v1) │
├─────────────────────────────────────────────────┤
│ L2  sdk/  — ЕДИНСТВЕННЫЙ публичный пакет        │
│     Open / Client.Run / Client.Close + типы     │
├─────────────────────────────────────────────────┤
│ L1  internal/*  — ядро, остаётся приватным      │
└─────────────────────────────────────────────────┘
```

**Ключевое решение: CLI становится первым потребителем библиотеки, а не
её соседом.** `rush run` идёт через `sdk`, а не мимо. Тогда расхождение
между «что умеет бинарник» и «что умеет библиотека» невозможно по
конструкции, а существующие тесты CLI автоматически становятся тестами
библиотеки. Это и есть механизм, гарантирующий требование «бинарник
собирается с тем же функционалом» — проверяемо, а не декларативно.

`internal/server` (веб-UI) остаётся на `internal/app` напрямую: веб не
входит в библиотечный контракт v1.

### Поверхность L2

```go
package sdk

type Options struct {
    WorkingDir string      // абсолютный; os.Chdir НЕ вызывается
    DataDir    string      // "" → <WorkingDir>/.rush
    Debug      bool
    MCP        MCPMode     // MCPOff | MCPEnabledInCLI | MCPAll
    Stdout     io.Writer   // nil → io.Discard
    Stderr     io.Writer   // nil → io.Discard
    SetupLogging bool      // default false: не трогать slog.Default() хоста
}

func Open(ctx context.Context, o Options) (*Client, error)
func (c *Client) Run(ctx context.Context, req RunRequest) (*RunResult, error)
func (c *Client) Close() error
```

`MCPMode` — прямое отображение уже существующего `app.RestrictMCPToCLI()`
и флага `rush run --all-mcp`, а не новая концепция.

### Про типы: почему нужны алиасы, а не «просто возвращать»

Тонкость, которая иначе всплывёт на реализации. Внешний код **может**
получить значение типа из `internal` через вывод типов
(`res := client.Run(...)`) и читать его поля. Но он **не может**
объявить `var r app.RunResult`, поле структуры или сигнатуру функции —
для этого нужен импорт `internal`, который запрещён.

Поэтому `sdk` обязан объявить алиасы:

```go
type RunResult       = app.RunResult
type UsageInfo       = app.UsageInfo
type SessionUsageInfo = app.SessionUsageInfo
type ToolCallStat    = app.ToolCallStat
type SubAgentOutput  = app.SubAgentOutput
type RecoveredPartial = app.RecoveredPartial
```

Алиас (`=`), а не новый тип: нулевое копирование, полная
взаимозаменяемость, ноль кода преобразования. Объявлять их можно, потому
что сам `sdk` импортировать `internal/app` вправе.

## 4. Фазы

Каждая — отдельный коммит с тестами. Фазы 1-3 независимы друг от друга и
могут идти в любом порядке; 4 зависит от 1-3, 5 от 4, 6 от 5. Фаза 7
опциональна и независима.

### Фаза 0 — сетка безопасности (до любых правок)

Дисциплина рефакторинга: сначала фиксируем границу «поведение не
меняется» и способ проверки, потом трогаем структуру.

- **Golden-тест JSON-конверта**: прогон с подставным провайдером,
  байты `rush run --json` сохраняются как эталон и сравниваются после
  каждой фазы. Утверждение, которое он защищает: **ни один JSON-тег и
  ни одно имя поля в проводном формате не меняется.**
- Остальное уже есть: `go test ./...`, `.githooks/pre-push` (сборка +
  тесты + lint под четыре GOOS).

Объём: малый. Без этой фазы остальные не проверяемы.

### Фаза 1 — экспортировать конверт (B1)

`runResult` → `RunResult`, `usageInfo` → `UsageInfo`,
`sessionUsageInfo` → `SessionUsageInfo`, `toolCallStat` → `ToolCallStat`,
`subAgentOutput` → `SubAgentOutput`, `recoveredPartial` →
`RecoveredPartial`.

Строго механически, JSON-теги не трогаем. Приёмка: golden-тест из фазы 0
проходит без изменения эталона.

Объём: малый. Риск: минимальный.

### Фаза 2 — расщепить вычисление и рендеринг (B2)

Выделить из `RunNonInteractive`:

```go
func (app *App) ExecuteRun(ctx context.Context, req RunRequest) (*RunResult, error)
```

— всё, что сегодня делает замыкание `finish`, но **без**
`json.NewEncoder(output).Encode(summary)` и без прямых обращений к
`os.Stderr`.

Потоки вывода переезжают в запрос:

```go
type RunRequest struct {
    Prompt            string
    Overrides         RunOverrides
    Mode              RunMode
    ContinueSessionID string
    UseLast           bool
    Stdout            io.Writer // nil → io.Discard
    Stderr            io.Writer // nil → io.Discard
    HideSpinner       bool
}
```

`RunNonInteractive` **сохраняется с той же сигнатурой и тем же
поведением** и становится тонкой обёрткой: зовёт `ExecuteRun`, при
`mode == RunModeJSON` кодирует результат в `output`, отображает
`RunResult` в `runIncompleteError` для кода возврата процесса.

Это принципиально для требования «функционал не меняется»: старая
функция остаётся на месте, все существующие тесты `internal/app`
продолжают её проверять как есть.

Побочно чинится реальный дефект B2 — пять захардкоженных `os.Stderr`.

Объём: средний. Это самая содержательная фаза.

### Фаза 3 — инъекция логгера (B4)

Добавить `log.NewLogger(path string, debug bool) *slog.Logger`.
`log.Setup` остаётся и становится `slog.SetDefault(NewLogger(...))` —
поведение CLI не меняется.

**Честная граница v1, которую надо записать в godoc, а не умолчать:**
ядро зовёт пакетные `slog.Info/Warn/Error` в сотнях мест, поэтому
внутренние логи по-прежнему уходят в `slog.Default()` хоста. Что
библиотека гарантирует — она **не перехватывает** `slog.Default()`, то
есть хост не теряет свой логгер. Полная изоляция логов — v2.

Обещать изоляцию, которой нет, хуже, чем назвать ограничение.

Объём: малый.

### Фаза 4 — фасад `sdk/` (основной блок)

`Open` делает ровно то же, что `setupApp` (`internal/cmd/root.go:333`),
минус три вещи: `os.Chdir`, безусловный `slog.SetDefault`, cobra.

Внутри фазы — **отдельная задача-аудит, а не допущение**: пройти по
инструментам и найти всех, кто читает `os.Getwd()` вместо рабочего
каталога из конфига. Приёмка аудита — тест, где `WorkingDir` намеренно
не совпадает с реальным cwd процесса, и запуск отрабатывает корректно.

Объём: средний.

### Фаза 5 — перевести CLI на фасад

`internal/cmd/run.go:787` перестаёт звать `a.RunNonInteractive` напрямую
и идёт через `sdk`. После этого дрейф между бинарником и библиотекой
структурно невозможен.

`runWebMode` не трогаем.

Объём: малый.

### Фаза 6 — доказательство встраиваемости

Тестовый Go-модуль в `testdata/embedder/` со своим `go.mod` и
`replace` на репозиторий, импортирующий **только**
`github.com/PHPCraftdream/rush/sdk` и выполняющий реальный запуск.

Это единственный способ доказать, что публичной поверхности достаточно и
что из неё ничего не «торчит» наружу неназываемым типом. Гипотетический
unit-тест внутри модуля этого не проверяет — он-то `internal` видит.

Плюс тест-запрет: в `sdk` не должно быть `os.Exit`, `os.Chdir`,
`slog.SetDefault`.

Объём: малый, ценность высокая.

### Фаза 7 — мульти-инстанс (опционально, отдельно)

Только если действительно нужно несколько независимых `Client` в одном
процессе. Требует убрать `initOnce` из `internal/agent/tools/mcp` и
сделать реестр per-App (B3), плюс разобраться с B7.

**Для v1 рекомендуется не делать, а честно задокументировать: один
`Client` на процесс.** Обоснование: основной сценарий встраивания — один
рабочий каталог на процесс; мультиворкспейс решается несколькими
процессами, и это уже боевой, оттестированный путь (lock-file +
heartbeat, `sessions_*.go`), а не гипотеза.

Объём: большой.

## 5. Имя и расположение фасада

Два варианта, различие существенное.

**Вариант A — `cmd/rush/main.go`, корень модуля становится `package rush`.**
Импорт: `github.com/PHPCraftdream/rush`, вызов `rush.Open(...)` — самый
красивый. Но меняет точку входа сборки, а она зашита в четырёх местах:
`Makefile:5`, `.goreleaser.yml` (секция `builds:` и строка 129 в
AUR-скрипте), `.github/workflows/publish-fork-npm.yml:137`.

**Вариант B — подкаталог `sdk/`.**
Импорт `github.com/PHPCraftdream/rush/sdk`, вызов `sdk.Open(...)`.
Изменений в сборке — ноль.

**Рекомендация: B для v1.** Смена точки входа сборки и проектирование
публичного API — независимые изменения; если смешать их и что-то
сломается, будет неясно, что именно виновато. Требование «бинарник
собирается с тем же функционалом» при варианте B выполняется тривиально
и проверяется существующим `.githooks/pre-push`.

Миграция в A позже — отдельный коммит, когда API устоится: фасад
переезжает в корень как `package rush`, а в `sdk/` остаётся файл из
шести строк-алиасов для обратной совместимости.

## 6. Как гарантируется «тот же функционал»

Пять механизмов, каждый проверяемый:

1. Точка входа сборки не меняется (вариант B) — `go build .` работает
   как раньше во всех четырёх местах.
2. `RunNonInteractive` сохраняет сигнатуру и поведение — все
   существующие тесты `internal/app` и `internal/cmd` остаются
   регрессионной сеткой, ничего не переписывается «под новый API».
3. Golden-тест конверта (фаза 0) — проводной формат байт-в-байт.
4. Фаза 5 делает CLI потребителем библиотеки — дрейф невозможен по
   конструкции, а не по дисциплине.
5. `.githooks/pre-push` уже гоняет `go build ./...`,
   `go test -short -failfast ./...` и lint под четыре GOOS.

## 7. Риски

**R1. Зависимость от cwd процесса.** `Open` не зовёт `os.Chdir`. Если
какой-то инструмент читает `os.Getwd()` вместо рабочего каталога из
конфига, пути разъедутся. Митигация — задача-аудит внутри фазы 4 плюс
тест с `WorkingDir` ≠ cwd. Не допущение, а работа.

**R2. Логи ядра идут в `slog.Default()` хоста** (см. фазу 3). Не блокер,
но должно быть в документации, а не сюрпризом.

**R3. Мутация конфига протекает между вызовами `Run` — латентный
дефект, который открывает именно библиотечное использование.**
`disableToolsInConfig` (`internal/app/app_run_gates.go:51-68`) удаляет
инструменты из опубликованного конфига и **ничего не восстанавливает**.
Собственный комментарий кода это признаёт
(`app_run_gates.go:26-28`): «only outlives this process if a future
caller reloads the in-memory config from disk — `rush run` exits
immediately after the agent turn so this is moot in practice».

«Moot in practice» верно ровно для одноразового CLI. `Client`, делающий
два `Run` подряд — первый с `DisableSubAgents: true`, второй с `false` —
получит во втором запуске урезанный тулсет. Нужен тест на это и решение:
восстанавливать состояние после запуска либо применять фильтр на копии,
не трогая опубликованный конфиг. Ловится в фазе 2 или 4.

**R4. Общий менеджер фоновых задач** (`internal/shell/background.go:329`)
разделяется между всеми `Client`. Не проявляется при «один `Client` на
процесс» (позиция v1), но должно быть записано как ограничение.

## 8. Чего не делаем

- **Не выносим `internal/*` наружу.** 35 пакетов как публичный API —
  обязательство, которое не потянуть, и оно не нужно: правило
  `internal/` модульное (раздел 1).
- **Не включаем веб-сервер и WebSocket-протокол в контракт v1.**
  Протокол `internal/server/protocol.go` заточен под конкретный
  React-фронтенд (~60 типов payload, без поля версии) и не готов быть
  внешним контрактом.
- **Не делаем мульти-инстанс в v1** (фаза 7 — опциональна).
- **Не меняем формат конверта** — это отдельный, уже существующий
  контракт, и рефакторинг не повод его двигать. Доработки конверта
  (`session_created`, `cost_basis`, `by_model[]`) спроектированы
  отдельно в `docs/plans/2026-08-27-agent-tree-backend-requirements-response.md`
  и с этим планом не связаны.

## 10. Итог одним абзацем

Главная поправка к постановке: выносить код из `internal/` не нужно —
правило Go модульное, и `main.go` уже сегодня импортирует `internal/cmd`
из корня модуля. Работа сводится к четырём содержательным вещам:
экспортировать типы уже объявленного «wire-stable» конверта, расщепить
`RunNonInteractive` на «посчитать результат» и «отрендерить вывод»
(попутно починив пять захардкоженных `os.Stderr`), не перехватывать
`slog.Default()` хоста и добавить тонкий фасад `sdk/`. Гарантия «бинарник
тот же» обеспечивается не обещанием, а тем, что CLI сам становится
первым потребителем этого фасада, точка входа сборки не двигается, а
проводной формат защищён golden-тестом. Мульти-инстанс — единственная
по-настоящему дорогая часть (процессный синглтон MCP), и он выносится за
границу v1 осознанно, потому что «несколько процессов на несколько
рабочих каталогов» в этом форке уже работает и оттестирован.
