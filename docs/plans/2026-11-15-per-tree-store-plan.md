# Хранилище по деревьям сессий: дизайн и план (2026-11-15)

- Статус: дизайн и план задач; исполнение — ПОСЛЕ приёмки спринта 0 (структура каталогов), по решению оператора. Задачи #96–#110 заведены с зависимостью от приёмки (#89); ведение задач — по этому файлу. Кода в этом документе нет.
- Открытый вопрос оператору (к R0): где по умолчанию папка данных пользователя — существующая глобальная папка данных (системный диск) или настраиваемый путь на `D:` (§15).
- Повод: в проекте shamir-db исполнитель упал с кодом 70, `batch runtime fault: jobbatch: commit failed: timeout`; общий файл `rush_store_v1.db` там 7,3 ГБ (рядом старый `rush.db` 5,5 ГБ). Идея оператора: отдельная БД на каждую корневую сессию (запущенную из web или CLI) вместе со всеми её под-сессиями, плюс малая общая БД; быстрый поиск корня по под-сессии, инструменты управления под-сессиями.
- Термины: **дерево** — корневая сессия и все её потомки (связь `sessions.parent_session_id`). Не путать с batch root: `root_id` в `batch_nodes` — корневой узел batch внутри дерева.

## 1. Факты о текущем хранилище

- Один файл на проект: `<data>/rush_store_v1.db`. WAL, `busy_timeout` 30 с (`internal/db/connect.go: BusyTimeout`), писатель — одно соединение на файл (`SetMaxOpenConns(1)`), читатели — отдельный пул. SQLite допускает одного писателя на файл, поэтому ВСЕ процессы проекта (web-сервер, каждый `rush run`, каждый агент) стоят в одной очереди на запись; ожидание дольше 30 с даёт `commit failed: timeout`, а чем больше файл и транзакции, тем дольше каждая фиксация.
- 26 таблиц, 22 SQL-файла, ~140 запросов. Почти все таблицы ссылаются на `sessions(id)` с `ON DELETE CASCADE` (внешние ключи включены): `files`, `messages`, `read_files`, `pending_injects`, `session_run_queue`, `orphan_call_outbox`, `session_drivers`, `session_notices`, `wake_schedules`, `batch_nodes`, `batch_control_requests`, `batch_timeout_checkins`, `session_agent_*`, `session_role_contracts`, `session_root_role_contracts`, `mcp_outputs`. Следствие: все они должны жить в одном файле с `sessions` своего дерева. Без внешнего ключа на сессию: `queue_tasks`, `async_hosts`, `session_permissions`, `batch_runner_checkpoints`.
- Размер на живом хранилище этого проекта (240 МБ, 141 сессия, 41 дерево, в среднем 3,4 сессии в дереве): `batch_nodes` 114 МБ (из них `response_envelope` 83 МБ), `messages` 79 МБ (`parts` 78 МБ), `files` 21 МБ (`content`), остальное мелочь. Объём — это содержимое сессий; координационные таблицы малы. Замер по shamir-db не делался (другой каталог, вне рабочей директории).
- Идентификаторы сессий — непрозрачные UUID; по id корень не определить.
- Девять мест открывают хранилище: `internal/app/app.go`, `internal/cmd/{batch_cli,root,sessions_batch_act,stats}.go`, `internal/server/r15bfixture/main.go`, `sdk/{library_mode,sdk}.go`.

## 2. Решение

1. **Папка дерева** `<data>/trees/<tree_id>/` (`tree_id` = id корневой сессии) с файлом `tree.db` (и его `-wal`/`-shm`); папка, а не одиночный файл, потому что в ней можно хранить и другие данные дерева (большие вложения, вывод MCP файлами) и удалять всё одним действием. В `tree.db` лежат: `sessions` дерева и все таблицы с внешним ключом на них, включая всё содержимое и всю batch-координацию дерева. Транзакции дерева (batch, финализация, долги реакций, уведомления, очередь запусков) остаются атомарными, как сегодня, потому что не выходят за дерево.
2. **Общая БД проекта** `<data>/rush_store_v1.db` (малая; имя сохраняется для совместимости): реестр деревьев, индекс «сессия → дерево», активность и общие очереди. Без внешних ключей на `sessions`; её таблицы — каталог ссылок, а не источник истины: пересобирается обходом файлов деревьев.
3. **Удаление дерева** — удаление папки целиком (без `VACUUM`, без построчных `DELETE` с каскадом): `purge` сводится к выбору деревьев по реестру, удалению их записей из реестра и индекса и удалению папки; `reap` и `gc` работают по реестру (§12).

## 3. Таблицы общей БД

| Таблица | Назначение | Кто пишет и как часто |
|---|---|---|

| `async_hosts`, `session_drivers` (вариант А) | живые процессы и драйверы; их читает финализация («чужие живые драйверы», блок против поспешного завершения) и восстановление | heartbeat процесса, редко |

Вариант Б для хостов и драйверов: хранить в файле дерева, а общая БД держит только «есть живая работа» в `trees.live_work`. Решение принимается в R0 после инвентаризации запросов (§4).

## 4. Межъядерные запросы: что нужно перенаправить

Запросы, которые сегодня видят все сессии сразу и после разделения идут через реестр: `ListSessions`/`ListAllSessions`/`ListSubSessions`, `ListLiveBatchRootsForHost`, `BatchRecoveryRoots`/`Elect`/`Interrupt` (восстановление после падения: обход деревьев с `live_work`), `ListAsyncHostRows`, `ListPendingRunQueueEntries`, `ListStaleLeasedRunQueueEntries`, `ListPendingOrphanOutboxEntries`, `ListCandidateInterruptedAssistantSessions`, `ListAllUserMessages`, `ListAllSessionPermissions`, запросы статистики и стоимости (`stats.sql`), `sessions grep/audit/cost/diff`, очереди пробуждений. Для каждого R0 фиксирует: остаётся в дереве (если принимает id сессии), идёт по реестру, или обходит файлы.
Единственная кодовая ссылка на «чужой корень» — `internal/agent/batch_install_adapters.go`.
Операции, пересекающие деревья (`sessions fork`, `inject` в чужое дерево): обычная запись в файл целевого дерева без общей транзакции; идемпотентность через идентификатор операции.

## 5. Поиск корня по под-сессии и инструменты управления

- Основной путь: `session_index` (одна строка на сессию, пишется при создании). Запасной: обход файлов деревьев (когда индекса нет или запись потеряна), результат кэшируется в индекс. Индекс — кэш: пересобирается командой `rush sessions reindex`.
- Необязательное дополнение: короткий префикс дерева в id новых сессий (`<tree8>-<uuid>`) — корень виден из id без запроса. Только для новых; старые id остаются непрозрачными. Решение в R0 (влияет на формат id во всех командах и web).
- Команда `rush sessions locate <id>`: дерево, файл, путь в дереве (цепочка родителей), статус.
- Команды управления поддеревом через корень: список детей, `show`/`kill`/`inject` по id под-сессии (поиск дерева автоматически), удаление дерева целиком. Часть уже есть (`sessions tree`, `kill`) — переводятся на поиск через индекс.

## 6. Маршрутизатор хранилища

Новый модуль `store/treestore` (после спринта 0 — в группе `store`): `Open(treeID)`, `Resolve(sessionID) → treeID`, `Create(rootSessionID)`, `Remove(treeID)`, пул открытых файлов с вытеснением (LRU, предел по числу файлов, по умолчанию 32; предел дескрипторов Windows), закрытие простаивающих, общий жизненный цикл с `db.Release`. Код дерева (`session`, `jobbatch`, `message`) получает соединение дерева, а не проектное; код проекта (список, восстановление, очереди) — реестр. Миграции схемы: при открытии файла дерева применяется цепочка миграций (версия в самом файле); файл дерева и общая БД имеют отдельные цепочки.

## 7. Миграция и совместимость

- Режим по флагу `options.store.layout`: `single` (как сегодня, по умолчанию до приёмки) и `per_tree`.
- Команда `rush sessions split-store`: офлайн, возобновляемая, разбивает единый файл по деревьям (каждая корневая сессия и все потомки в `trees/<id>.db`), строит реестр и индекс, сверяет число строк по каждой таблице до и после, оставляет прежний файл как `rush_store_v1.db.pre-split` до явного удаления. Откат: вернуть файл и выключить флаг.
- Старый `rush.db` (форк до v1) в разбиение не входит; для него остаётся существующий импортёр.

## 9. Риски

- Транзакции через деревья (fork/inject): нет общей атомарности; нужна идемпотентность и порядок записей «сначала цель, потом источник».
- Дескрипторы и блокировки Windows: много открытых файлов; удаление открытого файла невозможно — закрыть перед удалением; три файла WAL на дерево.
- Восстановление после падения: обход всех деревьев с `live_work`; флаг в реестре должен быть надёжным (иначе потерянная работа), поэтому реестр пересобирается по запросу и при старте проверяется выборочно.
- Миграции схемы по N файлам: ленивое применение при открытии и отдельная версия.
- Дублирование и рассинхронизация индекса: индекс — кэш, источник истины — файлы деревьев.
- Нагрузка записи большими значениями: `batch_nodes.response_envelope` (83 из 114 МБ таблицы на этом хранилище) делает каждую фиксацию дорогой; отдельное улучшение — вынести его в боковую таблицу; решается в R0 по замерам, не входит в разделение.
- Порядок относительно других работ: разделение трогает `internal/db`, `internal/session`, `internal/jobbatch` — не вести одновременно со спринтом 0 и с задачей #70 (пересборка финализации).

## 11. Освобождение места после purge (замечание оператора, 2026-11-15)

Симптом: «Purge завершён: удалена 1368 сессий старше 7 дней… Место на диске пока не вернулось: 928,4 МБ из 1,4 ГБ в хранилище — свободные страницы. Нужен `rush sessions compact` (VACUUM). Запускать его?» Оператор хочет, чтобы занятое место не оставалось без ручных шагов.

Причина (проверено по коду): прагма `auto_vacuum` не задана (`internal/db/connect.go`, список `pragmas`), поэтому SQLite возвращает освобождённые страницы только в свой список свободных (`freelist`), а файл не уменьшается; `internal/db/compact.go` честно описывает, что `purge`/`gc` лишь передают страницы в freelist, а вернуть место файловой системе может только `VACUUM`; `sessions purge` печатает подсказку (`compactHint`) и ничего не делает. `VACUUM` требует исключительной блокировки и временного места порядка размера живых данных, поэтому его нельзя делать молча при работающих агентах.

Решение (двухступенчатое):
1. **Новые хранилища и файлы деревьев**: `PRAGMA auto_vacuum=INCREMENTAL` при создании; свободные страницы возвращаются порциями командой `PRAGMA incremental_vacuum(N)`, это обычная короткая транзакция записи, исключительная блокировка не нужна, работающим агентам не мешает.
2. **`purge`/`gc` сами возвращают место:** после удаления, если свободные страницы выше порога (по умолчанию более 20% файла или более 256 МБ), выполняют `incremental_vacuum` порциями (между порциями отдают блокировку) и `wal_checkpoint(TRUNCATE)`; прогресс и итог печатаются; флаг `--no-reclaim` отключает. Для хранилищ, созданных до изменения (режим `auto_vacuum=NONE`), разовое преобразование выполняет `rush sessions compact` (он задаёт режим и делает `VACUUM`) — только при отсутствии живой работы и достаточном свободном месте на диске (предварительная проверка «нужно X, свободно Y»); `purge` в этом случае печатает точную команду и оценку выигрыша, а не просто подсказку.
3. **После перехода на деревья** (R2–R5) проблема исчезает по построению: удаление дерева — удаление файла; в общей БД остаются малые таблицы, для неё действует п. 1–2.

Проверки: тест на хранилище с `auto_vacuum=NONE` (подсказка, без изменений), на хранилище с `INCREMENTAL` (файл уменьшается после `purge`), порционность (блокировка отдаётся между порциями, параллельный писатель не получает таймаут), WAL усечён, отказ при нехватке места, `sessions audit` показывает режим и долю свободных страниц. Побочная польза: короче окна записи, меньше таймаутов фиксации.

## 12. purge и обслуживание после перехода (замечание оператора, 2026-11-15)

После перехода `purge` становится много быстрее: сегодня он построчно удаляет сессии каскадом по десяткам таблиц (на хранилище в гигабайты это минуты и блокировка писателя для всех), а затем оставляет свободные страницы. В новой архитектуре:
1. выбрать деревья по реестру (возраст последней активности дерева, статус, `live_work=0`, нет живых блокировок);
2. в одной короткой транзакции общей БД удалить записи дерева из `trees` и `session_index` (и из `wake_due`, при варианте А — из хостов и драйверов);
3. удалить папку `trees/<id>/` с диска (закрыв файл, если он открыт в пуле; на Windows удаление открытого файла невозможно).
Порядок «сначала реестр, потом папка»: если процесс упал между шагами, остаётся папка-сирота без записи в реестре; `rush sessions reap`/`reindex` находят такие папки сверкой каталога с реестром и удаляют или регистрируют заново (по флагу). Обратный порядок оставил бы запись реестра без файла — это хуже (ложная сессия в списках). Место возвращается мгновенно и полностью; для общей БД остаются малые таблицы и п. 1–2 раздела 11.

## 13. Все инструменты переделываются под новую архитектуру

Затронутый код (пока без правок, по замеру 2026-11-15): `rush sessions` — 33 семейства подкоманд (activity, audit, batch, budget, cache, cancel, compact, cost, delete, diff, fork, gc, grep, inject, jobs, kill, last, list, live, locks, pick, print, purge, reap, render, reset, show, stall, status, stop, subagents, tail, tree, watch, why), плюс `rush batch`, `rush queue`, `rush stats`, `rush result`, `rush ps`, `rush logs`, `rush migrate`; в коде — около 33 производственных файлов `internal/cmd`, 18 файлов `internal/server` (REST, WebSocket, SSE), 13 файлов `internal/app`, 4 файла `internal/agent`, 2 файла `sdk`. Каждое семейство относится к одному из классов:
- **по одному дереву** (`show`, `tail`, `watch`, `last`, `print`, `render`, `tree`, `jobs`, `why`, `status`, `live`, `activity`, `batch`, `subagents`, `stall`, `inject`, `cancel`, `stop`, `kill`, `budget`, `cache`, `diff`, `fork` внутри дерева): принимают id сессии, находят дерево через индекс (`Resolve`), работают с его `tree.db`;
- **по всем деревьям** (`list`, `pick`, `grep`, `audit`, `cost`, `locks`, `stats`, `ps`, `queue`): идут по реестру и индексу, а там, где нужны подробности, открывают деревья по очереди или параллельно с пределом;
- **обслуживание** (`purge`, `reap`, `gc`, `delete`, `compact`, `reset`): по папкам деревьев (§12, §11);
- **новые**: `locate`, `reindex`, `split-store`.
Задачи раскладываются по этим классам (R4a–R4d ниже в списке задач). Единообразие обеспечивает общий слой маршрутизатора (R2): команды не открывают файлы сами, а просят у него дерево или реестр; это же даёт одну точку для режима `single` во время перехода.

## 14. Привязка корневой сессии к рабочему дереву (замечание оператора, 2026-11-15)

Что есть сегодня: каждая сессия хранит `sessions.workspace_root` (корень checkout, где она создана; есть индекс `idx_sessions_workspace_updated`; то же поле у `queue_tasks`). Запрет «сессия принадлежит создавшему checkout» (`belongs to <root>`) и подсказка `sessions fork --cwd` опираются на него; запуск `rush run --worktree <slug>` создаёт worktree в `<main>/worktrees/<slug>` и связывает с ним сессию неявно.

Что меняется: привязка становится явным атрибутом дерева в реестре (`trees`): `workspace_root` (checkout или worktree, в котором работает дерево), `main_root` (основной каталог репозитория, чей `.rush` держит реестр и папки деревьев), `worktree_slug`, `branch`, `base_ref` (если дерево создано через `--worktree`). Правила:
- Привязка задаётся корневой сессией при создании и наследуется всем деревом (под-сессии работают в том же рабочем каталоге); у дерева ровно одно рабочее дерево.
- `rush run --session <id>` из другого checkout отказывает, как сейчас; `sessions fork --cwd <path>` создаёт НОВОЕ дерево, привязанное к другому worktree, с копией истории (раньше это был обходной путь, теперь — основной способ перенести работу).
- `sessions list` по умолчанию показывает деревья текущего рабочего дерева (быстро, по индексу реестра), `--worktree <slug>` и `--all` меняют фильтр; `sessions locate` и web показывают worktree и ветку.
- Жизненный цикл: `rush worktree remove <slug>` помечает дерево статусом `orphan` (рабочее дерево исчезло) и, по флагу или политике, ставит его на очистку; `purge` и `reap` находят деревья с исчезнувшим рабочим каталогом сверкой `workspace_root` с диском; результат работы дерева (отчёт, итоговый текст) остаётся доступным до очистки.
- Режим dev-сборки (`<wt>/.rush/dev`): отдельное хранилище на worktree остаётся как есть; привязка в этом режиме тривиальна.
- Миграция (R5): `workspace_root` корня берётся из существующей колонки; пустое значение (старые сессии) — «непривязанное дерево», видно только по `--all`.
Затронутые задачи: R2 (колонки реестра), R4a (фильтры `list`, `locate`, `fork --cwd`), R4c (`orphan`, очистка, интеграция с `rush worktree remove`), R4d (список web с worktree/веткой), R5 (перенос `workspace_root`).

## 15. Данные сессий в папке пользователя, по проектам (предложение оператора, 2026-11-15)

Идея: хранить хранилище не в `<repo>/.rush`, а в пользовательской папке, как это делает Claude Code (`~/.claude/projects/<проект>/…`): `<user-data>/rush/projects/<ключ-проекта>/`.

Что есть сегодня: каталог данных выбирается по приоритетам (`internal/config/datadir.go`): `--data-dir`, `options.data_directory`, найденный `.rush` с `rush.db`, для связанного worktree `<main>/.rush` (общий) или `<wt>/.rush/dev` (dev-сборка), иначе `<cwd>/.rush`. Реестр проектов `projects.json` в глобальной папке данных уже существует (`internal/projects`). Поэтому перенос — это смена умолчания в одной функции (`defaultDataDirForWorkspace`) плюс ключ проекта и миграция; явные флаг и опция остаются сильнее.

**Рекомендация: да, принять, вместе с переходом на деревья (одна миграция, а не две).** Зачем:
- один каталог на все проекты: анализ и очистка в одном месте (`rush projects ls/du/purge`, размер по проектам, «что занимает диск»), без обхода репозиториев (сегодня: shamir-db 7,3 ГБ + старый 5,5 ГБ внутри репозитория, у этого проекта `.rush` ~2,8 ГБ мусора, у соседних проектов то же);
- репозиторий не раздувается: ни индексатору IDE, ни антивирусу, ни резервному копированию не нужно ходить по гигабайтам; `git clean -xfd` и удаление worktree не могут стереть сессии (у игнорируемого `.rush` такой риск есть);
- удаление проекта из реестра — удаление одной папки; приватность: права на папку пользователя вместо каталога репозитория;
- естественное место для папок деревьев (§2): `<проект>/trees/<id>/` и общей БД проекта.

Что остаётся в репозитории `.rush`: проектные файлы, которые читаются из репозитория или нужны оркестратору рядом с кодом (`system-prompts/default.md`, `stdin/` вывод запусков, `tmp/`); решение по каждому подкаталогу — в R0. Переезжают: хранилище, `locks/`, `hosts/` (heartbeat), `logs/`, маркеры `workspaces/`.

**Ключ проекта:** нормализованный абсолютный путь основного checkout (регистр на Windows свёрнут) → `<имя>-<хеш8>`; внутри `project.json` (`main_root`, адрес `origin`, отпечаток репозитория, время создания и последнего использования). Все worktree основного checkout (по `git common dir`) попадают в один ключ, как сегодня в общий режим. Перемещён или переименован репозиторий: `rush projects relink <старый> <новый>` и автоопределение по отпечатку (первый коммит и `origin`); два клона одного репозитория — два проекта; другой репозиторий по тому же пути — коллизия ловится отпечатком.

**Риски и ограничения:**
- диск: домашняя папка пользователя часто на системном диске (на этой машине место берегут, для артефактов используют `D:`), поэтому расположение настраивается (`RUSH_GLOBAL_DATA`, `options.data_directory`) и показывается в `rush projects ls`; умолчание — существующая глобальная папка данных (локальная, не синхронизируемая);
- окружения без записи в домашнюю папку (CI, контейнеры, песочницы): откат на `<cwd>/.rush` по флагу, переменной окружения или автоматически при отказе в записи с предупреждением;
- dev-сборки (`<wt>/.rush/dev`) и `go test`: изоляция `testguard` уже направляет глобальное состояние во временный каталог, поведение сохраняется;
- многопользовательские машины: папка на пользователя, блокировки ключа проекта между процессами одного пользователя как сегодня;
- документы, скиллы и подсказки с путями `.rush/rush_store_v1.db` нужно обновить; сообщения об ошибках показывают фактический каталог данных;
- миграция гигабайтов между дисками: копирование с проверкой и возобновлением, исходный каталог остаётся до явного подтверждения (как `.pre-split`), на старом месте остаётся файл-указатель с новым путём.

**Связь с задачами:** R0 решает состав переезжающего и умолчание; R2b — ключ проекта, разрешение каталога данных, `projects relink`, файл-указатель; R5 — единая миграция «репозиторный единый файл → папка проекта с деревьями»; R4e — межпроектные инструменты (`rush projects ls/du/purge`, `sessions list --all-projects`).
