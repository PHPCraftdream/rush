# План: общий источник скилла и варианты для CLI

Статус: план, без реализации. Связан с [планом уведомлений Codex](2026-09-24-codex-run-completion-notification.md).

## Цель и текущее состояние

Один исходный текст должен собираться в команду Claude и скилл Codex: общие блоки попадают в оба файла, а блоки `claude` и `codex` — только в соответствующий. Для каждого скилла должны поддерживаться два формата источника: прежний обычный `.md` и новый упорядоченный список объектов.

Сейчас `internal/cmd/claude_slash_command.md` встраивается в бинарник из `internal/cmd/claude_init.go`; `codex-init`, `gemini-init`, `grok-init` и `qwen-init` читают тот же текст через `parseSlashCommandSource` в `internal/cmd/multi_cli_convert.go`. `codex-init` добавляет frontmatter и sentinel, но не меняет инструкции Claude внутри тела. Установленный пользователем Codex скилл уже содержит вручную добавленный callback, которого нет в исходнике: повторная установка затрёт его. Исходник также перешёл на `--idle-timeout`, тогда как установленные копии ещё говорят о `--timeout 60m`.

Формат результата Codex остаётся обычным `SKILL.md` с frontmatter `name`/`description`; это соответствует [документации OpenAI о скиллах](https://developers.openai.com/plugins/build/skills). Новый формат нужен только для **исходника генератора**, а не для установленного файла.

## Контракт двух форматов

1. Старый файл `<skill>.md` остаётся допустимым. Его существующие frontmatter и Markdown проходят прежний путь без изменения смысла. Не требовать миграции `rush-fallback`, `wrush` и `wcrush` ради внедрения движка.
2. Новый файл `<skill>.yaml` содержит общий `description` и `blocks`: упорядоченный массив объектов с необязательными полями `common`, `claude`, `codex`. Многострочные значения — Markdown. Пример:

   ```yaml
   description: Delegate this task to a rush sub-agent instead of doing it yourself
   blocks:
     - common: |-
         This skill is opt-in only.
     - claude: |-
         Launch with Bash run_in_background and wait for its completion event.
       codex: |-
         Pass --codex-thread-id and handle the queued completion message.
     - common: |-
         Verify the diff and tests after completion.
   ```

3. Для каждого объекта сборщик добавляет `common`, затем поле выбранной платформы; пустые поля пропускает. Блоки соединяются ровно одним пустым Markdown абзацем. Вариантные поля должны содержать целые абзацы или пункты, а не половины предложений. Порядок массива определяет порядок результата.
4. Формат выбирается по расширению, без угадывания содержимого. Если для одного скилла одновременно есть `.md` и `.yaml`, установка завершается диагностикой о двух источниках. Неведомые поля, пустые объекты, пустой итоговый текст и незаполненные маркеры сборки — ошибки до записи на диск. Использовать уже имеющийся `gopkg.in/yaml.v3` со строгой проверкой полей.
5. Для существующих Gemini/Grok/Qwen предусмотреть явные необязательные поля платформы либо общий, не привязанный к Claude текст. Не подставлять `claude` в эти цели молча. Их текущие `.md` источники продолжают работать, пока соответствующий скилл не мигрирован.

## Встраивание и установка

1. Вынести чтение обоих форматов и сборку в одну функцию уровня `internal/cmd`: вход — имя скилла, форматированный источник и целевая CLI; выход — `description` и готовое Markdown тело. Использовать `embed.FS` для файлов источника, чтобы `rush ...-init` не зависел от текущего каталога.
2. Подключить сборщик к `claude-init`, `codex-init` и другим потребителям того же источника. Оставить целевые оболочки отдельно: Claude frontmatter/`$ARGUMENTS`, Codex `SKILL.md`/sentinel, Gemini TOML, Qwen и Grok по их прежним правилам.
3. Первым перенести `/rush` в структурированный источник. Общие правила делегирования, разрешений и проверки результата оставить один раз; запуск, ожидание, мониторинг и примеры команд сделать вариантами. Кодексный текст после внедрения второго плана использует `--codex-thread-id` при наличии `CODEX_THREAD_ID` и `codex queue`, а иначе удерживает штатное событийное ожидание процесса. Временный `--on-finish` из ручной правки больше не нужен.
4. Проверить ссылки наследующих скиллов: `wrush`/`wcrush` должны указывать на правильный установленный файл, а `rush-fallback` не должен ссылаться на watchdog, отсутствующий в варианте Codex. Не менять sentinel и правило «не перезаписывать чужой файл».
5. Обновить инструкции `*-init` так, чтобы было ясно: установленный скилл всегда Markdown, исходник может быть Markdown или YAML. Обновление глобальных установок выполнять только после готовности CLI флага из второго плана.

## Тесты и критерии готовности

- Тест сборки фиксирует порядок `common → платформа` для нескольких объектов, пропуск чужой платформы, пустые поля, Unicode, кавычки и fenced code blocks без искажения Markdown.
- Тест совместимости сравнивает результат чтения старого `.md` с нынешним генератором; ошибки двух источников, неизвестных ключей и пустого результата проверяются отдельно.
- Интеграционные тесты `claude-init`/`codex-init` устанавливают файлы во временные каталоги. Codex содержит `--codex-thread-id` и не содержит `Bash({`/`run_in_background`; Claude содержит инструкцию фонового `Bash` и не содержит `codex queue`. Общие разделы совпадают, обе версии используют актуальный `--idle-timeout` и не возвращают старый совет всегда ставить `--timeout 60m`. Проверить frontmatter, sentinel, повторную установку и отказ перезаписывать чужой файл.
- Прогнать существующие тесты установщиков Gemini/Grok/Qwen и проверить, что в их результатах нет незаменённых полей или случайных Codex-инструкций.
- Готово, когда повторный `rush codex-init` воспроизводит целевой Codex текст из исходника без ручной правки установленного `SKILL.md`.
