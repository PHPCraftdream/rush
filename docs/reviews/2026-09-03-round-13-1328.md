## SDK Review Round 6

### R6-1 — P0: ephemeral ModeLibrary leaked real-disk/command tools

**Коммиты:** `2eff9f74` + `87e9c72c` (R6-2, но тот же дифф в
fs_scope.go) + `8d4fd702` (R6-4)

**Проблема (раунд 5):** `LibraryVirtualRoot = "/rush-library-mode-root"`
— строка, которую OS интерпретирует как реальный путь (на Windows
это drive-rooted путь, на Unix — обычный absolute). Эфемеральная
сессия (пустой WorkingDir, in-memory БД) получала все legacy
host-disk инструменты (bash, run_command, download, edit, multiedit,
glob, grep, ls, view, write) и fs_* семью на реальном диске.

**Исправление (три слоя):**

1. **Default-deny toolset:** `buildLibraryConfig` теперь передаёт
   `ephemeral=true`, что устанавливает `Options.DisabledTools =
   libraryEphemeralDisabledTools` — полный список host-disk/command
   инструментов плюс вся fs_* семья. Важно: `download` был пропущен
   в первом драфте (пишет прямо в реальный OS filesystem без
   DiskProvider seam) — найден и закрыт на месте.

2. **Per-OS LibraryVirtualRoot:** `internal/agent/tools/
   fs_library_virtual_root.go` — новвый файл, вычисляет
   `LibraryVirtualRoot` per-OS: `K:\rush-library-mode-root` на
   Windows (удовлетворяет реальному `filepath.IsAbs`), `/rush-...`
   на Unix. Это закрывает contract violation: DiskProvider's
   documented contract требует что "every method receives an absolute
   path" — prior literal не удовлетворял `filepath.IsAbs` на Windows.

3. **Backstop в resolveScopedPath:** `rejectRealDiskUnderLibraryVirtualRoot`
   вызывается после join+clean, ПЕРЕД первым `disk.Stat` — если
   resolved путь попадает под sentinel И disk это реальный OSDisk —
   fail closed с явной ошибкой. Защита на случай:
   - caller Supply FolderScopes без DiskProvider
   - caller прямой misuse

**Важный нюанс:** `applyCallFolderScope` (в `coordinator_tools.go`)
re-adds fs_* инструменты НЕЗАВИСИМО от `DisabledTools` когда
`FolderScopes` grants соответствующую операцию. Это documented
в `libraryEphemeralDisabledTools` doc-комментарии: per-call
FolderScopes opt-in работает, но без DiskProvider
`rejectRealDiskUnderLibraryVirtualRoot` fail-closed на реальном диске.

`bash`/`run_command`/`download` — hard-denied всегда, нет opt-in:
shell execution не может быть виртуализирован DiskProvider'ом.

**Доказательство:** 5 регрессионных тестов в `sdk/r6_1_library_mode_diskless_test.go`:
- default toolset excludes real-disk/command tools
- write/bash attempts never touch real disk
- download attempt never touches real disk (R6-1 gap в первом драфте)
- FolderScope без DiskProvider → fail closed before provider traffic
- custom DiskProvider paths are always absolute (filepath.IsAbs contract)

**Статус:** ✅ Закрыто.

### R6-2 — P1: fs_list/fs_find checked alias-spelled result paths against canonicalized scope

**Коммит:** `87e9c72c`

**Проблема:** R5-2 каноникализировал корни scope'ов и напрямую
запрошенные item paths через `resolveScopedPath`, но НЕ трогал пути,
приходящие ОБРАТНО от traversal provider'а. `fsListOne`/`fsFindOne`
проверяли `disk.List`/`disk.Find` результат лексически, без
ре-резолва. OSDisk's fastwalk (`Follow: true`) crossing directory
symlinks сохраняет alias spelling — deny carve-out, скомпилированный
против canonical target'а, обходился через alias.

**Исправление:** Оба `fsListOne` и `fsFindOne` теперь ре-резолвят
каждый provider-returned путь через `resolveScopedPath` (мигрируя
`fs_grep`'s existing pattern) перед `scope.Check`. Не-resolvable
результат → dropped, never rendered. Rendered output сохраняет
оригинальный provider-returned spelling.

**Доказательство:** 3 регрессии:
- `TestFSListOSDiskSymlinkNeverLeaksDenyCarvedSubtreeThroughListing` —
  real-OSDisk + real `os.Symlink`, end-to-end
- `TestFSListFakeProviderAliasResultRespectsCanonicalDenyCarveOut` —
  fake provider с injected alias result
- `TestFSFindFakeProviderAliasResultRespectsCanonicalDenyCarveOut` —
  то же для fs_find

**Статус:** ✅ Закрыто.

### R6-3 — P1: pinCallTools fail-closed guard missed DisableSubAgents/ModelRole

**Коммит:** `3e84a240`

**Проблема:** R5-1 refactor pushed fail-closed decision onto every
caller individually (`scopedCallToolsRequired(ctx)` check after
`pinCallTools`). R6-3 нашёл что `RunSessionAgentCall`'s
durable-replay call site НЕ был widened для DisableSubAgents/ModelRole:
вызов `--agents single` (DisableSubAgents=true) после durable-рестарта
молча восстанавливал delegation tools (agent/agentic_fetch).

**Исправление:**
1. `pinCallTools` теперь возвращает `([]fantasy.AgentTool, error)`.
   Fail-closed decision двинута ВНУТРЬ функции — каждый caller
   получает один unambiguous answer.
2. `scopedCallOptionsRequireDistinctTools` — новая predicate,
   widening от FolderScope/DiskProvider до DisableSubAgents и
   non-empty ModelRole. Используется и в `scopedCallToolsRequired`
   (ctx-based), и напрямую в `RunSessionAgentCall` (struct-based).
3. Все 4 call site'а обновлены: `resolveSessionModelsInternal`,
   `applyModelOverrides`, `resolveCredentialsModels`,
   `RunSessionAgentCall`.

**Важный нюанс:** Для genuinely legacy call'ов (no CallOptions, или
none of these fields set) build/ready-gate failures всё ещё возвращают
`(nil, nil)` — log-only, preserving pre-R6-3 "fall back to shared
toolset" behavior.

**Доказательство:** 8 регрессий: 3 для durable replay path, 4 для
ordinary call sites, 1 negative control (unscoped still falls back).

**Статус:** ✅ Закрыто.

### R6-4 — P2: CallOptionsSpec.Version was write-only metadata

**Коммит:** `8d4fd702`

**Проблема:** `toSessionCallOptionsSpec` всегда стампил `Version`,
но `fromSessionCallOptionsSpec` никогда не проверял его — реконструировал
CallOptions из любых полей, которые удалось декодировать. mixed-version
deployment: older binary → newer durable row → silent weaker semantics.

**Исправление:**
1. `fromSessionCallOptionsSpec` теперь возвращает `(*CallOptions, error)`
   и refused non-nil spec с mismatched Version.
2. `ErrCallOptionsSpecVersionUnsupported` sentinel error.
3. `RebuildSessionAgentCall` propagates error → refuses row.
4. `FromSessionAgentCallData` (тест-only) → `callOptionsFromCallData`
   helper, который discard'ает error (сохраняя существующий
   no-error-channel contract для тестов).

**Доказательство:** 5 регрессий: nil spec, accepted v1, zero version,
future version, end-to-end RebuildSessionAgentCall с tampered version.

**Статус:** ✅ Закрыто.

## Memory-leak / Hang fixes (cec10b5d, 53aa30d9)

### M1 — slog.SetDefault(prev) не восстанавливает log.Writer/log.Flags

**Коммит:** `53aa30d9` (первичный) + `cec10b5d` (follow-up)

**Механизм:** `slog.SetDefault(prev)` только вызывает `log.SetOutput`
когда новый handler не `*defaultHandler` (log/slog/logger.go).
Восстановление на defaultHandler-backed logger → log's writer stays
pointed at dead local test buffer → unbounded process-lifetime
retention sink. 5+4 тестов затронуто.

**Исправление:** В каждом затронутом тесте capture/restore
`log.Writer()` и `log.Flags()` в defer.

**Подтверждение:** Live incident — combined `go test ./internal/session/...
./internal/agent/... ./internal/app/...` → ~64 GB committed memory →
system-wide memory eviction.

**Статус:** ✅ Закрыто.

### M2 — fireCacheKeepAlive unbounded fantasy step loop

**Коммит:** `cec10b5d`

**Механизм:** `fireCacheKeepAlive` (agent_cache_keepalive.go) строила
replay agent без `fantasy.WithStopConditions`. Fantasy step loop
имеет内置 step cap — `noExecuteTool`'s refusal — NORMAL tool response
(не Go error) → provider, который keep возвращает tool calls → unbounded
model<->tool ping-pong. Подтверждено через hard 4GB job-object cap →
crash с loop's own goroutine в stack.

**Исправление:** `fantasy.WithStopConditions(fantasy.StepCountIs(2))`
— single background ping, never legitimately needs more than one
tool-calling round.

**Статус:** ✅ Закрыто.

### M3 — Unpaced busy-spin toggle goroutines

**Коммит:** `cec10b5d`

**Механизм:** Два тестовых goroutine (`p436_config_snapshot_threading_test.go`,
`p577_rebuild_provider_options_test.go`) — tight loop без Sleep/
Gosched, 100% OS thread busy → amplifying GC/scheduler pressure →
test hang under concurrent load.

**Исправление:** `time.Sleep(10 * time.Microsecond)` per iteration —
still far more toggles than main loop's iterations need.

**Статус:** ✅ Закрыто.

### M4 — db.Release before pump.Stop() race

**Коммит:** `cec10b5d`

**Механизм:** `TestP0_338_FinalizerReachableDespiteHungCleanup`:
`db.Release` ran before `pump.Stop()` → pump worker mid-flight на
single writer connection → Windows `TempDir.RemoveAll` failure
("process cannot access the file").

**Исправление:** `pump.Stop()` (idempotent, 5s bounded) before
`db.Release`. Дополнительно: atomic `testDone` guard для
`t.Logf` в hung-cleanup callback (callback fires >1 once per
`Release()` call; double channel close → panic).

**Статус:** ✅ Закрыто.

## Положительные наблюдения

- `pinCallTools` return contract документация (R6-3) — одна из лучших
  doc-комментарий в кодовой базе: явно перечисляет все 4 failure
  mode'а, возвращаемые значения для legacy vs. scoped call'ов,
  и почему decision двинута внутрь функции.
- `rejectRealDiskUnderLibraryVirtualRoot` — точечная defense-in-depth:
  fail closed BEFORE первый `disk.Stat`, не после.
- `LibraryVirtualRoot` per-OS computation + `K:\` на Windows —
  практичный компромисс: avoids UNC name-resolution timeout risk,
  satisfies `filepath.IsAbs`, collision-safe через unconditional
  denial.
- Memory-leak fixes instrumentation-first: capm/win-nice job-object
  caps → confirmed root cause → targeted fix → verified via same
  harness.
- `callOptionsFromCallData` — сознательный trade-off: тест-only
  конвертер сохраняет no-error-channel contract, production path
  (`RebuildSessionAgentCall`) получает strict version validation.

assert что `FromSessionAgentCallData` не вызывается из production
кода, либо мигрировать на error-returning версию.
