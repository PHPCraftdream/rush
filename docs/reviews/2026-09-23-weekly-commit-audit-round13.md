## Подтверждённые findings на HEAD

### R13-1 — P2: release живого владельца не завершает предварительный durable drain

**HEAD места:** `internal/app/app_run.go:90-98`; `internal/app/app_run_drain_pending.go:19-35,42-55`; `internal/session/run_queue_drain_session.go:437-466`; `internal/session/run_queue_entry_exec.go:691-700`; `internal/agent/mailbox_ownership.go:69-75`; `internal/app/app.go:69-79`.

**Допустимый execution order:**

1. Обычный локальный turn O владеет session mailbox; ранее принятая durable row Q для той же сессии pending. Новый не-fail-fast `ExecuteRun` R видит Q в `HasOutstandingRunQueueEntriesForSession` и вызывает `DrainSessionNow`.
2. Drain lease-ит Q, но `Coordinator.Run` встречает O. `mailbox.submit` для `FromDurableQueue` не добавляет вторую копию в mailbox; адаптер переводит `(nil,nil)` в `ErrCallQueuedNotExecuted`. `executeEntrySync` Nack-ает Q обратно в pending без attempt penalty и ставит локальный `busyBackoffUntil` на lease TTL. `DrainSessionNow` сообщает `DrainNoWork`/busy: до освобождения O никакого Q не исполнилось.
3. `drainPendingBeforeRun` только логирует ошибку и deferred `waitLocalOwnerReleased` ждёт завершения O. Как только O отпустил mailbox, helper возвращает управление `ExecuteRun`; повторного `DrainSessionNow` и проверки Q уже нет. Из-за busy backoff фоновый pump не заберёт Q немедленно. R выигрывает свободный mailbox и выполняет свой prompt **до** Q. Если R — короткий `rush run`, процесс может закончиться, оставив Q для будущего процесса/запуска.

Второй вход в тот же дефект: однократная ошибка `HasOutstandingRunQueueEntriesForSession` на строке 19 сразу пропускает и drain, и `waitLocalOwnerReleased`; если собственный pump в это время исполняет Q, R вновь может queued-exit за ним. Это не утверждение о частоте SQLite-ошибок; достаточно поддерживаемого error outcome, после которого последующие DB операции успешны.

**Impact:** обещанный порядок «accepted durable work first» нарушен; новый prompt видит сессию до ранее принятой работы. Оставшаяся row не исчезает из БД, но её выполнение переносится на следующий pump/процесс, а результат нового `rush run` может выглядеть успешным при незавершённом backlog. При preflight error возвращается и первоначальная траектория queued-behind-local-pump. Межпользовательская утечка и обязательная повторная запись side effects здесь не утверждаются.

**Минимальный fix:** после освобождения локального владельца снова drain-ить эту сессию и начинать новый turn только после подтверждённой пустой очереди (`DrainComplete` либо проверенный `DrainNoWork` без outstanding); ошибки preflight/drain не превращать молча в разрешение на запуск. Сохранить ctx-aware прекращение ожидания и ограничить retry, чтобы не создавать busy loop при внешнем владельце.

**Детерминированный oracle:** test double/barriers: держать O в provider, поставить Q pending, заставить первый drain получить busy/Nack и зафиксировать backoff, затем отпустить O; R не должен вызвать provider до Q, после R не должно остаться Q. Отдельно один раз инъецировать ошибку `HasOutstanding...` при работающем pump и затем вернуть БД к успеху; R должен либо дождаться/обработать Q, либо вернуть явную incomplete error, но не queued-exit за ним. Без `Sleep` и нагрузки. Нынешний `TestExecuteRun_WaitsForLocalOwnerAfterDrainReturns` (`internal/app/app_run_drain_pending_test.go:70-123`) проверяет O и R, но не проверяет выполнение либо остаток Q.

### R13-2 — P2: cancellation сохраняет provisional успешный JSON outcome другого execution

**HEAD места:** `internal/app/app_run_reviewer.go:217-250,282-289,351-380,515-580,693-724`; `internal/app/app_run_result.go:195-208,268-305`; `internal/app/app_run.go:542-564`.

**Допустимый execution order:** A/canceled завершает исходную generation; loop запускает durable drain и переводит `eventOwner` на B-recorder, оставляя `callResultRec=A`. B создаёт и публикует `end_turn`, и live `handleMessageEvent` устанавливает `finalReason="end_turn"`, `finalText=B`. Ack B ещё не подтверждён (barrier на `AckRunQueueEntry`). Parent ctx отменяется, select выбирает `ctx.Done()` раньше `drainDone`. Probe находит committed A row; `finish(context.Canceled)` отвергает её в `handleMessageEvent`, а исправленная строка 580 оставляет `authoritativeTerminal=false`, так что **nil-success round 12 действительно закрыт**. Но `finalReason` и `finalText` от B не очищаются. `buildRunResult` берёт непустой `finalReason` раньше `canceled` и из-за `canceled=true` не заполняет `Error`. JSON получает `exit_reason="end_turn"`, `final_text=B`, `error` отсутствует, а `hookExitReason` становится `end_turn`; только отдельное возвращаемое Go error содержит cancellation. `RunNonInteractive` кодирует этот JSON до возврата error. Ack B затем вправе ошибиться; envelope уже выдан.

**Impact:** JSON/SDK consumer и on-finish hook могут принять неподтверждённое B за успешный завершённый ответ, несмотря на ненулевой process/Go error. Это менее тяжёлый остаток исправленного P1: возврат nil больше не происходит, но machine-readable результат противоречит ошибке. Не требуется reviewer, повторный исполнитель или data race.

**Минимальный fix:** при отмене до `DrainComplete` не оставлять provisional terminal metadata в финальном результате. Либо явно помечать его incomplete/canceled и сохранять B text только как partial с соответствующим статусом; не запускать JSON strip по нему как по успешному `end_turn`. Status, Error и hook reason должны описывать один и тот же execution outcome.

**Детерминированный oracle:** продолжить fixture `TestFinishRejectsSupersededRecorderRowAsAuthoritative_R12_1` (`internal/app/r12_1_drain_cancel_authoritative_test.go:44-108`): с A-recorder, B-owner и B live `end_turn` вызвать `finish(context.Canceled)`, затем проверить не только `ErrorIs`, но и `result.ExitReason=="canceled"` (либо явный `incomplete`), непустую failure diagnostic и `hookExitReason`. Интеграционный контроль: барьер между B message commit и Ack, parent cancel, затем injected Ack error; JSON не должен объявлять `end_turn`/подтверждённый B. Существующий тест намеренно считает текущий `ExitReason="end_turn"` «cosmetic» и проверяет только Go error; поэтому он не закрывает wire contract.

### R13-3 — P2: удалённый provider сохраняется для OAuth refresh с сетью нового snapshot

**HEAD места:** `internal/agent/coordinator_providers_auth.go:140-177`; `internal/agent/coordinator_providers_network.go:21-30`; `internal/nettransport/config.go:32-53`; `internal/config/store_oauth.go:248-275,431-460`.

**Допустимый execution order:** 401 либо proactive refresh начинается с provider P из поколения A: OAuth refresh token TA и global proxy PA. Reload публикует B, где P удалён, а global proxy изменён на PB. Это достижимо при `disable_default_providers` и удалении P из конфигурации; `RemoveProviderAPIKey` (`store_oauth.go:517-543`) также публикует snapshot без P. `refreshOAuth2Token` читает B (`:163`), но `cfg.Providers.Get(P)` не находит entry и оставляет переданный `providerCfg` из A (`:164-168`). Затем `resolveProviderHTTPClient(cfgB, providerA)` наследует PB из B (`nettransport/config.go:37-53`) и создаёт CB. `RefreshOAuthTokenWithClient` получает старый TA; disk preflight для удалённого P возвращает nil, после чего `hyperExchangeTokenFn`/Copilot отправляет TA через CB. CAS позже откажет публикации, потому что P исчез, но outbound request уже выполнен. Пара PB/TA не принадлежала ни A, ни B. Это другая граница, чем закрытая round-12 CA/TB при существующем provider.

**Impact:** при поддерживаемом hot reload auth-трафик для уже удалённого provider уходит по новому global маршруту, который оператор не задавал для этого credential; возможен ошибочный exchange либо обход намерения отключить P. Ни TLS verification bypass, ни отправка на произвольный endpoint не утверждаются. Без удаления P прежняя same-snapshot защита работает.

**Минимальный fix:** если P отсутствует в свежем snapshot, завершать refresh до client build и сетевого вызова; если бизнес-контракт разрешает завершить начатый запрос, передавать **весь** pinned snapshot A, включая global network, а не только provider A. Дисковый CAS остаётся обязательным.

**Детерминированный oracle:** дать `refreshOAuth2Token` stale provider A, затем через управляемый reload опубликовать B без P и с другим global proxy; перехватить OAuth exchange через существующий function double. Ожидать ноль exchange и явную ошибку (либо, если выбран pinned-A контракт, строго PA/TA), никогда PB/TA. Positive control: при P в B и изменённых token+network сохранить уже существующий same-generation тест; отдельно сохранить CAS тест при reload во время network call. `TestRefreshOAuth2Token_UsesFreshSameSnapshotProviderPair` (`coordinator_pinned_rebuild_snapshot_test.go:348-365`) покрывает provider **найденный** в B, а не этот fallback.

### R13-4 — P2: финальная проверка reload держит два mutex во время файлового I/O

**HEAD места:** `internal/config/store_reload.go:558-564,716-750,70-111,156-167`; `internal/config/store_write.go:227-236`; `internal/config/store_oauth.go:136-138,297-319,399-412`.

**Допустимый execution order:** `ReloadFromDisk` собирает candidate вне `publishMu`, затем берёт `publishMu` и `diskWriteMu`. Его финальный `candidateInputsChanged` проходит по всем config/MCP fingerprints и вызывает `readStableConfigFileOwned`, который открывает regular file, дважды выполняет `io.ReadAll` и повторяет проверки/чтения при изменениях; в эту функцию не передан reload `ctx`. Если разрешённый config-файл расположен на медленном или остановившемся filesystem, один `Read` остаётся внутри обеих critical sections. Одновременно OAuth refresh после успешного exchange пытается `setOAuthTokenIfCurrent` и ждёт `diskWriteMu`, а `SetProviderRuntimeConfig`/`applyOAuthToken` ждут `publishMu`. Отмена их contexts не прерывает `sync.Mutex.Lock`; ожидание продолжается до возврата файлового I/O. Это конкретная последовательность владения, не lock-order cycle и не утверждение, что каждый локальный файл медленный.

**Impact:** hot reload одного workspace/MCP config может удержать публикацию нового token и другие config writes, а следом user turn, на время файлового stall без соответствующего deadline. `Snapshot()` читает опубликованный pointer без этого mutex и потому не объявляется заблокированным. Код финальной проверки внесён до рассматриваемой недели (`git blame` указывает на 6 сентября); он включён как соседний lifecycle-механизм, достижимый из недельного OAuth refresh, а не приписан недельному commit.

**Минимальный fix:** вынести полный обход путей и чтение/хеширование bytes из-под `publishMu`; на коротком этапе публикации сверять version/generation и координировать внутренние disk writes без обратного lock order. Для внешних изменений сохранять существующий optimistic retry/dirty detection. Если полная проверка файлов обязательна под отдельным lock, она не должна удерживать mutex, который нужен token publication, на всём протяжении I/O.

**Детерминированный oracle:** использовать test hook `runConfigBeforeOpenHook` или `runConfigAfterStableReadHook` только на **втором**, финальном вызове `candidateInputsChanged`; барьер останавливает его внутри `readStableConfigFileOwned` после захвата locks. Параллельно вызвать `SetProviderRuntimeConfig` и OAuth publish с deadline и отменить contexts. До исправления обе операции остаются в `sync.Mutex.Lock` до освобождения барьера; после исправления config publication не должна ждать заблокированный файл. Зафиксировать порядок каналами, без sleep, реального сетевого mount и искусственной нагрузки. Такой oracle предлагается, здесь не исполнялся.

- **Add/Wait, channels и completion:** `agent_control.go:143-150,168-170,232-245` и `session/run_queue_drain_session.go:314-385` регистрируют работы под admission gate до Wait, а `run_queue_entry_dispatch.go:260-297` публикует outcome и освобождает session/slot в defer даже при panic. `app_run_reviewer.go:131,169,237-250` использует buffered `done` и `drainDone` ёмкости 1, поэтому ушедший receiver не блокирует единственный send. `ready_gate.go:71-103` поддерживает повторный и nested Go/Wait через Cond. Отдельный доказанный lost-completion здесь не установлен.
- **Context, watchdog и shutdown:** `run_queue_entry_exec.go:105-156,289-414,564-655` наследует execution ctx, имеет lease watchdog, останавливает и join-ит renewal перед Ack; Ack получает новый ограниченный DB context. `nettransport/handshake.go`, `proxy.go:117-184` и `client.go:188-231` ограничивают handshake/dial и освобождают conn при error. `app_run_drain_pending.go:42-55` имеет cancelable wait, хотя новый запуск после wait требует R13-1 fix. `runAgentTurnRecovered` (`app_run_turn.go:43-98`) посылает buffered completion даже при recover; panic background pump сохраняет re-panic после release, а не выдаёт ложный Ack.
- **Identity и retry:** `coordinator_attempt_evidence.go:31-66` запечатывает per-attempt callback; `coordinator_call_result.go:62-120` отделяет late generation; `app_run_reviewer_drain_identity.go:70-108` принимает durable identity только после `DrainComplete`; `session/run_queue_admission.go` привязывает waiter к admission entry. Указанные здесь R13-1/R13-2 происходят на иных границах, поэтому прежние R3-1/R7-1/R9-1 не подсчитаны повторно.
- **Прочий недельный diff и performance:** состав peak-hours/JSON, web metadata, npm cleanup, MCP test isolation и fs tool commits сверен с историей; отдельной доказанной concurrency regression по ним нет. Reconciliation читает session history, но без измеренного user impact от его стоимости performance finding не выставлен. Cache capacity ограничивает транспортный pool; нагрузки или benchmark не проводились.

## Метод и предел проверки

Использованы read-only `git status`, `rev-parse`, `log`/`rev-list`, `show`, `diff --stat`/`--numstat`/`--check`, поиск и чтение committed production-кода, его callers и точных test assertions. `git diff --check base..HEAD` не сообщил whitespace errors. Каждая приведённая последовательность разделяет DB message commit, queue Ack, mailbox ownership и config publish как самостоятельные события; доказательство не зависит от случайного scheduler timing. Предлагаемые oracles здесь **не исполнялись**.

**Не запускались:** любые Go tests (включая узкие и `-race`), полный suite, build, lint/vet, benchmarks, browser E2E, CI, реальные OAuth/LLM/MCP вызовы, fault probes и искусственная нагрузка. Поэтому здесь нет утверждения о runtime acceptance или об отсутствии всех возможных interleavings. Для снятия NO-GO нужны адресные fixes и детерминированные regression oracles выше на новом committed HEAD; результаты из commit messages/rounds 1–12 не приписываются round 13.
