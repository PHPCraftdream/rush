# Фаза 4, редакция 4: долговечное ядро работы — одна правда, историю пишет только ведущий, жизнь без часов

Статус: архитектурное решение оркестратора (2026-09-28). Основание: два
раунда ревью первой реализации фазы 4 (ветка `async-phase4`, не влита,
12 P1) и три раунда ревью этого документа (ред. 1: 6 P1; ред. 2: 2 P1;
ред. 3: 3 P1 в собранном вручную «ходе-заборе» — заменён вызовом-забором
через обычный `Run`; всё учтено ниже). Заменяет разделы «write-through»,
«доставка», «lease/heartbeat» и «recovery sweep» в
`docs/plans/2026-09-28-async-phase4-spec.md`; остальное переиспользуется с
правками ниже. Дизайн серии: `docs/plans/2026-09-27-async-structured-concurrency.md`,
законы: `docs/async-invariants.md`.

## 1. Диагноз: почему правки не сходились

Находки ревью первой реализации — следствия трёх решений:

1. **Два источника правды.** Состояние задачи жило в памяти и в SQLite; БД
   догоняла память записью вдогонку из каждого места перехода.
2. **Историю сессии писали посторонние.** Уведомления вставляли три
   механизма в произвольный момент, отметку «доставлено» ставили отдельно.
3. **Жизнь хоста по часам.** Сравнение отметок времени разных процессов.

Новая архитектура убирает все три источника. Ни одна из находок в ней
невыразима.

## 2. Понятия

- **Строка задачи** — `async_jobs`: async-задача (`bash`, `run_command`,
  `agent`, `agentic_fetch`, вызванные из CLI/web).
- **Строка уведомления** — `session_notices`: уведомление без строки
  задачи (надзор, маркер неудачного пробуждения, завершение фонового shell
  SDK-вызова, `wake_only`-таймаут).
- **Ведущий сессии** — держатель её мейлбокса **и** её OS session-lock,
  то есть идущий ход (`Run`), включая вызов-забор (3.4). Только ведущий
  пишет в историю сессии уведомления.
- **Хост** — процесс, исполняющий async-задачи; жив ⇔ держит ОС-блокировку
  своего файла (2.6).

## 3. Архитектура

### 3.1 Одна правда: `transition`

Состояние строки задачи меняет **одна функция** `transition`: транзакция с
SQL-CAS `UPDATE … WHERE owner=? AND call=? AND state='running'`, в ней же —
поля доставки (3.2).

- Победитель CAS обновляет память после коммита; проигравший читает
  строку и принимает её состояние. Память сходится к БД.
- Держатель исхода (исполнитель, отмена, таймаут, `job_kill`, `abort`)
  повторяет операцию с нарастающей паузой, пока не закоммитит или не
  увидит строку терминальной/удалённой.
- Внешняя причина действует в порядке «снимок вывода → `transition` с
  причиной → остановка исполнителя»; остановленный исполнитель
  проигрывает CAS, причина не подменяется «context canceled».
- Защёлка «переход идёт» в памяти: другие триггеры её **пропускают** (не
  ждут); держатель после коммита подаёт сигнал области.
- Защёлка shutdown проверяется **внутри** `transition`. «Вызван
  завершением процесса» ⇔ защёлка поднята **и** контекст исполнителя
  отменён самим `close()`; такие переходы подавляются, естественные
  завершения записываются. То же правило действует в `recheckChild`:
  ход ребёнка, прерванный shutdown, не считается «область ребёнка
  закрыта», и делегация не завершается усечённым текстом.

Память (`workLedger`) хранит исполнителей, функции отмены, защёлки и
сигналы и никогда не решает исход async-задачи. **Sync-задачи**
(SDK-вызовы: результат — ответ самого инструмента) в БД не пишутся и
живут по старой схеме в памяти; `wake_only` для них не применяется
(вызывающий и так ждёт); SDK-делегации не видны `sessions why/list` —
это принятое ограничение библиотечного режима.

Если БД недоступна при старте async-задачи — инструмент возвращает ошибку
и задачу не запускает (fail-closed).

### 3.2 Исходящий ящик в строке

Поля строки задачи: `delivery` = `none` | `pending` | `done` | `void`,
`notice_message_id`, `wake` (0/1), причина терминального состояния.
Терминальный `transition` в той же транзакции ставит `delivery='pending'` и
`wake` по причине (3.4). `abort` (ack-транзакция не прошла) удаляет строку
`announced=0` под тем же правилом повтора.

Строки уведомлений (`session_notices`) — тот же ящик: `owner` (внешний
ключ на `sessions` с `ON DELETE CASCADE`), вид, текст, `wake`,
`delivery`, необязательный ключ задачи для условия «задача ещё
`running`»; ретеншн — тем же проходом, что и строки задач.

### 3.3 Забор: историю пишет только ведущий, только между шагами

Ведущий забирает `pending` своей сессии (строки задач с `announced=1` и
строки уведомлений) в двух точках:

- **в начале хода — до загрузки истории для промпта;**
- **на границе шага** (`PrepareStep` обычного хода, по образцу
  `DrainPendingInjects`, с подмешиванием в текущий промпт). Шаги
  компакции не забирают.

Одна транзакция на уведомление: `UPDATE … SET delivery='done' … WHERE …
AND delivery='pending' [AND announced=1] RETURNING …` → `INSERT`
сообщения → id в строку. 0 строк → откат. Для уведомления с ключом задачи
в той же транзакции проверяется, что задача `running`, иначе оно
`void`. События UI публикуются после коммита. Ошибка забора не валит ход:
строки остаются `pending`.

Уведомление появляется в истории только между шагами. Два ведущих
невозможны (мейлбокс + session-lock); транзакция в любом случае допускает
ровно одного победителя.

Пользовательские вставки (`InjectMessage`, `sessions inject`) этим
законом не охватываются и пишут как раньше — вне объёма фазы.

### 3.4 Нужен ли ход: вызов-забор через обычный `Run`

**Нужен ход для сессии S** ⇔ у S есть `pending` c `wake=1` (строки задач
с `announced=1` и строки уведомлений).

**Вызов-забор** — отдельный вид `SessionAgentCall` (`Drain`), который идёт
обычным путём `Run`/`submit`, а не собирается из деталей:

- сессия свободна — вызов становится владельцем как любой ход (мейлбокс и
  session-lock берёт сам `runOwned`); занята — встаёт в очередь, но в
  очереди сессии не больше одного вызова-забора (одинаковые сливаются);
- никогда не ставится в долговременную очередь и не переживает
  `restartOrphaned`: долговечны строки, а не вызов;
- в начале хода забирает уведомления (3.3); если среди забранных нет
  `wake=1` или политика сессии запрещает ход — освобождает сессию **без
  обращения к провайдеру**; иначе ведёт ход с **пустым промптом**
  (`ErrEmptyPrompt` снимается только для вызова-забора; последнее
  сообщение истории — забранное уведомление) и признаками
  `AutoResumed`/`BackgroundJobNotice` (заголовок сессии не строится по
  уведомлению).

**Кто запускает вызов-забор:**

- После коммита перехода/уведомления с `wake=1` подаётся неблокирующая
  **подсказка** сессии.
- **Каждое освобождение мейлбокса** (единая воронка `onSessionIdle`,
  фаза 3) проверяет по БД «нужен ход для S». Строка коммитится до
  подсказки, а проверка читает БД после освобождения — уведомление,
  пришедшее во время последнего шага, не застревает.
- На подсказку или положительную проверку запускается вызов-забор — **в
  отдельной горутине**, никогда из `defer` освобождения. Три правила
  против холостого круга: (а) вызов-забор, который ничего не забрал, при
  своём освобождении проверку не повторяет; (б) session-lock S держит
  другой процесс (разделяемая проба) — ничего не делать: там свой
  ведущий, его освобождение сделает проверку само; (в) ошибка забора или
  проверки — повтор по следующей подсказке или 60-секундному проходу, не
  сразу.
- **Сессии с внешним ведущим** (CLI-корень: его ведёт цикл `rush run`)
  вызов-забор не получают — только подсказку циклу. Цикл сам решает по
  тому же предикату и собирает итог своих ходов.

**Политика сессии «можно ли ход»:** дочерняя сессия — да (её драйвер);
CLI-корень — решает цикл; web — только при автономии (`autoResumeEligible`
с его пределом подряд идущих ходов и сбросом по сообщению человека);
иначе вызов-забор только переносит уведомления в историю. Web-клиент,
подписавшийся на сессию, тоже запускает вызов-забор без хода — после
перезапуска сервера уведомления видны сразу.

**Политика `wake`:**

| Источник | `wake` |
|---|---|
| естественное завершение задачи, таймаут | 1 |
| Stop, `job_kill`, прерывание (3.7) | 0 |
| надзор | 1; при заборе — `void`, если область уже закрыта |
| `wake_only`-таймаут | 1; при заборе — `void`, если задача уже не `running` |
| маркер неудачного пробуждения | 0 |
| завершение фонового shell SDK-вызова | как у web-автономии |

Для `job_kill` итог — ответ самого инструмента, строка сразу `done`.
**Stop** в том же проходе ставит `wake=0` всем `pending` строкам задач и
уведомлений остановленного дерева — завершившееся за секунду до Stop не
запускает ход после него.

### 3.5 Область и выход `rush run` — из БД

**Область S открыта** ⇔ у S есть `running` строка задачи на **живом**
хосте, или S ведёт ход / зарезервирована, или «нужен ход для S». Дочерняя
работа входит через строку делегации: она `running`, пока область ребёнка
не закрыта (фаза 3). Потомки по `parent_session_id` не обходятся.

В начале хода и при оценке области (не на каждом шаге) ведущий выполняет
**восстановление своей области** (3.7): строки мёртвых хостов в области →
`interrupted`. Поэтому `rush run --continue` после падения или Ctrl-C
прошлого запуска не ждёт мёртвые строки, а первым ходом получает
«прервано».

CLI-цикл: ход ⇔ «нужен ход для корня» (или исходный запрос); выход ⇔
область корня закрыта. Лишняя или потерянная подсказка исхода не меняет.
Ошибка чтения БД при оценке — повтор с паузой, не молчаливый пропуск.

**Единственный межпроцессный запасной путь — 60-секундный проход:**
подсказки живут внутри процесса, поэтому хост раз в 60 с перепроверяет
свои припаркованные делегации, а CLI-цикл, в области которого есть строки
чужого живого хоста, раз в 60 с заново оценивает область. Других опросов
в архитектуре нет.

### 3.6 Жизнь процесса — блокировка ОС, без часов

- Хост регистрируется **лениво, при первом claim** async-задачи: случайный
  uuid, файл `<data>/hosts/<host_id>.lock`, эксклюзивная ОС-блокировка на
  всё время жизни процесса, сильная ссылка (без финализатора).
- **Мёртв ⇔ блокировку удалось захватить**, либо файла нет (ENOENT).
  «Жив» — при отказе «занято» (`EWOULDBLOCK` / `ERROR_LOCK_VIOLATION`).
  Любая другая ошибка — «неизвестно»: строки остаются, область их не
  считает открытыми только при «мёртв». Проба открывает файл без
  создания. Свой host_id и host_id других App этого процесса не
  пробуются. Файловая система без блокировок — отказ при регистрации;
  каталог данных — только локальный диск; `hosts/` руками не трогать.
- Пробовать и восстанавливать может **любой** процесс (ведущий, CLI,
  web), не только хост: захват блокировки мёртвого не требует быть хостом.
- Файл удаляет владелец при выходе, если строк не осталось; чужие —
  восстановитель, держащий блокировку, после проверки, что открытый файл
  тот же, что по пути (на Windows — закрыть, затем удалить; проигранная
  гонка оставляет лишний файл, его уберёт ретеншн).
- `async_hosts` — только для показа, без внешнего ключа из `async_jobs` и
  без отметок времени для решения о жизни.

### 3.7 Восстановление — только факты

Выполняется: ведущим для своей области (3.5); хостом — при регистрации и
раз в 60 с по всем мёртвым хостам. Для мёртвого хоста, удерживая его
блокировку:

- `running` с `announced=1` → `transition` в `interrupted` (`wake=0`):
  для делегации — с последним сообщением ассистента дочерней сессии; для
  bash/run_command — «вывод не сохранялся; процесс мог остаться
  запущенным» (процессы не убиваются: на Windows дерево уже снято job
  object хоста, на POSIX надёжной метки группы нет);
- `running` с `announced=0` → удалить без следа (ASYNC-05);
- строк не осталось → удалить строку хоста и файл.

Хост раз в 60 с также перепроверяет свои припаркованные делегации
(`recheckChild`), дочерние задачи которых могли быть восстановлены другим
процессом. Ретеншн (этим же проходом): `done`/`void` старше порога,
файлы мёртвых хостов без строк.

Восстановление **не пишет историю и не будит сессии**; «прервано»
заберёт ведущий. Корректный выход процесса = падение: исполнители
останавливаются, переходы от отмены при shutdown подавлены, строки
остаются `running`, следующий ведущий/хост их восстановит.

### 3.8 Stop, Rerun, делегации, ASYNC-01

- **Stop транзитивен:** отмена сессии отменяет всё дерево через
  `running` строки делегаций; всем строкам — `wake=0` (ASYNC-08). Дочерние
  задачи не будят детей после Stop.
- **Rerun** (усечение истории) переводит строки, анонсированные в
  удалённом хвосте, в `void`: их уведомления не материализуются.
  Компакция строки не трогает.
- **Claim делегации** пишет `child_session_id` сразу (id детерминирован;
  внешний ключ на `sessions` для этой колонки убирается). В транзакции
  claim: сначала чтение по ключу (идемпотентный повтор); затем проверка
  частичного уникального индекса `child_session_id WHERE state='running'`
  (ASYNC-01): конфликт с мёртвым хостом → восстановить его строку в той же
  попытке; с живым → ошибка инструмента **до** «started». Это меняет
  поведение: раньше `resume_session_id` при делегации, ход ребёнка
  которой закончен, а его задачи ещё идут, вставал в очередь; теперь —
  ошибка с понятным текстом («у под-агента ещё идёт работа прошлой
  делегации; дождитесь её результата»). Отразить в CHANGELOG.
- **Ack gate:** «started» и `announced=1` — одна транзакция без условия на
  состояние; если строка уже терминальна — после коммита подсказка.
- Читатели между процессами (`LiveJobs`, `sessions jobs`): живость =
  `running` и хост жив по 3.6 (разделяемая проба).
- Индексы: `(host_id)`, `(owner_session_id) WHERE delivery='pending'`,
  `(state) WHERE state='running'`, уникальный частичный по
  `child_session_id`; для `session_notices` — `(owner) WHERE delivery='pending'`.

## 4. Законы (в `docs/async-invariants.md`)

| ID | Закон |
|---|---|
| DUR-1 | Состояние async-задачи меняет только `transition`: одна транзакция с SQL-CAS; память сходится к БД; держатель исхода повторяет до коммита. |
| DUR-2 | Терминальный переход, `delivery='pending'` и `wake` по причине — одна транзакция. |
| DUR-3 | Уведомления пишет в историю только ведущий сессии, только в начале хода или на границе шага; уведомление и `delivery='done'` — одна транзакция. |
| DUR-4 | «Нужен ход» и «область открыта» решаются по БД; каждое освобождение мейлбокса проверяет «нужен ход» и при необходимости подаёт вызов-забор обычным путём `Run`. Подсказка лишь будит. Вызов-забор, ничего не забравший, проверку не повторяет. |
| DUR-5 | Процесс жив ⇔ держит ОС-блокировку своего файла хоста; «мёртв» — только при захвате или отсутствии файла. Часы не используются. |
| DUR-6 | Восстановление только переводит `running` мёртвого хоста в `interrupted`/удаляет неанонсированное; историю не пишет и сессии не будит. |
| DUR-7 | «started» и `announced=1` — одна транзакция; неанонсированная задача никогда не даёт уведомления. |
| DUR-8 | БД недоступна при старте async-задачи — задача не запускается. |
| DUR-9 | Stop отменяет дерево делегаций; отменённая и прерванная работа не будит никого. |

## 5. Порядок реализации

Новая ветка от `main`; куски ветки `async-phase4` переносятся по мере
надобности. Коммит на шаг; каждый шаг собирается и проходит тесты.

0. Схема (`async_jobs`, `async_hosts`, `session_notices`) и sqlc —
   миграция не выпущена, правится сама.
1. Хост: ленивая регистрация, блокировка, проба (3.6).
2. `transition`: повтор, защёлки, приём проигрыша, порядок внешних
   причин, shutdown-защёлка; все места перехода — через него.
3. Забор ведущим (начало хода, `PrepareStep`), строки уведомлений;
   перевести надзор, `wake_failed`, SDK bg shells, `wake_only` на
   `session_notices`; удалить `InjectMessage`-путь уведомлений,
   `s.ready`, `markDrained`, `ClaimAsyncCompletions`, `noticedBefore`.
4. Вызов-забор (`Drain` через `Run`/`submit`, слияние в очереди, без
   долговременной очереди, пустой промпт), проверка на освобождении,
   политика `wake` и сессий, CLI-цикл по БД (3.4, 3.5).
5. Восстановление: область ведущего, проход хоста, перепроверка
   делегаций, ретеншн (3.7).

## 6. Обязательные тесты (реальная SQLite, где речь о БД)

- DUR-1: `transition` при занятой БД повторяется и коммитит; проигравший
  принимает состояние; отмена/таймаут/`job_kill` дают свою причину;
  shutdown не подавляет естественное завершение.
- DUR-3: уведомление не оказывается между вызовом инструмента и его
  результатами (ход с двумя инструментами, async-задача завершается
  между ними); ведущие в двух процессах (два `*sql.DB` на файл) — одно
  сообщение; ошибка забора не валит ход; компакция не забирает.
- DUR-4: задача ребёнка завершается во время последнего шага его хода —
  на освобождении запускается вызов-забор, **ребёнок делает ход над
  уведомлением** (проверяется ход, а не только закрытие делегации),
  делегация родителя закрывается, `rush run` завершается;
  лишняя/потерянная подсказка не даёт лишнего хода; вызов-забор при
  session-lock, занятом другим процессом, и при постоянной ошибке забора
  не зацикливается (счётчик запусков ограничен); у CLI-корня вызов-забор
  не запускается, итог последнего хода цикла попадает в JSON-конверт;
  провайдер не видит уведомление дважды.
- Stop через секунду после естественного завершения задачи — нового хода
  нет.
- Маркер неудачного пробуждения при постоянно отказывающем провайдере не
  порождает цепочку ходов и маркеров.
- Быстрая задача, завершившаяся до ack: одно уведомление, после «started».
- DUR-9: Stop сессии с N под-агентами, у которых свои bash — ни одного
  нового хода ни в одной сессии; N фактов; после перезапуска — ни одного
  лишнего.
- Rerun после Stop: уведомления об удалённых вызовах не появляются.
- ASYNC-01: `resume_session_id` при живой делегации — ошибка до
  «started»; при мёртвой — восстановление и старт; повтор того же вызова —
  идемпотентный ответ.
- DUR-5: живой хост не «мёртв» ни при какой пробе; неизвестная ошибка не
  даёт «мёртв»; процесс без задач хост не регистрирует.
- DUR-6: восстановление не создаёт сообщений и ходов.
- Сквозные в `internal/app` (два App на одном каталоге данных):
  (а) A запускает async bash, анонсирует, «падает» (освобождает
  блокировку без close); `rush run --continue` в B получает ровно одно
  «прервано» в первом промпте и завершается; (б) задача завершена и
  доставлена в A — B ничего не добавляет; (в) Ctrl-C `rush run` с живыми
  задачами — ни одного нового хода, после перезапуска — одно «прервано»
  на задачу.
- `job_kill`: итог в ответе инструмента с реальным выводом; второго
  уведомления и хода нет.
