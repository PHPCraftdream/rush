## Findings

### F1 — P1: `messages_list` может затереть более новые live-события

Файлы: `web/src/useWS.ts:169-244`, `web/src/store.ts:130-132, 240-265, 298-302`, `web/src/ws.ts:87-133`.

Добавленный guard сравнивает только ID запросов `load_messages`. Он не учитывает изменения, пришедшие между чтением snapshot на сервере и его доставкой клиенту. Возможная последовательность:

1. отправлен `load_messages`, сервер получил старый snapshot;
2. приходит `message_created`/`message_updated`, сообщение добавляется через `upsertMessage`;
3. старый, но формально «последний разрешённый» `messages_list` принимается и вызывает безусловный `setMessages(msgs)`.

В результате новое сообщение или свежие части assistant-сообщения исчезают с экрана до следующего poll/reload. Для sub-agent используется такой же wholesale replace через `setSubAgentMessages`. База данных при этом не повреждается, но transcript UI теряет данные и может отправить оператора к неверному действию.

**Что исправить:** ввести per-session revision/event epoch (или серверный sequence), связать snapshot с ним и применять snapshot только если после запроса не было более новых событий. Альтернатива — merge по message/part ID с правилами удаления и tombstone, а не безусловная замена массива.

### F2 — P2: устаревший `sessions_list` может откатить sidebar

Файлы: `web/src/useWS.ts:113-145, 361-364`, `internal/server/handlers_sessions.go:224-245`.

Polling отправляет `list_sessions` без correlation ID. Сервер обрабатывает запросы worker pool без FIFO. Каждый ответ полностью вызывает `setSessions(sessions)`, тогда как `session_created`, `session_updated` и `session_deleted` изменяют список инкрементально. Старый snapshot может прийти после live-события и вернуть удалённую сессию, убрать только что созданную или откатить заголовок/ownership.

**Что исправить:** тегировать poll-запросы и отбрасывать старые ответы; лучше — добавлять server revision и объединять snapshot с live-событиями по revision/updated-at.

### F3 — P2: отправка attachment без текста невозможна

Файл: `web/src/components/ChatInput.tsx:316-318, 350-359, 633-638`.

`send` и `sendFast` возвращаются при пустом `text`, а `canSend` отключает кнопки при пустом тексте. При этом attachment уже выбран и backend `send_message` принимает `Attachments`; пользователь не получает ни отправки файла, ни объяснения. Коммит `0a877228` подключил attachments к существующим send paths, но не изменил это условие.

**Что исправить:** разрешить отправку при `activeSessionID && (text.trim() || attachments.length > 0)` и явно определить поведение slash-команд/пустого prompt.

### F4 — P1: disconnected send silently drops пользовательский ввод

Файлы: `web/src/ws.ts:68-71`, `web/src/components/ChatInput.tsx:316-360`.

`ws.send` просто возвращает, если сокет не `OPEN`, без результата и ошибки. `ChatInput` очищает текст и attachments сразу после вызова. Пользователь может нажать Send в короткое окно disconnect/reconnect и потерять уже набранное сообщение или файл без уведомления. Та же семантика затрагивает fast/interrupt/inject paths; busy-очередь также не имеет подтверждения доставки на сервер.

**Что исправить:** возвращать `boolean`/результат принятия, очищать форму только после успешной передачи; для надёжного UX нужен outbox с retry/ack и явное offline-состояние.

### F5 — P2: stale `get_system_prompt` может применить prompt другой сессии

Файл: `web/src/components/ChatToolbar.tsx:47-66`; серверный ответ: `internal/server/handlers_sessions.go:272-284`.

Modal подписывается на все `system_prompt` события и отправляет `get_system_prompt` без ID. Listener не проверяет ни `msg.id`, ни `payload.sessionID`. Если active session меняется пока modal открыт, ответ worker-а для A может прийти уже после переключения на B и заполнить форму B содержимым A; последующее сохранение запишет его в B.

**Что исправить:** присваивать UUID get-запросу, фильтровать по `msg.id` и sessionID, а также обрабатывать timeout/disconnect.

### F6 — P2: async delete в Sidebar использует устаревший active/session snapshot

Файл: `web/src/components/Sidebar.tsx:74-130`.

Reply-handler замыкает `activeID`/`allSessions` из render до отправки. Если пользователь переключит сессию до ответа `delete_session`, проверка `if (activeID === target.id)` может очистить уже другой текущий выбор. `delete_other_sessions` отправляет старый `keepID` и удаляет список из старого `allSessions`; live events в итоге исправят часть UI, но во время гонки возможны неверный active state и повторная загрузка не той сессии.

**Что исправить:** сверять актуальный store на момент ответа, reconcile по ID результата и блокировать/отменять конфликтующее переключение на время destructive operation.

### F7 — P2: редактирование provider с локальным scope сохраняется как global

Файл: `web/src/components/ProvidersModal.tsx:103-126, 611-648`.

Форма явно признаёт, что current scope не читается, и всегда начинает с `scope = "global"`. При редактировании effective provider из workspace/local config сохранение без ручной смены scope пишет global override, оставляя локальную запись нетронутой или создавая дубликат. UI удаления, напротив, предлагает Global/Local, то есть scope функционально значим.

**Что исправить:** отдавать scope в provider wire model и подставлять его при edit; либо запретить неявное сохранение и потребовать явного выбора с предупреждением.

### F8 — P2: `set_session_models` допускает частичный commit и сообщает success

Файл: `internal/server/handlers_models.go:45-109, 139`.

Smart/fast, worker/reviewer и reasoning effort обновляются отдельными операциями. Если поздний шаг падает, ранние изменения остаются в БД, но reply может быть `EventResponse`. Ошибки `UpdateWorkerReviewerReasoningEffort` и `UpdateReasoningEffort` только логируются как warning. Кроме того, пустой reasoning effort означает «не менять», поэтому явное очищение значения невозможно через этот payload.

**Что исправить:** одну транзакцию для всей операции либо response с per-field status; ошибки persistence не должны превращаться в общий `status=ok`. Разделить «не передано» и «очистить» в wire contract.

### F9 — P2: recovery намеренно оставляет orphan child messages

Файл: `internal/app/app_recovery.go:16-43`.

Startup sweep обрабатывает только top-level sessions. После hard kill trailing assistant message sub-agent остаётся без finish part навсегда; сейчас UI выводит parent-level `Process restarted`, но DB/CLI-потребитель child transcript видит незавершённую работу. Это не deadlock, а разрыв инварианта liveness, который станет багом при появлении нового consumer-а.

**Что исправить:** либо включить children в recovery с отдельным бюджетом/батчем, либо хранить явный child interruption marker и централизованно считать его при чтении.

## Дополнительные code smells (P3)

- `web/src/store.ts:697-705`: `dequeueNextMessage` больше не используется и возвращает только `string`, теряя attachments, тогда как основной путь использует `dequeueAllMessages` с attachments. Удалить dead API или синхронизировать контракт.
- `web/src/components/ChatInput.tsx:284-292`: send-now для skill не передаёт выбранные attachments и не очищает их, поэтому badge остаётся, а пользовательская команда уходит без файла.
- `web/src/components/ConfirmDialog.tsx:45-48`: overlay `onClick={onCancel}` не учитывает `busy`; backdrop закрывает destructive dialog во время запроса, вопреки комментариям о блокировке обеих кнопок.
- `web/src/ws.ts:111-119`: `latestLoadMessagesID` никогда не удаляет записи; это bounded по числу сессий, но lifetime map не очищается при удалении сессии.
- `internal/server/server.go:171-172`: `handleWS` отправляет `register` без select по server context. При остановленном Hub и заполненном register channel handshake goroutine может зависнуть до закрытия процесса. Это shutdown edge case, не основной runtime deadlock.
- Bounded worker pool после disconnect может доработать уже поставленные в очередь handlers и изменить DB, хотя клиент больше не получит reply. Это ожидаемая decoupling-семантика для agent run, но для destructive/config handlers стоит отдельно решить, нужна ли отмена по connection lifetime.

## Deadlock/freeze assessment

Исправление прежней проблемы выглядит структурно корректным:

- `dispatch` делает non-blocking enqueue в `workQueue` и возвращает overload вместо блокировки `readPump`;
- fixed worker pool ограничивает concurrency;
- `dispatchControl` отделён от долгих work handlers;
- `readPump` закрывает queue только после выхода из read loop, когда новые dispatch уже невозможны;
- unregister/send channel закрываются через hub event loop, `reply` защищён от send-closed panic.

В просмотренных последних изменениях не найдено классического цикла блокировок. Но это не устраняет F1/F2: UI может выглядеть «замороженным» или откатываться из-за stale snapshot даже при полностью живом backend. Также перегруз control semaphore (256 долгих interrupt requests) приведёт к отказу cancel с `server busy`, поэтому стоит иметь метрику/отдельный single-flight cancel per session.

## Что уже исправлено в диапазоне

Структурно полезными выглядят: request-order guard для конкурирующих `load_messages`, server-side wait перед sidebar deletion, payload результата `delete_other_sessions`, ack-aware save System Prompt, корректная адресация burst thinking parts, передача reasoning effort по wire, исправления done-state SubAgentBlock и защита metadata при редактировании message parts. Эти исправления не покрывают перечисленные выше snapshot-vs-live и offline-delivery гонки.
