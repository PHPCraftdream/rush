Вывод: ~5800 добавленных строк — внутренняя машинерия. Внешний контракт почти

взрыва. Это делает консолидацию безопасной для остального репозитория.

Структурная причина роста — состояние MCP живёт в package-level глобалах
(`init.go:366-377`):

```go
var (
    sessions    = csync.NewMap[string, *ClientSession]()   // 126 ссылок
    states      = csync.NewMap[string, ClientInfo]()       //  52
    stateOwners = csync.NewMap[string, *serverAdmission]() //   7
    broker      = pubsub.NewBroker[Event]()                //  15
    leases      = newLeaseRegistry()                       //  66
    lifecycleMu contextlock.RWMutex                        // 272
    owner       *Owner                                     // 736
    initDone    = closedChannel()                          //  25
    generation  uint64                                     //  55
)
```

Каждый `fence`/`pin`/`linearize`/`admission`/`generation`/`epoch` существует
только для того, чтобы заставить глобальное изменяемое состояние вести себя
как per-instance. Триггер был законный (SDK: несколько `App` в одном процессе
при одном реестре на процесс), ответ — несоразмерный.

**Поправка от 2026-09-09 (этап 0.2 закрыт):** описанный ниже P0 уже был
исправлен коммитом `00c9911f5` (2026-09-07 08:35, `lifecycleMu` внутри
`detachSessionLocked`, `init.go:4689-4693`) — примерно через 90 минут после
того, как ревью подтвердило его как живой. Обе проверки были верны на свой
момент времени. Задача #899 добавила недостающий оракул на cross-server
случай (`TestCommittedAdmissionsDisableAndPublishCrossServer`), revert-check
воспроизведён дважды независимо. Прод-код не менялся. Текст ниже оставлен как
описание механизма — он остаётся верным описанием того, ПОЧЕМУ нужен лок.

Открытый подтверждённый P0 на `main`: `Owner.committedAdmissions` — обычная
`map`, которую `detachSessionLocked` (`init.go:3889`) и его вызывающие
(`DisableSingle:2482-2488`, `disableServerWithResultPersistence`,
`removeServerWithResultPersistence`, `fenceMCPRuntimeLocked`) мутируют под
per-server `lease`, а `publishPreparedClientLocked:2441` и
`commitRenewalForLease` — под глобальным `lifecycleMu`. Конкурентный
disable/remove сервера A во время publish/renew сервера B →
`fatal error: concurrent map writes`, процесс падает целиком.

Почему цикл не сходился: у ревью не было условия остановки. Ревью
конкурентного кода над глобальным состоянием всегда находит ещё одно
достижимое чередование; каждый фикс добавлял guard и увеличивал пространство
состояний; следующее ревью находило больше. Цикл ускорялся, а не сходился.

## 1. Принципы

1. **Ничего полезного не удаляется.** Удаляется только код, ставший ненужным
   по построению, и только после того, как тест, который его защищал, продолжает
   проходить без него.
2. **Тесты — страховочная сетка, не балласт.** 11.5к строк тестов, в основном
   невакуумных (проверено пятью независимыми ревью), — это исполняемая
   спецификация. Она делает миграцию механической.
3. **Каждый шаг компилируется и проходит полный тест-прогон пакета.** Нет
   «большого перехода» — только последовательность малых, каждый из которых
   откатываем.
4. **Измеримый выход у каждого этапа.** Без него этап не закрыт.
5. **Условие остановки ревью задано заранее**, а не «пока находится».

### Этап 1 — Реестр инвариантов (3–4 дня). Главная работа.

Цель: отделить золото от свинца. Извлечь из guard-кода законы, которые он
защищает, и связать каждый с тестом.

**1.1. Инвентаризация guard-кода.**
Что: пройти `init.go` (и остальные 5 прод-файлов) функция за функцией; для
каждого `fence`/`pin`/`admission`/`generation`/`epoch`/`lease`-механизма
записать в `docs/mcp-invariants.md` одну строку: *какой закон он защищает*.
Формат строки: `INV-NN | формулировка | где в коде | какой тест доказывает |
коммит, который это выучил`. Зачем: инвариант в чистом виде — одна фраза;
сейчас каждый размазан по сотням строк. Реестр — постоянный актив при любом
будущем коде. Оценка: 2 дня. Ожидаемый размер: 15–25 инвариантов.

**1.2. Привязка тест ↔ инвариант.**
Что: для каждого из ~200 тестов в `mcp/*_test.go` указать, какой INV он
пиннит. Тест без инварианта — либо тестирует саму машинерию (fence тестирует
fence), либо вакуумный; пометить. Инвариант без теста — дыра в спецификации;
пометить для 1.4. Зачем: это и есть карта «за что заплачено». Оценка: 1 день.

**1.3. Разметка инвариантов по типу.**
Что: каждому INV присвоить одну из трёх меток:
- **S (структурный)** — станет невозможным нарушить, если состояние будет
  per-Owner (например: «fence переживает смену owner'а» — если нет общего
  состояния между owner'ами, нечего переживать).
- **M (механический)** — остаётся и требует реального механизма даже при
  per-Owner состоянии (например: «публикация и удаление одного имени внутри
  одного owner'а линеаризованы»).
- **X (спекулятивный)** — guard без наблюдаемого сценария отказа и без теста.
Зачем: это входные данные для этапа 2. Ожидание: S — большинство, M — 5–8,
X — остаток. Оценка: полдня.

**1.4. Дописать тесты для инвариантов без тестов.**
Что: для каждого INV с пустой колонкой «тест» — написать тест, который падает
при нарушении инварианта (revert-check обязателен). Зачем: миграция в этапе 3
опирается на тесты как на сетку; дыра в сетке — дыра в безопасности миграции.
Оценка: зависит от числа дыр, ориентир — полдня–день.

**1.5. Заполнить пустые тела коммитов ретроспективно.**
Что: не переписывать историю; вместо этого в `docs/mcp-invariants.md`
добавить раздел «коммит → инвариант», чтобы `git log` читался через реестр.
Зачем: сейчас у большинства MCP-коммитов пустое тело (chunk5: 43/43,
chunk3: 23/26); обоснование живёт только в 18 review-документах. Оценка: входит
в 1.1.

Выход этапа: `docs/mcp-invariants.md` с полным реестром, каждый инвариант
привязан к тесту, каждый помечен S/M/X. **Ни одна строка кода не удалена.**

Условие остановки этапа: реестр закрыт, когда 1.1 прошёл все прод-функции
пакета и 1.2 — все тесты. Не «пока находятся инварианты».

### Этап 2 — Дизайн сосуда (1 день, без кода)

Цель: с реестром в руках перевернуть вопрос — не «как защитить глобальное
состояние», а «в какой структуре инварианты выполняются сами».

**2.1. Модель владения.**
Что: одна страница `docs/plans/mcp-ownership-design.md`. Утверждение для
проверки: всё состояние из `init.go:366-377` становится полями `Owner`;
package-level остаётся только `currentOwner *Owner` (одна переменная — «кто
сейчас активен») и мьютекс на её замену. 27 экспортируемых функций становятся
тонкими обёртками: `func RunTool(...) { return currentOwner().runTool(...) }`.
Зачем: если нет общего состояния между owner'ами, S-инварианты невозможно
нарушить — и защищающий их код исчезает по построению.

**2.2. Соотнесение реестра с моделью.**
Что: для каждого INV из этапа 1 — одна строка: «держится структурой» (S,
код удаляется) / «держится механизмом» (M, механизм остаётся, но локальный
внутри Owner, без cross-owner защиты). Для X — решение: удалить или
переквалифицировать в S/M с тестом. Зачем: это спецификация того, что именно
удалится в этапе 3, — до того, как удалилось.

**2.3. Порядок миграции глобалов.**
Что: последовательность переноса, от малого к большому, чтобы каждый шаг был
мал и откатываем:

| Шаг | Глобал | Ссылок | Почему в этом месте |
|---|---|---|---|
| 3.1 | `stateOwners` | 7 | разминка, минимальный радиус |
| 3.2 | `broker` | 15 | независим от остальных |
| 3.3 | `initDone` | 25 | связан только с `Initialize`/`WaitForInit` |

### Этап 3 — Миграция (несколько дней, инкрементально)

Цель: перенести состояние в `Owner` под тестами; удалить guard-код, ставший
ненужным по построению; впервые увидеть строки, идущие вниз.

**3.1–3.8. По одной глобальной переменной, в порядке из 2.3.**
Каждый шаг — один коммит, одинаковая процедура:
1. Перенести переменную в поле `Owner`; все обращения — через owner.
2. `go build ./...` чист.
3. `go test -race -count=1 ./internal/agent/tools/mcp/...` — все тесты
   проходят. Число тестов ≥ базовой линии из 0.4.
4. Для каждого INV с меткой S, который этот шаг сделал структурным: удалить
   защищающий код; повторить п. 3. Если тест упал — код не был ненужным,
   вернуть, пометить INV как M, идти дальше.
5. Revert-check: временно вернуть глобал — тест из реестра, привязанный к
   удалённому guard'у, должен продолжать проходить (значит, инвариант
   действительно держится структурой, а не случайно).
6. Коммит с телом: какой глобал, какие INV стали структурными, сколько строк
   ушло.

Зачем именно так: поведение не меняется, меняется только владение. Тесты —
огонь, в котором проверяется каждый шаг; неверный шаг сгорает сразу, а не
через неделю в проде.

**3.9. Удаление X-инвариантов.**
Что: guard-код, помеченный X в 1.3 и не переквалифицированный в 2.2, —
удалить; полный прогон. Зачем: это спекулятивное укрепление без сценария
отказа; если тест не падает без него — он не нужен. Делается последним,
когда S уже удалены и картина ясна.

**3.10. Финальная сверка с реестром.**
Что: для каждого INV — проверить, что колонка «где в коде» актуальна, тест
проходит. Обновить `docs/mcp-invariants.md`.

Выход этапа — измеримый, чтобы цикл не воскрес:
- `init.go` < 2000 строк (ориентир — upstream 1391 + честная надбавка за
  M-инварианты);
- число тестов в `mcp/` ≥ базовой линии из 0.4 — **с оговоркой из этапа 1.2**
  (см. ниже про сеймы);
- 0 открытых P0/P1 с воспроизводимым сценарием;
- package-level `var` в `mcp/` — только `currentOwner` и его мьютекс.

Оценка: 3–5 дней. Честная оговорка: на текущей базе это дороже, чем было бы
на откаченной (1354 внутренних ссылки против пары сотен). Это цена того,
чтобы ничего не выбрасывать.

**Уточнение критерия «тестов не меньше 230» (внесено после этапа 1.2).**
Этап 1.2 обнаружил структурное ограничение: значительная часть оракулов
работает через ПРОД-сеймы — `serverLeaseHooks` (`init.go:442`),
`addAdmissionHooks` (`:449`), `mcpInitTestHooks`, renewal-хуки на
`serverLease`. Они используются в 8+ тест-файлах (до 33 ссылок в одном).
Если шаг 3.x удаляет guard вместе с инструментирующим его сеймом, такие
тесты **перестают компилироваться** — это механическое переписывание, а не
потеря покрытия.

Поэтому на каждом шаге 3.x применяется правило, а не голое число:
- тест удалён или переименован без замены → **стоп**, разбираться;
- тест переписан под новый сейм и продолжает пиннить тот же INV → допустимо,
  зафиксировать в коммите: какой тест, какой INV, почему потребовалось;
- итоговая проверка на этапе 3.10 — не «≥ 230 строк в `-list`», а «каждый из
  25 INV по-прежнему имеет хотя бы один живой невакуумный оракул».

Это единственный критерий, который нельзя удовлетворить, тихо удалив тесты.
