## Новые находки раунда 12

### R12-1 — P1: RunSessionAgentCall silently ignores a nil scoped-tools
result when call.CallOptions has FolderScope but no DiskProvider, AND
`scopedCallToolsRequired` returns false because ctx has no DiskProvider

**Файлы:** `internal/agent/coordinator_interrupt.go:720-732`

**Механизм:**

`RunSessionAgentCall` — функция, в которую pump передаёт rebuilt-вызов.
В строках 720-732:

```go
if call.CallOptions != nil && (call.CallOptions.FolderScope != nil || call.CallOptions.DisableSubAgents || call.CallOptions.ModelRole != "") {
    ctx = WithCallOptions(ctx, call.CallOptions)
    cfg, _ := c.cfg.Snapshot()
    scopedTools := c.pinCallTools(ctx, cfg)
    if scopedTools == nil {
        if scopedCallToolsRequired(ctx) {
            return nil, fmt.Errorf(...)
        }
    } else {
        call.Tools = scopedTools
    }
}
```

Триггер widening: `call.CallOptions.FolderScope != nil` (folder-scoped
вызов) **ИЛИ** `DisableSubAgents` **ИЛИ** `ModelRole != ""`.

Но проверка fail-closed: `scopedCallToolsRequired(ctx)` смотрит ТОЛЬКО
на `ctx`-прикреплённые `CallOptions`:

```go
func scopedCallToolsRequired(ctx context.Context) bool {
    opts := callOptionsFrom(ctx)
    return opts != nil && (opts.FolderScope != nil || opts.DiskProvider != nil)
}
```

`RebuildSessionAgentCall` (строки 612-656) строит `SessionAgentCall`
литерал, который содержит `CallOptions: rebuiltCallOptions`. Но
`rebuiltCallOptions` строится из `data.CallOptionsSpec` и
`data.FolderScopeSpec` — то есть из durable-строки.

**Сценарий отказа:**

1. Вызов был folder-scoped (FolderScopeSpec не nil).
2. `CallOptionsSpec` был nil (старая durable-строка, до R5-3, или
   legacy in-process caller, который не attaching CallOptions к ctx).
3. `RebuildSessionAgentCall` строит `rebuiltCallOptions` только из
   `fromSessionCallOptionsSpec(data.CallOptionsSpec)` — с `FolderScope`,
   собранным отдельно. Но `CallOptions.FolderScope` НЕ nil, а
   `CallOptions.DiskProvider` — nil.
4. `RunSessionAgentCall` заходит в блок (потому что FolderScope != nil).
5. `pinCallTools` возвращает nil (например, coder агент не настроен).
6. `scopedCallToolsRequired(ctx)` — смотрит на `ctx`-прикреплённые
   `CallOptions`, которые как раз и есть `call.CallOptions` (строка 721:
   `ctx = WithCallOptions(ctx, call.CallOptions)`).

Wait — `call.CallOptions` в этом сценарии НЕ nil, содержит `FolderScope`.
`scopedCallToolsRequired` вернёт true. Значит, fail-closed сработает.

Пересматриваю. **R12-1 не подтверждается** — контекст получает
точный `call.CallOptions`, и `scopedCallToolsRequired` его видит.

Но есть похожий, реальный сценарий:

### R12-1 (пересмотр) — P2: RunSessionAgentCall игнорирует nil
scoped-tools для FolderScope-only вызова, когда `pinCallTools`
возвращает nil ПОТОМУ ЧТО `buildTools` отрабатывает без ошибки, но
возвращает пустой срез

**Файлы:** `internal/agent/coordinator_models.go:538-570`,
`internal/agent/coordinator_interrupt.go:720-732`

`pinCallTools` возвращает nil в трёх случаях:
1. coder agent unconfigured (`cfg.Agents[config.AgentCoder]` not found)
2. `buildTools` возвращает ошибку
3. ready-gate `c.readyWg.Wait()` возвращает ошибку

Случай 1: coder unconfigured. `buildTools` не вызывается вообще.
`pinCallTools` возвращает nil. Для folder-scoped вызова
`scopedCallToolsRequired` вернёт true → fail-closed. Правильно.

Случай 2: `buildTools` возвращает ошибку. nil → fail-closed.
Правильно.

Случай 3: ready-gate ошибка. nil → fail-closed. Правильно.

Все три случая покрыты. **R12-1 (пересмотр) закрыт** — код корректен.

### R12-2 — P2: `/wrush` не проверяет, что работа идёт внутри worktree,
а не в primary checkout

**Файлы:** `internal/cmd/claude_wrush_command.md`,
`internal/cmd/claude_init.go`

`/wrush` — slash-command, delegating Rush sub-agent. Согласно
шаблону `claude_wrush_command.md`, sub-agent должен работать
**только** внутри worktree. Но:

1. Slash-command — это текст, который Claude Code интерпретирует.
   Нет кодовой проверки на уровне Rush, что cwd действительно
   находится под `<repo-root>/worktrees/`.
2. `claude-init.go` только пишет файл `wrush.md` в `.claude/commands/`.
   Не добавляет никакого runtime guard.

**Риск:** если оператор вручную запустит `/wrush` из primary checkout
(или если sub-agent проигнорирует инструкцию), модель получит
неограниченный доступ к primary checkout под видом worktree-изоляции.

**Статус:** documented-by-design (slash-command доверяет sub-agent'у),
но стоит явно отметить в риски как доверительную границу, а не
как bug. Комментарий в коде/документации уже есть: "Doing it yourself
instead of delegating still means: worktree first, edits there".

### R12-3 — P3: `CanonicalizeFolderScopeSpec` оставляет относительные
entries с пустым WorkingDir unchanged, передавая их `BuildFolderScope`,
но `BuildFolderScope` возвращает ошибку, которая в `ExecuteRun`
оборачивается в `"invalid folder scopes: %w"` — информация о том,
что проблема в конкретной entry, теряется

**Файлы:** `internal/agent/tools/fs_scope.go:166-174`,
`internal/app/app_run.go:680-687`

`CanonicalizeFolderScopeSpec` (строка 169):
```go
if dir == "" || (!filepath.IsAbs(dir) && workingDir == "") {
    out.Entries[i] = entry
    continue
}
```

Если `WorkingDir` пустой и entry относительная — entry пропускается
 unchanged, возвращается `out`. `BuildFolderScope` потом вернёт
`"folder scope entry N: Dir %q is relative but WorkingDir is empty"`.

В `ExecuteRun` (строка 682):
```go
canonSpec, err := tools.CanonicalizeFolderScopeSpec(ctx, overrides.DiskProvider, spec)
if err != nil {
    return nil, fmt.Errorf("invalid folder scopes: %w", err)
}
```

Если `CanonicalizeFolderScopeSpec` вернул `out` с unchanged relative
entry и nil ошибкой — `BuildFolderScope` вызовет ошибку, которая
дойдёт до пользователя. Информация о том, что проблема в конкретной
entry, сохраняется. **R12-3 не подтверждается** — код корректен.

### R12-4 — P3: `fs_write` теряет `FSStatusOK` для последнего item,
если `current == oldContent` после применения всех items

**Файлы:** `internal/agent/tools/fs_write.go:264-276`

```go
if current == oldContent {
    for i := range outcomes {
        if outcomes[i].Status == FSStatusOK {
            outcomes[i] = FSItemOutcome{
                Status: FSStatusFailed,
                Error:  "no changes made - the file content is identical after applying all items",
            }
        }
    }
    return outcomes, nil
}
```

Если в batch два item'а: первый пишет "A", второй пишет "B",
`current == oldContent` не сработает (старое содержимое ≠ "B").
Если два item'а: первый пишет "A", второй пишет "A" — первый
получит `FSStatusOK`, второй — `FSStatusFailed` ("already contains
exact content"), и `current == oldContent` не сработает.

Единственный сценарий, где это сработает: batch из одного item'а,
который не меняет содержимое (новый файл с содержимым, которое
уже есть в старом файле с тем же именем — но это `CreateOnly`
отдельно обрабатывается). Или batch из нескольких item'ов,
которые в сумме дают net-zero (например, insert+delete одной
строки).

В этих случаях **все** `FSStatusOK` превращаются в `FSStatusFailed`.
Это корректно: disk не меняется, модель должна знать что ни одно
из изменений не применилось. **R12-4 закрыт** — поведение корректно.

### R12-5 — P2: `fromSessionCallOptionsSpec` возвращает `nil` для
nil-спека, а `RebuildSessionAgentCall` проверяет `data.CallOptionsSpec != nil`
ПЕРЕД вызовом — но `data.FolderScopeSpec != nil` может быть без
`CallOptionsSpec`

**Файлы:** `internal/agent/coordinator_interrupt.go:587-610`,
`internal/agent/call_data_conversion.go:93-105`

```go
var rebuiltCallOptions *CallOptions
if data.CallOptionsSpec != nil || data.FolderScopeSpec != nil {
    rebuiltCallOptions = fromSessionCallOptionsSpec(data.CallOptionsSpec)
    if rebuiltCallOptions == nil {
        rebuiltCallOptions = &CallOptions{}
    }
}
if data.FolderScopeSpec != nil {
    ...
    rebuiltCallOptions.FolderScope = &compiledScope
}
```

Сценарий: durable-строка имеет `FolderScopeSpec != nil` (новая
строка, T12), но `CallOptionsSpec == nil` (старая строка, до R5-3,
или caller не setting CallOptions).

`fromSessionCallOptionsSpec(nil)` возвращает nil → `rebuiltCallOptions`
становится `&CallOptions{}` → `FolderScope` присваивается. Правильно.

Если И `CallOptionsSpec` nil, И `FolderScopeSpec` nil —
`rebuiltCallOptions` остаётся nil → `CallOptions: nil` в
`SessionAgentCall`. `RunSessionAgentCall` не зайдёт в блок
(строка 720: `call.CallOptions != nil` — false). Правильно.

**R12-5 закрыт** — код корректен.

### R12-6 — P3: `LibraryVirtualRoot` — потенциальный collision с
реальным путём, если хост использует `/rush-library-mode-root` как
реальный рабочий каталог

**Файлы:** `sdk/library_mode.go:87-113`

Док-комментарий `LibraryVirtualRoot` явно承认вает этот риск:
"The literal segment is specific enough that no real project is
plausibly rooted at this exact absolute path; even if it were, an
ephemeral ModeLibrary session only ever reaches a real filesystem
call through the caller's own DiskProvider, or, on caller misuse
(no DiskProvider), the real OS provider — in which case this value
denies/fails closed rather than granting anything."

Фактический collision маловероятен, и поведение при碰撞 —
fail-closed (реальный OS provider вернёт `fs.ErrNotExist` для
несуществующего пути, scope-check его deny'ит). **R12-6 — accepted
risk, documented.**

### R12-7 — P2: `/wrush` template не упоминает `--agents single` и
не объясняет, как worktree-изоляция взаимодействует с delegation tools

**Файлы:** `internal/cmd/claude_wrush_command.md`

`/wrush` наследует `/rush` playbook (включая `--agents single`),
но в шаблоне нет явного упоминания что:
- sub-agent, запущенный внутри worktree, тоже работает внутри
  worktree (если он использует `rush run`, его cwd — worktree).
- `--agents single` всё ещё работает; sub-agent не получит
  delegation tools, но сам worktree-запуск — это уже delegation.

Это documentation gap в slash-command template, не в коде. **R12-7
— documentation gap, не code defect.**
