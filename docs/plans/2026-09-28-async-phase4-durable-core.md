# Фаза 4, редакция 2: долговечное ядро работы — одна правда, историю пишет только ведущий, жизнь без часов

Статус: архитектурное решение оркестратора (2026-09-28) по итогам двух
раундов ревью первой реализации фазы 4 (ветка `async-phase4`, 19 коммитов,
не влита) и ревью первой версии этого документа (6 P1, все учтены ниже).
Заменяет разделы «write-through», «доставка», «lease/heartbeat» и
«recovery sweep» в `docs/plans/2026-09-28-async-phase4-spec.md`; остальное
(схема задач, ack gate, идемпотентный старт, читатели, CLI) переиспользуется
с правками ниже. Дизайн серии: `docs/plans/2026-09-27-async-structured-concurrency.md`,
законы: `docs/async-invariants.md`.

## 1. Диагноз: почему правки не сходились

Два раунда ревью первой реализации нашли 12 P1 — следствия трёх решений:

1. **Два источника правды.** Состояние задачи жило в памяти и в SQLite; БД
   догоняла память записью вдогонку из каждого места перехода. Каждое
   место — шанс забыть запись, потерять её при сбое, записать не в том
   порядке. Очередь повторов лечила симптом.
2. **Историю сессии писали посторонние.** Уведомления вставляли три
   механизма (очередь CLI, горутина пробуждения, восстановление из чужого
   процесса) в произвольный момент, а отметку «доставлено» ставили
   отдельно. Отсюда потери, дубли, вставка между вызовом инструмента и его
   результатом, чужие ходы в сессиях после перезапуска.
3. **Жизнь хоста по часам.** Сравнение отметок времени разных процессов
   ломается от сна, шага часов, остановки монотонных часов.

Новая архитектура убирает все три источника. Ни одна из находок в ней
невыразима.

## 2. Архитектура

### 2.1 Одна правда: строка задачи

Строка `async_jobs` — единственный источник правды о состоянии async-задачи
(`bash`, `run_command`, `agent`, `agentic_fetch` из CLI/web). Любое
изменение состояния делает **одна функция** `transition`: транзакция с
SQL-CAS `UPDATE … WHERE owner=? AND call=? AND state='running'`.

- Победитель CAS обновляет память после коммита. Проигравший читает строку
  и принимает её состояние — память всегда сходится к БД.
- Тот, кто держит исход (исполнитель, отмена, таймаут, `job_kill`),
  повторяет `transition` с нарастающей паузой, пока не закоммитит или не
  увидит строку терминальной/удалённой. Исход не теряется из-за занятой БД.
- Внешняя причина (отмена, таймаут, `job_kill`) действует в порядке
  «снимок вывода → `transition` с причиной → остановка исполнителя».
  Исполнитель, остановленный после, проигрывает CAS — причина не
  подменяется «context canceled».
- В памяти на время транзакции стоит защёлка «переход идёт» — повторные
  попытки из других триггеров её ждут, а не долбят БД.

Память (`workLedger`) хранит лишь исполнителей, функции отмены, защёлки и
сигналы. Она никогда не решает исход.

**Sync-задачи** (SDK-вызовы, результат — ответ самого инструмента) в БД не
пишутся: их доставка — сам ответ, долговечность им не нужна, падение
процесса обрабатывает существующая синтетика осиротевших вызовов.

Если БД недоступна при старте async-задачи — инструмент возвращает ошибку
и задачу не запускает (fail-closed).

### 2.2 Доставка: строка — это исходящий ящик, пишет историю только ведущий

У строки: `delivery` = `none` | `pending` | `done`, `notice_message_id`,
`wake` (будить ли владельца), причина терминального состояния.
Терминальный переход в той же транзакции ставит `delivery='pending'` и
`wake` по причине (2.3).

**Ведущий сессии** — тот, кто держит её мейлбокс (владение ходом или
кратковременное резервирование `ReserveExclusive`). Только ведущий пишет в
историю сессии. Он забирает уведомления **сам, в безопасных точках**:

- в начале хода и на каждой границе шага (`PrepareStep`, тем же способом,
  что `DrainPendingInjects`) — все `pending` строки своей сессии с
  `announced=1`;
- одна транзакция на уведомление:
  `UPDATE async_jobs SET delivery='done' … WHERE … AND delivery='pending' AND announced=1 RETURNING …`,
  затем `INSERT` сообщения с id в строку; 0 строк → откат (доставил другой
  или строку удалил каскад удаления сессии);
- событие UI публикуется после коммита.

Сообщение появляется в истории только между шагами, никогда между вызовом
инструмента и его результатами. Два ведущих одновременно невозможны
(мейлбокс), два процесса — невозможны (session-lock), а транзакция всё
равно допускает ровно одного победителя.

### 2.3 Пробуждение — только подсказка, что ведущему есть работа

После коммита перехода с `wake=1` ledger подаёт подсказку «у сессии X есть
`pending`». Подсказка обеспечивает, что ведущий существует:

- сессия занята ходом в этом процессе — ничего делать не нужно, ход
  заберёт уведомление на следующей границе шага;
- CLI-корень `rush run` — сигнал его циклу (его цикл и есть ведущий);
- web-сессия — `wakeSession` резервирует мейлбокс и запускает ход (ход
  начнётся с забора уведомлений); при выключенной автономии —
  резервирует мейлбокс, забирает уведомления в историю и освобождает;
- дочерняя сессия — её драйвер.

Подсказка неблокирующая; её потеря не теряет факт — строка `pending`
будет забрана при следующем ходе.

**Политика пробуждения по причине:** естественное завершение и таймаут —
`wake=1`; отмена сессии (Stop) и `job_kill` — `wake=0` (факт записан,
пользователь/модель остановили работу сами — новый ход не запускается;
для `job_kill` ответ самого инструмента несёт итог, строка сразу
`delivery='done'`).

**Советующие уведомления** (`wake_only`-таймаут, надзор, маркер
неудачного пробуждения) идут тем же путём ведущего; `wake_only`
пишется, только если задача всё ещё `running` (условие в той же
транзакции), поэтому «ещё работает» не может встать после «завершилась».

### 2.4 Жизнь процесса — блокировка ОС, без часов

- Хост регистрируется **лениво, при первом claim** async-задачи: случайный
  uuid, файл `<data>/hosts/<host_id>.lock`, эксклюзивная блокировка ОС на
  всё время жизни процесса, сильная ссылка на неё (без финализатора,
  отпускающего замок). Процессы без задач (`rush sessions *`) хост не
  регистрируют и восстановлением не занимаются.
- **Процесс мёртв ⇔ его блокировку можно захватить.** Проба открывает
  файл без создания; «жив» — только при отказе «занято»
  (`EWOULDBLOCK` / `ERROR_LOCK_VIOLATION`); любая другая ошибка —
  «неизвестно», никогда «мёртв». Файловая система без блокировок —
  отказ при регистрации (как SQLite WAL, данные должны лежать на
  локальном диске). Свой host_id и host_id других App этого процесса не
  пробуются никогда.
- Файл удаляет только его владелец — при выходе, если у хоста не осталось
  строк. Чужие файлы мёртвых хостов удаляет восстановитель, держащий их
  блокировку, после проверки, что открытый файл — тот же, что по пути.
- Строка `async_hosts` — только для показа (pid, метка, время старта); без
  внешнего ключа из `async_jobs`, без отметок времени для решения о жизни.

### 2.5 Восстановление — только факты, без пробуждений

Проход при регистрации хоста и раз в 60 с:

1. Для каждого чужого мёртвого хоста (2.4), удерживая его блокировку:
   - `running` строки с `announced=1` → `transition` в `interrupted`
     (`delivery='pending'`, `wake=0`); текст — последняя известная
     сводка; для делегации — последнее сообщение ассистента дочерней
     сессии; для bash — «вывод не сохранялся; процесс мог остаться
     запущенным» (на POSIX, если записан id группы процессов, группа
     предварительно убивается через `childgroup_registry`);
   - `running` строки с `announced=0` удаляются без следа (ASYNC-05);
   - когда строк не осталось — удалить строку хоста и файл.
2. Ретеншн: `done`-строки старше порога удаляются этим же проходом.

Восстановитель **не пишет в историю и не будит сессии**. Уведомление
«прервано» заберёт ведущий, когда сессия будет вести ход: `rush run
--continue`, открытие в web, или родитель делегации в своём ходе.
Чужой процесс никогда не запускает ходов в чужих сессиях.

**Корректное завершение процесса** (выход web-сервера, Ctrl-C `rush run`):
исполнители останавливаются без `transition` (защёлка shutdown), строки
остаются `running`, блокировка освобождается при выходе, следующий
процесс переводит их в `interrupted`. Один путь для падения и выхода.

### 2.6 Область и выход `rush run` — из БД

Область сессии открыта ⇔ в области (сессия и её потомки) есть `running`
или `pending`-с-`wake=1` строки, или её мейлбокс занят. CLI-цикл:

- нужен ход ⇔ у корня есть `pending` строки или подсказка пришла;
- выход ⇔ область закрыта и корень не ведёт ход.

Решение принимается по БД, а не по сигналу: потерянный или лишний сигнал
не меняет исхода. Подсказка лишь будит ожидание.

### 2.7 Прочее

- Ack gate: сообщение «started» и `announced=1` — одна транзакция, **без
  условия на состояние** (быстрая задача могла уже завершиться); после
  коммита — подсказка, если строка уже терминальная.
- ASYNC-01 в БД: частичный уникальный индекс
  `async_jobs(child_session_id) WHERE state='running'` — вторая
  делегация на ту же дочернюю сессию не стартует, пока идёт первая.
- Идемпотентный claim по `(owner, tool_call_id)`; повтор отвечает по
  состоянию строки; идемпотентный `CreateTaskSession`; `child_session_id`
  заполняется после создания дочерней сессии.
- Читатели между процессами (`LiveJobs`, `sessions jobs`): живость строки
  = `running` и хост жив по 2.4 (разделяемая проба, не захват).
- Индексы под запросы прохода и ведущего: `(host_id)`,
  `(owner_session_id) WHERE delivery='pending'`, `(state) WHERE state='running'`.

## 3. Законы (в `docs/async-invariants.md`)

| ID | Закон |
|---|---|
| DUR-1 | Состояние async-задачи меняет только `transition`: одна транзакция с SQL-CAS; память сходится к БД (победитель — после коммита, проигравший — читая строку). Держатель исхода повторяет до коммита. |
| DUR-2 | Терминальный переход, `delivery='pending'` и политика `wake` пишутся одной транзакцией. |
| DUR-3 | Историю сессии пишет только её ведущий, только на границе хода/шага; уведомление и `delivery='done'` — одна транзакция. |
| DUR-4 | Пробуждение — неблокирующая подсказка; решение «нужен ход / можно выходить» принимается по БД. |
| DUR-5 | Процесс жив ⇔ удерживает ОС-блокировку своего файла хоста; «мёртв» — только при успешном захвате. Часы не используются. |
| DUR-6 | Восстановление только переводит `running` мёртвого хоста в `interrupted`; не пишет историю и не будит сессии. |
| DUR-7 | «started» и `announced=1` — одна транзакция; неанонсированная задача никогда не даёт уведомления. |
| DUR-8 | БД недоступна при старте async-задачи — задача не запускается. |

## 4. Порядок реализации

Новая ветка от `main`; куски ветки `async-phase4` переносятся по мере
надобности (схема, sqlc, ack gate, claim, читатели, CLI, тесты на реальной
БД). Коммит на шаг, каждый шаг собирается и проходит тесты:

0. Схема и sqlc (миграция не выпущена — правится сама).
1. Хост: ленивая регистрация, блокировка, проба, удаление своего файла.
2. `transition` (повтор, защёлка, приём проигрыша, порядок внешних
   причин); все места перехода в `internal/agent` — через него.
3. Ведущий забирает уведомления (начало хода, `PrepareStep`,
   резервирование для простаивающей web-сессии); подсказки; политика
   `wake`; советующие уведомления тем же путём. Удалить `s.ready`,
   `markDrained`, `ClaimAsyncCompletions`, `noticedBefore`,
   `InjectMessage`-путь уведомлений.
4. CLI-цикл: решение по БД (2.6).
5. Восстановление и shutdown (2.5).
6. Claim, ack gate, повтор по состоянию, `job_kill`, причины отмены,
   ASYNC-01-индекс.
7. Читатели, `sessions jobs`, `sessions gc`; удалить
   `internal/session/descendant_liveness.go`.
8. Законы DUR-1…8 в реестр, переанкеровка ASYNC-строк, CHANGELOG.

## 5. Обязательные тесты (реальная SQLite, где речь о БД)

- DUR-1: `transition` при занятой БД (искусственная блокировка записи)
  повторяется и закоммичивает; проигравший принимает состояние строки;
  отмена/таймаут/`job_kill` дают свою причину, не «context canceled».
- DUR-3: уведомление никогда не оказывается между вызовом инструмента и
  его результатами (ход с двумя инструментами, async-задача завершается
  между ними); два ведущих в двух процессах (два `*sql.DB` на файл) —
  одно сообщение.
- Быстрая задача, завершившаяся до ack: ровно одно уведомление, после
  «started».
- Отмена N параллельных под-агентов: N фактов, ни одного нового хода;
  после перезапуска — ни одного лишнего уведомления.
- DUR-5: живой хост не «мёртв» ни при какой пробе; неизвестная ошибка
  пробы не даёт «мёртв»; процесс без задач хост не регистрирует.
- DUR-6: восстановление не создаёт сообщений и ходов; уведомление
  «прервано» забирает следующий ход владельца.
- Сквозной тест в `internal/app`: два экземпляра App на одном каталоге
  данных; A запускает async bash, анонсирует, «падает» (освобождает
  блокировку хоста без close); B регистрирует хост и восстанавливает;
  `rush run --continue` владельца в B получает ровно одно «прервано» в
  промпте. Обратный случай: задача завершена и доставлена в A — B ничего
  не добавляет. Ctrl-C `rush run` с живыми задачами — ни одного нового
  хода, после перезапуска — одно «прервано» на задачу.
- CLI-цикл: лишняя/потерянная подсказка не меняет итог и не даёт лишнего
  хода; уведомление, пришедшее после последнего шага, получает ход.
- `job_kill`: итог в ответе инструмента содержит реальный вывод; второго
  уведомления и хода нет.
