First mitigation (8 batches instead of 4, `-parallel 1` instead of 2) moved the failure from batch 1 to batch 2 — real progress, not a fix. Second layer, `GOMEMLIMIT=1500MiB` (forces the GC to shed heap proactively instead of asking the OS to commit more), fully resolved it — confirmed green twice.
4. **`internal/hooks/runner_abandon_test.go`**: `TestRunnerAbandonHardKillSeam` received a phantom `nil` pids value instead of its real `[]int{424242}` — `hardKillAbandoned` (runner.go) spawns its own goroutine calling the package-level `abandonSeam` independently of when the wedged worker itself finishes; the *previous* test's (`TestRunnerAbandonedDoesNotBlockCaller`, via `wedgeRunShell`) hard-kill goroutine could survive past its own test's cleanup and fire against the *next* test's freshly-installed `abandonSeam`. `wedgeRunShell` now saves/restores `abandonSeam` too and drains exactly `invoked.Load()` hard-kill completions before returning.
5. **`internal/session/p350_dup_dispatch_test.go`**: `TestReleaseGate_P350_LeaseRenewedDuringLongExecution` reproduced the *exact same* already-diagnosed race from a prior task (#447) — lease renewal fires every `TTL/3`, so a too-tight TTL starves the renewal goroutine's wall-clock budget under CI contention. Task #447 had already widened TTL 1s→3s with this same reasoning; it recurred on windows-latest even at 3s (~1s/attempt still insufficient once). Escalated the *same* understood ratio to 5s (~1.67s/attempt) — this is a continuation of an already-principled fix, not a fresh guess.
