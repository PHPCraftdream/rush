## 4. Disk provider identity (75ccf190) — независимая проверка R15-3/R16-6

**Статус: безвредный рефакторинг; заявленная угроза ложна.**

### Проверка семантики Go

Standalone-программа (временный каталог вне модуля, `go run`) с `DP` interface, `osDisk struct{}`, `memDisk{files map, tags []string}` и `wrap{DP; tags []string}`:

```
mem != os (different dyn types)          -> true
os != mem (different dyn types)          -> true
w != os (wrap embeds os)                 -> true
mem == nil                               -> false
nilDP == nil                             -> true
mem == mem (same value)                  PANIC: comparing uncomparable type main.memDisk
mem == mem2 (same dyn type, uncomparable) PANIC: comparing uncomparable type main.memDisk
os == os                                 -> true
```

Вывод подтверждает спецификацию (Go spec, Comparison operators): сравнение двух interface-значений сначала сравнивает dynamic types; panic возникает только когда типы **идентичны** и этот тип uncomparable. Сравнение с `nil` не паникует никогда.

Применительно к коду до фикса:
- `overrides.DiskProvider == nil` / `disk != nil` — паника невозможна в принципе.
- `overrides.DiskProvider == tools.OSDisk()` / `disk != tools.OSDisk()` — dynamic type `OSDisk()` есть неэкспортируемый `osDisk struct{}` (`internal/agent/tools/fs_provider_os.go:18`), comparable. Внешний код не может сконструировать значение этого типа (даже через reflect он получит comparable `struct{}`), поэтому единственный случай совпадения типов — оба `osDisk` — comparable. Паника недостижима ни для одного `sdk.DiskProvider`, сколько бы map/slice полей он ни содержал.

R15-3 (`docs/reviews/2026-09-04-sdk-library-review-round-15-6928.md:149-174`) и R16-6 (`...-round-16-1209.md:197-215`, включая «panic выходит прямо из `Client.Run`») — **опровергнуты**. Более ранняя дисконфирмация в истории репозитория верна.

### Оценка самого коммита

- Код: `HasDiskProvider` (`fs_provider_os.go:39-46`) — эквивалент `d != nil` через type switch; `IsOSDisk` (`:51-54`) — marker interface `osDiskMarker` (`:24-28`); `IsCustomDiskProvider` (`:58-60`). Call sites: `coordinator_models.go:535`, `coordinator_tools.go:466`, `disk_provider_durable.go:33`, `fs_library_virtual_root.go:73`, `app_run.go:662,734,762`. Семантика идентична прежним сравнениям. Marker-метод не продвигается через embedded `DiskProvider` interface (не входит в его method set), поэтому wrapper `struct{ tools.DiskProvider; ... }` корректно классифицируется как custom — тест `TestDiskProviderIdentityPredicatesHandleNonComparableValues` это фиксирует.
- Комментарии утверждают ложную модель: `fs_provider_os.go:36-38` «deliberately uses a type switch rather than interface equality because DiskProvider's dynamic type is allowed to contain maps or slices», `:48-50` «providers whose dynamic values are not comparable, are never compared as interface values». Marker-предикат — легитимный identity-механизм сам по себе (устойчив к будущим экспортируемым/comparable-но-чужим типам), но обоснование в комментариях неверно.

### CR-1 — P0: `Owner.Initialize` отменяет context всех MCP transports сразу после инициализации (введено `01e909d0`)

Цепочка в HEAD:

- `init.go:454` — `initCtx, cancel := context.WithCancel(ctx)`.
- `init.go:467-469`:

  `defer cancel()` выполняется **безусловно** при возврате из `Initialize` — то есть на нормальном пути после `wg.Wait()` и `finishInitialize()` (`:511-512`).
- `init.go:506` — `initClient(initCtx, ...)` → `:564` `createSession(ctx=initCtx, ...)` → `:974` `mcpCtx, cancel := context.WithCancel(ctx)` → `:977` `createTransport(mcpCtx, ...)`.

- http/sse: `:1105`, `:1127` — `headerRoundTripper{ctx: mcpCtx}`; `RoundTrip` (`:1171-1198`) регистрирует `context.AfterFunc(rt.ctx, cancel)` на каждый запрос; для уже отменённого `rt.ctx` `AfterFunc` срабатывает немедленно.

Сценарий отказа: `rush` (web) или `rush run --all-mcp` с одним stdio MCP-сервером. `app.New` → `go app.mcpOwner.Initialize(ctx, ...)` (`internal/app/app.go:292-296`). Сервер стартует, `getTools/getPrompts` проходят, `sessions.Set`, `StateConnected`. `Initialize` возвращается → `cancel()` → `initCtx` → `mcpCtx` отменён → os/exec watcher вызывает `cmd.Cancel` → процесс сервера убит (на unix SIGKILL всей группе). Первый же `RunTool` → `getOrRenewClient` → `Ping` fails → `StateError` → renewal (см. CR-2) → новый процесс на один вызов. Наблюдаемо: каждый MCP tool call = полный респаун сервера (npx/uvx — секунды, вплоть до 15s timeout), состояние сервера (например, in-memory MCP, соединения с БД) теряется между вызовами, UI мигает Connected→Error→Connected. Для HTTP MCP: каждый запрос после init отменяется до отправки, тот же renewal-цикл.

### CR-2 — P1: renewal-сессии умирают при освобождении lease (`963d584a`, усиливает pre-existing)

`init.go:791-802` — `operationCtx, finish = o.operationContext(ctx)`; `:231-238` `operationContext` = `WithCancel(ctx вызова)` + `AfterFunc(lifecycleCtx)`; `finish` = `stop(); cancel()`. `:860` — `createSession(operationCtx, ...)`: `mcpCtx` renewal-сессии — потомок `operationCtx`. `:897-909` `newClientLease.release` вызывает `finish()` при `lease.close()` — то есть сразу после `CallTool`/`ReadResource`/`GetPrompt`.

Сценарий: любой успешный renewal (даже без CR-1 — например, сервер упал и перезапустился) создаёт сессию, чей stdio-процесс/HTTP round-tripper отменяется в момент `defer lease.close()` у вызывающего (`tools.go:59`, `resources.go:33,54`, `prompts.go:27`). Следующий вызов снова видит мёртвую сессию → снова renewal. Session никогда не переживает один вызов. До серии `createSession(ctx вызова)` тоже привязывал сессию к ctx вызова, но отмена зависела от вызывающего; теперь `finish()` делает её гарантированной.

Исправление: для `createSession` в renewal использовать ctx, производный от `o.lifecycleCtx` (плюс `mcpTimeout` для connect-фазы, как уже делает `cancelTimer`), а `operationCtx` — только для `Ping` и самой операции.

**Статус на `bc786a4d`:** закрыт именно так — `sessionCtx = o.lifecycleCtx` с комментарием «The renewed MCP session itself must survive that lease closing» (`init.go:1433-1440`). Тот же принцип не применён к начальной сессии в `initClientAdmitted` (CR-1).

### CR-3 — P2: `WaitForInit` может зависнуть на pre-Close `initDone`

`init.go:456-465` — ранние return'ы `Initialize` (`owner != o || o.closing`, `!beginInit()`) не вызывают `finishInitialize`. `finishClose` (`:300-305`) подменяет `initDone` на закрытый канал, но waiter, взявший старый канал в `WaitForInit` (`:518-520`) между `Acquire` и `finishClose`, ждёт до своего `ctx.Done()`. Единственный production-вызов — `internal/app/app_run.go:628` с ctx запуска (`rush run` без deadline). Достижимо только при гонке `Shutdown` с ещё не стартовавшим `Initialize`; практически — зависший `ExecuteRun` при немедленном shutdown после `New`. Низкая вероятность, но фикс тривиален: `finishInitialize` в `defer` независимо от пути выхода.

### CR-4 — P2 (design): `serverLease.RLock` удерживается на весь tool call

`init.go:804-823` — read-lease живёт до `lease.close()` у вызывающего; `:829` renewal берёт `Lock()`; `DisableSingle` (`:614-616`) и `RemoveServer` (`:761-763`) — тоже `Lock()`. `sync.RWMutex` даёт writer preference: как только один вызов провалил `Ping` и встал в `Lock()`, **все новые** вызовы на этот сервер блокируются в `RLock()` до завершения всех in-flight операций (MCP tool с минутным runtime — минутный стоп для всех сессий App). Аналогично «disable server» из UI висит за долгим tool call. Не deadlock (in-flight операции не берут lock повторно), но latency cliff, не описанный в комментариях `:76-82`.

## Итог

**Блокирует:** CR-1 (P0 на `0e4b9ed3`, P1 на текущем `bc786a4d`). До `01e909d0` MCP-серия была корректной; после — любой сконфигурированный MCP-сервер в application mode переживает только инициализацию. Проверено по цепочке `Initialize:454,469,506` → `createSession:974-977` → `platform.Command` = `exec.CommandContext` → go-sdk `CommandTransport.Connect` стартует тот же `exec.Cmd`; для HTTP — `headerRoundTripper.ctx` = тот же отменённый `mcpCtx`. Тестовое покрытие не могло этого поймать (`echo`-серверы и in-memory transports). На `bc786a4d` renewal стал lifecycle-scoped (CR-2 закрыт), но начальная сессия по-прежнему убивается — теперь уже на выходе из `initClientAdmitted`. Требуется фикс (начальная сессия должна деривироваться от `o.lifecycleCtx` так же, как renewal) + e2e regression с живым stdio-сервером, переживающим `Initialize` без `StateError`.

**Подождёт:** CR-3, CR-4, CR-8 и CR-12. CR-2 закрыт на HEAD; документационные CR-5..CR-7 закрыты этой correction-серией, а CR-9 закрыт как process limitation.

**Correction note по CR-10/CR-11:** принятый в `main` коммит `ee32c4a8`
закрыл оба nit: hook cleanup теперь безопасен при любом частичном `mktemp`
failure, мёртвый goose `init()` удалён, а race-only oracle явно описан.

Остальные 22 коммита (ephemeral tool surface, hook, goose, SDK client, background jobs, DB pool, cliprovider, test fixtures) корректны, тесты по большей части невакуумные, утечек не добавляют. Вопрос по `75ccf190`: паника при сравнении внешнего `DiskProvider` с `tools.OSDisk()`/`nil` в Go недостижима (разные dynamic types → `false`, без panic; `osDisk` comparable и неэкспортируем) — коммит безвреден как identity-рефакторинг; его комментарии и R15-3/R16-6 теперь исправлены correction notes без изменения production behavior.
