# Фаза 4, редакция 2: долговечное ядро работы — одна правда, одна доставка, жизнь без часов

Статус: архитектурное решение оркестратора (2026-09-28) по итогам двух
раундов ревью первой реализации фазы 4 (ветка `async-phase4`, 19 коммитов,
не влита). Заменяет разделы «write-through», «доставка», «lease/heartbeat» и
«recovery sweep» в `docs/plans/2026-09-28-async-phase4-spec.md`; остальное
(схема задач, ack gate, идемпотентный старт, читатели, CLI) переиспользуется
с правками ниже. Дизайн серии: `docs/plans/2026-09-27-async-structured-concurrency.md`,
законы: `docs/async-invariants.md`.

## 1. Диагноз: почему правки не сходились

Два раунда ревью нашли 12 P1. Все они — следствия трёх решений первой
реализации, а не отдельные недосмотры:

1. **Два источника правды.** Состояние задачи живёт в памяти (`workLedger`)
   и в SQLite; БД догоняет память «записью вдогонку» (write-through) из
   каждого места перехода — `finish`, `cancelSession`, `handleTimeout`,
   `abort`, `recheckChild`, `job_kill`. Каждое место — отдельная возможность
   забыть запись (P1-3), потерять её при сбое (P1-4), записать не в том
   порядке (N3). Очередь повторов лечит симптом и добавляет новые порядки.
2. **Доставка размазана.** Три механизма: очередь `s.ready` для CLI-корня,
   горутина пробуждения для web, отдельная отметка `delivered_at`
   (`MarkDelivered`) из двух мест. Факт «уведомление сохранено» и факт
   «отмечено доставленным» — разные записи в разное время; между ними
   падение даёт потерю или дубль (P1-6, N1, N3).
3. **Жизнь хоста по часам.** Lease и heartbeat сравнивают отметки времени
   разных процессов; сон ноутбука, шаг часов и монотонные часы, стоящие во
   сне, ломают любое сравнение (P1-5, N4); удаление «протухшего» хоста
   ломает живой (P2).

Новая архитектура убирает эти три источника целиком. Ни одна из находок
раундов 1–2 в ней невыразима.

## 2. Архитектура

### 2.1 Одна правда: строка задачи

Строка `async_jobs` — единственный источник правды о состоянии задачи.
Любое изменение состояния делает **одна функция** `transition` (пакет
`internal/session`, вызывается из `internal/agent`): транзакция с SQL-CAS
`UPDATE async_jobs SET state=?, … WHERE owner=? AND call=? AND state='running'`.
Победитель CAS — тот, у кого затронута 1 строка. Память обновляется только
после коммита и только победителем.

Память (`workLedger`) хранит лишь то, что не может жить в БД:
исполнители (горутины, процессы), функции отмены, ожидающие sync-вызовы,
каналы сигналов области. Память никогда не решает исход — она исполняет
решение, принятое транзакцией. Записи вдогонку, очереди повторов и сверки
памяти с БД больше нет: расходиться нечему.

Если БД недоступна при старте задачи — инструмент возвращает ошибку и
задачу не запускает (fail-closed). Режима «работаем без долговечности»
нет: он и порождал невидимые расхождения.

### 2.2 Доставка — часть той же строки (transactional outbox)

У строки задачи — колонка `delivery`: `none` | `pending` | `done`, и
`notice_message_id`. Терминальный переход в той же транзакции ставит
`delivery='pending'` (для sync-задач — `done`: их доставка — ответ самого
инструмента). Терминального состояния без записи к доставке не бывает.

**Доставка — одна функция `deliver`** и одна транзакция:

```
BEGIN
  INSERT сообщение-уведомление (User, BackgroundJobNotice, NoticeKind)
  UPDATE async_jobs SET delivery='done', notice_message_id=?
         WHERE owner=? AND call=? AND delivery='pending'
  -- затронуто 0 строк → ROLLBACK: доставил кто-то другой
COMMIT
→ после коммита: опубликовать CreatedEvent, подать сигнал будильнику владельца
```

Сообщение существует ⇔ строка `done`. Два доставщика одновременно (живой
процесс и восстановление, два процесса) — коммитит ровно один, второй
откатывает свою вставку. Ровно один раз — по построению, без карт
идемпотентности (`noticedBefore` удаляется).

`deliver` вызывается сразу после коммита терминального перехода, в той же
горутине. Если вызов не удался (БД занята) — строка остаётся `pending`, её
доставит следующий проход восстановления (2.4) этим же или другим
процессом. Отдельного механизма повторов нет.

### 2.3 Пробуждение — только сигнал

После коммита доставки `deliver` подаёт сигнал «в сессии X новое
уведомление» её будильнику. Будильник — одна точка на сессию:

- по умолчанию — `wakeSession`: ход над уже сохранённым сообщением
  (`ExistingMessageID`); если сессия занята — сообщение уже в БД и
  подмешивается в идущий ход существующим `injectIfBusy`;
- для CLI-корня `rush run` — его цикл регистрирует свой будильник: сигнал
  в цикл, который сам запускает следующий ход над сохранёнными
  сообщениями. Очередь `s.ready`, `markDrained`, `ClaimAsyncCompletions`,
  `MarkAsyncCompletionDelivered` и путь «завершение → текст нового
  промпта» удаляются: CLI и web получают факт одинаково.

Потеря сигнала не теряет факт: уведомление уже сохранено и увидится на
следующем ходе.

### 2.4 Жизнь процесса — блокировка ОС, без часов

Каждый процесс, владеющий задачами, при старте создаёт
`<data>/hosts/<host_id>.lock` и держит его эксклюзивную блокировку ОС
(`session.TryAcquireFileLock`) всё время жизни. ОС снимает её при любой
смерти процесса — kill, OOM, падение, выключение. **Процесс мёртв ⇔ его
блокировку можно захватить.** Нет heartbeat, lease, `heartbeat_at`,
`lease_expires_at`, сравнения часов и защиты от скачков часов — удаляются.
Строка `async_hosts` остаётся только для показа (pid, метка, время старта).

### 2.5 Восстановление

Проход восстановления — при старте процесса и раз в 60 с, пока процесс
живёт (дешёвый запрос по индексам):

1. Для каждого чужого `host_id`, у которого есть `running` строки или
   `pending` доставки: попытка захватить его блокировку. Не удалось — хост
   жив, пропустить. Удалось — держать блокировку на всё время обработки
   (она же сериализует восстановителей из разных процессов):
   - каждую `running` строку — `transition` в `interrupted`
     (`delivery='pending'`, текст с последним известным выводом);
   - каждую `pending` строку — `deliver`;
   - строки с `announced=0` удаляются без уведомления (ASYNC-05);
   - когда у хоста не осталось строк — удалить строку хоста и файл.
2. Свои `pending` строки (доставка не удалась при переходе) — `deliver`.
   Гонки с живой доставкой нет: транзакция 2.2 допускает ровно одного
   победителя.
3. Сессия-владелец занята ходом в **другом живом** процессе (её
   session-lock удерживается) — её уведомления пропускаются до следующего
   прохода: чужой ход не получает вставку в середину. В своём процессе
   занятость не мешает — работает `injectIfBusy`.

Корректное завершение процесса (выход web-сервера с живыми задачами) —
ничего особенного не делает: задачи остаются `running`, блокировка
освобождается, следующий процесс доставит «прервано». Отдельной ветки
shutdown нет.

### 2.6 Что остаётся из первой реализации

- Схема `async_jobs`/`async_hosts` и sqlc — с правками 2.1–2.4 (удалить
  `lease_expires_at`, `heartbeat_at`, `delivered_at`; добавить `delivery`,
  `notice_message_id`, причину отмены; индексы под запросы 2.5).
  Миграция не выпущена — правится сама, не добавляется новая.
- Ack gate: сообщение «started» и `announced=1` — одна транзакция
  (`CreateWithQuerier`, `PublishCreated` после коммита).
- Идемпотентный claim по `(owner, tool_call_id)` для всех четырёх
  инструментов; повтор отвечает по состоянию строки; идемпотентный
  `CreateTaskSession`; `child_session_id` заполняется после создания
  дочерней сессии.
- Читатели между процессами (`LiveJobs`, `sessions jobs`), `sessions gc
  --jobs-older-than`: живость строки = `running` и хост жив по 2.4.
- `job_kill`: решение «остановлено» — `transition` с причиной
  `job_kill`; вывод снимается до убийства процесса; причины отмены
  различимы (`job_kill`, отмена сессии, таймаут, прерывание) — #1063.

### 2.7 Что не меняется

Фазы 1–3 и надзор: единый реестр в памяти как исполнитель, область
закрывается событием, `rush run` ждёт работу потомков, надзор не держит
область. Сигнал области («изменилось») подаёт `transition` после коммита.
`wake_only`-таймаут и надзор — советующие уведомления без строки задачи:
доставляются через `wakeSession` не более одного раза, их потеря не
теряет результат задачи.

## 3. Законы (в `docs/async-invariants.md`)

| ID | Закон |
|---|---|
| DUR-1 | Состояние задачи меняет только `transition`: одна транзакция с SQL-CAS; память — после коммита, только победитель. |
| DUR-2 | Терминальный переход и `delivery='pending'` (sync — `done`) пишутся одной транзакцией. |
| DUR-3 | Уведомление и `delivery='done'` пишутся одной транзакцией; сообщение существует ⇔ строка `done`. |
| DUR-4 | Пробуждение — сигнал после коммита доставки; его потеря не теряет факт. |
| DUR-5 | Процесс жив ⇔ удерживает ОС-блокировку своего файла хоста. Часы для решения о жизни не используются. |
| DUR-6 | Восстанавливает чужие задачи только держатель блокировки мёртвого хоста. |
| DUR-7 | «started» и `announced=1` — одна транзакция; неанонсированная задача никогда не даёт уведомления. |
| DUR-8 | БД недоступна при старте задачи — задача не запускается (fail-closed). |

## 4. Порядок реализации

Новая ветка от `main`; куски ветки `async-phase4` переносятся по мере
надобности (схема, sqlc, ack gate, claim, читатели, CLI, тесты на
реальной БД). Каждый шаг собирается и проходит тесты, коммит на шаг:

0. Схема и sqlc по 2.6.
1. Файл-блокировка хоста (2.4), регистрация, удаление при восстановлении.
2. `transition` + `delivery` (2.1, 2.2): все места перехода в
   `internal/agent` вызывают его; write-through удалить.
3. `deliver` и будильники (2.2, 2.3): web и CLI через одну доставку;
   удалить `s.ready`, `markDrained`, `ClaimAsyncCompletions`,
   `MarkAsyncCompletionDelivered`, `noticedBefore`.
4. Восстановление (2.5).
5. Claim, ack gate, повтор по состоянию строки, `job_kill`, причины отмены.
6. Читатели, `sessions jobs`, `sessions gc`; удалить
   `internal/session/descendant_liveness.go`.
7. Законы DUR-1…8 в реестр, переанкеровка ASYNC-строк, CHANGELOG.

## 5. Обязательные тесты (реальная SQLite)

- DUR-2/3: два доставщика одновременно (две горутины, два `*sql.DB` на
  один файл) — ровно одно сообщение; падение между переходом и доставкой —
  восстановление доставляет ровно одно.
- CLI: отказ хода до создания сообщения (session-lock занят другим
  процессом, shutdown) — уведомление всё равно сохранено ровно один раз.
- DUR-5: блокировка хоста у живого процесса не захватывается; после
  «смерти» (освобождение блокировки без удаления строк) — восстановление;
  при этом никаких отметок времени в решении.
- Отмена N параллельных под-агентов — N уведомлений, после выхода
  процесса и прохода восстановления — ни одного лишнего.
- Сквозной тест в `internal/app`: два экземпляра App на одном каталоге
  данных; A запускает async bash, анонсирует, «падает» (освобождает
  блокировку хоста, не вызывая close); B стартует — у владельца ровно одно
  «прервано», и оно попадает в следующий промпт B. Обратный случай: задача
  завершена и доставлена в A — B не добавляет ничего.
- `job_kill`: содержимое уведомления об остановке содержит реальный вывод,
  не «failed» и не «already finished».
