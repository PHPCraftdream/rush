# Фаза 4, редакция 7 (итоговая): долговечное ядро работы — одна правда, историю пишет только ведущий, жизнь без часов

Статус: архитектурное решение оркестратора (2026-09-28). Основание: два
раунда ревью первой реализации фазы 4 (ветка `async-phase4`, не влита,
12 P1) и три раунда ревью этого документа (ред. 1: 6 P1; ред. 2: 2 P1;
ред. 3: 3 P1 в собранном вручную «ходе-заборе» — заменён вызовом-забором
через обычный `Run`; ред. 4: 3 P1 — обязанность реагировать хранилась во
временном состоянии, теперь это долговечный «долг реакции»; ред. 5: 1 P1 —
реакция выводилась из порядка сообщений, теперь это явная отметка
`reacted`, пишущаяся вместе с шагом модели; ред. 6: вставка на границе
шага видна одному шагу — вставки середины хода переносятся на все
следующие шаги; закрытие долга неудачей уточнено. На этом ревью документа
закончено по решению оператора; дальше — реализация и ревью кода). Заменяет разделы «write-through»,
«доставка», «lease/heartbeat» и «recovery sweep» в
`docs/plans/2026-09-28-async-phase4-spec.md`; остальное переиспользуется с
правками ниже. Дизайн серии: `docs/plans/2026-09-27-async-structured-concurrency.md`,
законы: `docs/async-invariants.md`.

Поправки после ревью раунда 1 (2026-09-29) — в конце документа, раздел
«Amendments after review round 1»; текст редакции 7 ниже не менялся.

## 1. Диагноз: почему правки не сходились

Находки ревью первой реализации — следствия трёх решений:

1. **Два источника правды.** Состояние задачи жило в памяти и в SQLite; БД
   догоняла память записью вдогонку из каждого места перехода.
2. **Историю сессии писали посторонние.** Уведомления вставляли три
   механизма в произвольный момент, отметку «доставлено» ставили отдельно.
3. **Жизнь хоста по часам.** Сравнение отметок времени разных процессов.

Новая архитектура убирает все три источника. Ни одна из находок в ней
невыразима.

## 2. Понятия

- **Строка задачи** — `async_jobs`: async-задача (`bash`, `run_command`,
  `agent`, `agentic_fetch`, вызванные из CLI/web).
- **Строка уведомления** — `session_notices`: уведомление без строки
  задачи (надзор, маркер неудачного пробуждения, завершение фонового shell
  SDK-вызова, `wake_only`-таймаут).
- **Ведущий сессии** — держатель её мейлбокса **и** её OS session-lock,
  то есть идущий ход (`Run`), включая вызов-забор (3.4). Только ведущий
  пишет в историю сессии уведомления.
- **Хост** — процесс, исполняющий async-задачи; жив ⇔ держит ОС-блокировку
  своего файла (2.6).

## 3. Архитектура

### 3.1 Одна правда: `transition`

Состояние строки задачи меняет **одна функция** `transition`: транзакция с
SQL-CAS `UPDATE … WHERE owner=? AND call=? AND state='running'`, в ней же —
поля доставки (3.2).

- Победитель CAS обновляет память после коммита; проигравший читает
  строку и принимает её состояние. Память сходится к БД.
- Держатель исхода (исполнитель, отмена, таймаут, `job_kill`, `abort`)
  повторяет операцию с нарастающей паузой, пока не закоммитит или не
  увидит строку терминальной/удалённой.
- Внешняя причина действует в порядке «снимок вывода → `transition` с
  причиной → остановка исполнителя»; остановленный исполнитель
  проигрывает CAS, причина не подменяется «context canceled».
- Защёлка «переход идёт» в памяти: другие триггеры её **пропускают** (не
  ждут); держатель после коммита подаёт сигнал области.
- Защёлка shutdown проверяется **внутри** `transition`. «Вызван
  завершением процесса» ⇔ защёлка поднята **и** контекст исполнителя
  отменён самим `close()`; такие переходы подавляются, естественные
  завершения записываются. То же правило действует в `recheckChild`:
  ход ребёнка, прерванный shutdown, не считается «область ребёнка
  закрыта», и делегация не завершается усечённым текстом.

Память (`workLedger`) хранит исполнителей, функции отмены, защёлки и
сигналы и никогда не решает исход async-задачи. **Sync-задачи**
(SDK-вызовы: результат — ответ самого инструмента) в БД не пишутся и
живут по старой схеме в памяти; `wake_only` для них не применяется
(вызывающий и так ждёт); SDK-делегации не видны `sessions why/list` —
это принятое ограничение библиотечного режима.

Если БД недоступна при старте async-задачи — инструмент возвращает ошибку
и задачу не запускает (fail-closed).

### 3.2 Исходящий ящик в строке

Поля строки задачи: `delivery` = `none` | `pending` | `done` | `void`,
`notice_message_id`, `wake` (0/1), причина терминального состояния.
Терминальный `transition` в той же транзакции ставит `delivery='pending'` и
`wake` по причине (3.4). `abort` (ack-транзакция не прошла) удаляет строку
`announced=0` под тем же правилом повтора.

Строки уведомлений (`session_notices`) — тот же ящик: `owner` (внешний
ключ на `sessions` с `ON DELETE CASCADE`), вид, текст, `wake`,
`delivery`, необязательный ключ задачи для условия «задача ещё
`running`»; ретеншн — тем же проходом, что и строки задач.

### 3.3 Забор: историю пишет только ведущий, только между шагами

Ведущий забирает `pending` своей сессии (строки задач с `announced=1` и
строки уведомлений) в двух точках:

- **в начале хода — до загрузки истории для промпта;**
- **на границе шага** (`PrepareStep` обычного хода, по образцу
  `DrainPendingInjects`, с подмешиванием в текущий промпт). Шаги
  компакции не забирают.

Одна транзакция на уведомление: `UPDATE … SET delivery='done' … WHERE …
AND delivery='pending' [AND announced=1] RETURNING …` → `INSERT`
сообщения → id в строку. 0 строк → откат. Для уведомления с ключом задачи
в той же транзакции проверяется, что задача `running`, иначе оно
`void`. События UI публикуются после коммита. Ошибка забора не валит ход:
строки остаются `pending`.

Уведомление появляется в истории только между шагами. Два ведущих
невозможны (мейлбокс + session-lock); транзакция в любом случае допускает
ровно одного победителя.

Пользовательские вставки (`InjectMessage`, `sessions inject`) этим
законом не охватываются и пишут как раньше — вне объёма фазы.

### 3.4 Долг реакции и вызов-забор

**Долг реакции сессии S** — явная отметка, не вывод из порядка сообщений:
у строк задач и уведомлений есть поле `reacted`. Долг S ⇔ есть строка
(задачи с `announced=1` или уведомления) с `wake=1`, `delivery` ∈
{`pending`, `done`} и `reacted=0`.

- **Реакция записывается там, где она происходит:** когда шаг хода S
  сохраняется с реальным содержимым (текст, вызовы инструментов или
  рассуждение; завершение не error/canceled/пустое), новый метод
  хранилища одной транзакцией пишет финал шага (нынешний
  `persistStepFinish`) и `reacted=1` всем строкам S с `wake=1`,
  `reacted=0`, `delivery='done'`, перенесённым в историю до начала этого
  шага. Это **факт БД**, а не «id уведомления есть в промпте»: уведомления,
  срезанные компакцией или окном контекста, тоже отмечаются, и сессия не
  зацикливается. Пустая заготовка сообщения ассистента, неудачный шаг,
  сводка компакции реакцией не считаются; часы и порядок `created_at` не
  используются. Отметка — «не менее одного раза»: если финал шага не
  записан (fantasy отбрасывает ошибку `OnStepFinish`, досрочные выходы
  по лимиту стоимости или peak hours), долг остаётся и будет ещё один
  вызов-забор — допустимо.
- **Уведомление видно всем последующим шагам хода.** fantasy строит вход
  шага как `initialPrompt + ответы шагов`, и вставка на границе шага
  (`PrepareStep`) видна только одному шагу. Поэтому `PrepareStep` хранит
  каждую вставку середины хода (уведомления и пользовательские вставки)
  с её позицией и заново вставляет её на ту же позицию в каждом
  следующем шаге этого хода — до обрезки окна и разметки кэша. Только
  так «шаг с вызовом инструмента — реакция» верно: модель продолжает
  видеть уведомление.
- Шаг только с вызовами инструментов — реакция (модель видела
  уведомление). Посторонний ход пользователя, чей шаг сохранился с
  содержимым, — тоже реакция: уведомление было в его промпте.
- **Закрытие долга неудачей** — только после неудачного хода провайдера
  (не при отказе в допуске: session-lock занят, `ErrAgentShuttingDown`,
  `ErrSessionBusy` — долг остаётся). Временная неудача после повторов
  координатора оставляет долг и увеличивает счётчик попыток в строке;
  следующая попытка — 60-секундным проходом (web-сессии тоже в наборе
  перепроверки). После K=3 неудачных проходов, при квоте/401/402 и
  прочих невосстановимых отказах — долг закрывается: маркер неудачного
  пробуждения (`wake=0`) и `reacted=1` с причиной «ошибка». Закрытие
  пишет сам последний ход в своей ветке ошибки, ещё владея сессией, и
  только для строк, которые были `done` на момент его начала. Повторы и
  продолжения координатора сохраняют вид вызова-забора. Дочерняя сессия с
  закрытым неудачей долгом завершает делегацию как неудачную и передаёт
  родителю текст неотреагированных уведомлений; `rush run` в этом случае
  завершается с неуспешным `exit_reason`. Неудачные вызовы-заборы не
  расходуют предел автоматических ходов web.
- **Пустой промпт:** если последнее сообщение промпта не user/tool
  (например, прерванный текст ассистента), вызов-забор добавляет
  несохраняемую подсказку-сообщение пользователя; пустую строку
  пользователя в истории не создаёт никогда.
- Переносить уведомления в историю может любой держатель session-lock
  (в том числе web-вкладка, открывшая сессию `rush run`), реагирует только
  законный ведущий (ниже). Повтор хода после сбоя провайдера, забор без
  хода и слияние вызовов долг не стирают.
- Надзорное уведомление — долг, только пока в области (без учёта самого
  надзора) есть `running` строки; иначе при заборе оно `void`, а
  перенесённое — `reacted=1`.
- Проверка долга — один индексированный `EXISTS` по частичным индексам
  `(owner) WHERE wake=1 AND reacted=0 AND delivery<>'void'` на обеих
  таблицах. Политика сессии проверяется **до** подачи вызова-забора: при
  запрещённом ходе (предел, после Stop) вызов не подаётся.

**Вызов-забор** — отдельный вид `SessionAgentCall` (`Drain`), который идёт
обычным путём `Run`/`submit`:

- сессия свободна — вызов становится владельцем как любой ход (мейлбокс и
  session-lock берёт сам `runOwned`); занята — встаёт в очередь; в очереди
  сессии не больше одного вызова-забора на **любом** пути вставки (в том
  числе возврат вытесненного вызова в голову очереди); при слиянии
  побеждает более сильная политика («ход разрешён» сильнее «только
  перенести»);
- никогда не ставится в долговременную очередь: если вызов-забор оказался
  «осиротевшим» при освобождении, вместо отбрасывания выполняется новая
  проверка долга после того, как мейлбокс свободен;
- в начале хода переносит уведомления (3.3), затем решает **по долгу
  реакции**, а не по тому, что забрал сам: долга нет или политика
  запрещает ход — завершение хода **без обращения к провайдеру** через
  обычный конец хода (`drainOrReleaseMerged`, чтобы поставленные в очередь
  вызовы пользователя выполнились, а не осиротели); долг есть и ход
  разрешён — ход с **пустым промптом** (`ErrEmptyPrompt` снимается только
  для вызова-забора) и признаками `AutoResumed`/`BackgroundJobNotice`;
- вид вызова и признаки уведомления **никогда не наследуются**: вызовы,
  построенные из активного вызова (`InterruptAndReplace`, прерывание
  `sessions inject --interrupt`) или из шаблона драйвера, создаются одним
  конструктором, который их сбрасывает;
- в списке очереди (`QueuedPromptsList`) вызов-забор не показывается.

**Кто запускает вызов-забор:**

- После коммита перехода/уведомления с `wake=1` подаётся неблокирующая
  **подсказка**; у сессии — счётчик подсказок.
- **Каждое освобождение мейлбокса** (воронка `onSessionIdle`, фаза 3)
  проверяет долг реакции S по БД и при долге подаёт вызов-забор — **в
  отдельной горутине**, никогда из `defer`.
- Против холостого круга: (а) вызов-забор, завершившийся без хода,
  повторную проверку при своём освобождении пропускает, **только если**
  счётчик подсказок S не изменился с момента его проверки; пропускается
  лишь повторный запуск вызова-забора — `recheckChild` и хуки надзора на
  освобождении работают всегда; (б) session-lock S держит другой процесс
  (разделяемая проба) — S заносится в набор 60-секундной перепроверки, а
  не забывается (lock могут держать и не ведущие: `sessions
  kill/locks/reap`); (в) ошибка забора или проверки, временная ошибка провайдера в ходе
  вызова-забора — следующая попытка по подсказке или 60-секундному
  проходу, не сразу (правила закрытия долга неудачей — выше).
- **Сессии с внешним ведущим** (CLI-корень: его ведёт цикл `rush run`)
  вызов-забор с ходом не получают — только подсказку циклу. Цикл решает по
  долгу реакции корня и сам собирает итог своих ходов. Перенос
  уведомлений в его историю другим держателем lock (web-вкладкой) долг
  не стирает.

**Политика сессии «можно ли ход»:**

| Сессия | Ход по долгу реакции |
|---|---|
| дочерняя | только пока её строка делегации `running`; после Stop или завершения делегации — нет (по построению, без отдельной гонки со Stop) |
| CLI-корень | решает цикл `rush run` |
| web, уведомления async-задач и делегаций | да, как сегодня; собственный предел подряд идущих автоматических ходов (сброс по сообщению человека); после Stop — автоматические ходы приостановлены до следующего сообщения человека |
| web, фоновые shell SDK-вызовов | только при `AutoResumeOnJobDone` (как сегодня) |
| web-вкладка, открывшая сессию | только перенос уведомлений, без хода |

**Политика `wake`:**

| Источник | `wake` |
|---|---|
| естественное завершение задачи, таймаут | 1 |
| Stop, `job_kill`, прерывание (3.7) | 0 |
| надзор | 1; при заборе — `void`, если область уже закрыта |
| `wake_only`-таймаут | 1; при заборе — `void`, если задача уже не `running` |
| маркер неудачного пробуждения | 0 |
| завершение фонового shell SDK-вызова | 1 (ход — по политике сессии) |

Для `job_kill` итог — ответ самого инструмента, строка сразу `done`.
**Stop** в том же проходе ставит `wake=0` всем `pending` строкам задач и
уведомлений остановленного дерева; гонку с естественным завершением за
мгновение до Stop закрывает политика: у отменённой делегации нет права на
ход.

**Надзор и забор:** `recordProgress` (сброс отсчёта тишины) вызывается при
переносе в историю уведомлений, кроме надзорных; `pushDeadlineOnTurnEnd`
не срабатывает для вызовов-заборов без хода — открытие вкладки не
сбрасывает таймер тишины корня.

### 3.5 Область и выход `rush run` — из БД

**Область S открыта** ⇔ у S есть `running` строка задачи на **живом**
хосте, или S ведёт ход, или у S есть долг реакции и политика S разрешает
ход. Дочерняя
работа входит через строку делегации: она `running`, пока область ребёнка
не закрыта (фаза 3). Потомки по `parent_session_id` не обходятся.

В начале хода и при оценке области (не на каждом шаге) ведущий выполняет
**восстановление своей области** (3.7): строки мёртвых хостов в области →
`interrupted`. Поэтому `rush run --continue` после падения или Ctrl-C
прошлого запуска не ждёт мёртвые строки, а первым ходом получает
«прервано».

CLI-цикл: ход ⇔ долг реакции корня (или исходный запрос); выход ⇔
область корня закрыта. Лишняя или потерянная подсказка исхода не меняет.
Ошибка чтения БД при оценке — повтор с паузой, не молчаливый пропуск.

**Единственный межпроцессный запасной путь — 60-секундный проход:**
подсказки живут внутри процесса, поэтому хост раз в 60 с перепроверяет
свои припаркованные делегации и долг реакции их дочерних сессий, сессии из
набора перепроверки (3.4, правило б), а CLI-цикл, в области которого есть
строки чужого живого хоста, заново оценивает область. Других опросов в
архитектуре нет.

### 3.6 Жизнь процесса — блокировка ОС, без часов

- Хост регистрируется **лениво, при первом claim** async-задачи: случайный
  uuid, файл `<data>/hosts/<host_id>.lock`, эксклюзивная ОС-блокировка на
  всё время жизни процесса, сильная ссылка (без финализатора).
- **Мёртв ⇔ блокировку удалось захватить**, либо файла нет (ENOENT).
  «Жив» — при отказе «занято» (`EWOULDBLOCK` / `ERROR_LOCK_VIOLATION`).
  Любая другая ошибка — «неизвестно»: строки остаются, область их не
  считает открытыми только при «мёртв». Проба открывает файл без
  создания. Свой host_id и host_id других App этого процесса не
  пробуются. Файловая система без блокировок — отказ при регистрации;
  каталог данных — только локальный диск; `hosts/` руками не трогать.
- Пробовать и восстанавливать может **любой** процесс (ведущий, CLI,
  web), не только хост: захват блокировки мёртвого не требует быть хостом.
- Файл удаляет владелец при выходе, если строк не осталось; чужие —
  восстановитель, держащий блокировку, после проверки, что открытый файл
  тот же, что по пути (на Windows — закрыть, затем удалить; проигранная
  гонка оставляет лишний файл, его уберёт ретеншн).
- `async_hosts` — только для показа, без внешнего ключа из `async_jobs` и
  без отметок времени для решения о жизни.

### 3.7 Восстановление — только факты

Выполняется: ведущим для своей области (3.5); хостом — при регистрации и
раз в 60 с по всем мёртвым хостам. Для мёртвого хоста (без удержания его
блокировки, см. поправку (z)):

- `running` с `announced=1` → `transition` в `interrupted` (`wake=0`):
  для делегации — с последним сообщением ассистента дочерней сессии; для
  bash/run_command — «вывод не сохранялся; процесс мог остаться
  запущенным» (процессы не убиваются: на Windows дерево уже снято job
  object хоста, на POSIX надёжной метки группы нет);
- `running` с `announced=0` → удалить без следа (ASYNC-05);
- строк не осталось → удалить строку хоста и файл.

Хост раз в 60 с также перепроверяет свои припаркованные делегации
(`recheckChild`), дочерние задачи которых могли быть восстановлены другим
процессом. Ретеншн (этим же проходом): `done`/`void` старше порога,
файлы мёртвых хостов без строк.

Восстановление **не пишет историю и не будит сессии**; «прервано»
заберёт ведущий. Корректный выход процесса = падение: исполнители
останавливаются, переходы от отмены при shutdown подавлены, строки
остаются `running`, следующий ведущий/хост их восстановит.

### 3.8 Stop, Rerun, делегации, ASYNC-01

- **Stop транзитивен:** отмена сессии отменяет всё дерево через
  `running` строки делегаций; всем строкам — `wake=0` (ASYNC-08). Дочерние
  задачи не будят детей после Stop.
- **Rerun** (усечение истории): `running` строки удалённого хвоста
  останавливаются с семантикой `job_kill` (для делегаций — по дереву);
  терминальный `transition` сохраняет `void`
  (`CASE delivery WHEN 'void' THEN 'void' ELSE 'pending' END`); строки,
  анонсированные в удалённом хвосте, → `void`; строки, анонсированные до точки усечения, чьё
  уведомление оказалось в удалённом хвосте, → снова `pending` с
  `reacted=0` — ход после Rerun заберёт их результат заново (ASYNC-04 для
  новой ветки). Компакция строки не трогает.
- **Claim делегации** пишет `child_session_id` сразу (id детерминирован;
  внешний ключ на `sessions` для этой колонки убирается). В транзакции
  claim: сначала чтение по ключу (идемпотентный повтор); затем проверка
  частичного уникального индекса `child_session_id WHERE state='running'`
  (ASYNC-01): конфликт с мёртвым хостом → восстановить его строку в той же
  попытке; с живым → ошибка инструмента **до** «started». Это меняет
  поведение: раньше `resume_session_id` при делегации, ход ребёнка
  которой закончен, а его задачи ещё идут, вставал в очередь; теперь —
  ошибка с понятным текстом («у под-агента ещё идёт работа прошлой
  делегации; дождитесь её результата»). Отразить в CHANGELOG.
- **Ack gate:** «started» и `announced=1` — одна транзакция без условия на
  состояние; если строка уже терминальна — после коммита подсказка.
- Читатели между процессами (`LiveJobs`, `sessions jobs`): живость =
  `running` и хост жив по 3.6 (разделяемая проба).
- Итог делегации: если последнее завершённое сообщение ребёнка без
  текста (только рассуждение/вызовы), родитель получает «завершено без
  итогового ответа», а не текст, снятый при парковке делегации.
- CLI-цикл при отказе «session-lock занят» на своей сессии (вкладка web
  переносит уведомления, `sessions locks`) повторяет ход с короткой
  ограниченной паузой, а не завершает `rush run`.
- Проход ревьюера в `rush run` запускается по тому же предикату области
  из БД (3.5), а не по памяти (`HasPendingAsyncJobs`); ход ревьюера —
  обычный ход и тоже переносит уведомления.
- Индексы: `(host_id)`, `(owner_session_id) WHERE delivery='pending'`,
  `(state) WHERE state='running'`, уникальный частичный по
  `child_session_id`; для `session_notices` — `(owner) WHERE delivery='pending'`.

## 5. Порядок реализации

Новая ветка от `main`; куски ветки `async-phase4` переносятся по мере
надобности. Коммит на шаг; каждый шаг собирается и проходит тесты.

0. Схема (`async_jobs`, `async_hosts`, `session_notices`) и sqlc —
   миграция не выпущена, правится сама.
1. Хост: ленивая регистрация, блокировка, проба (3.6).
2. `transition`: повтор, защёлки, приём проигрыша, порядок внешних
   причин, shutdown-защёлка; все места перехода — через него.
3. Забор ведущим (начало хода, `PrepareStep`), строки уведомлений;
   перевести надзор, `wake_failed`, SDK bg shells, `wake_only` на
   `session_notices`; удалить `InjectMessage`-путь уведомлений,
   `s.ready`, `markDrained`, `ClaimAsyncCompletions`, `noticedBefore`.
4. Вызов-забор (`Drain` через `Run`/`submit`, слияние в очереди, без
   долговременной очереди, пустой промпт), проверка на освобождении,
   политика `wake` и сессий, CLI-цикл по БД (3.4, 3.5).
5. Восстановление: область ведущего, проход хоста, перепроверка
   делегаций, ретеншн (3.7).
6. Stop-дерево, Rerun-void, claim делегации с ASYNC-01, ack gate, повтор
   по состоянию, `job_kill` (3.8).
7. Читатели, `sessions jobs`, `sessions gc`; удалить
   `internal/session/descendant_liveness.go`.
8. Законы DUR-1…9 в реестр, переанкеровка ASYNC-строк, CHANGELOG.

## 6. Обязательные тесты (реальная SQLite, где речь о БД)

- DUR-1: `transition` при занятой БД повторяется и коммитит; проигравший
  принимает состояние; отмена/таймаут/`job_kill` дают свою причину;
  shutdown не подавляет естественное завершение.
- DUR-3: уведомление не оказывается между вызовом инструмента и его
  результатами (ход с двумя инструментами, async-задача завершается
  между ними); ведущие в двух процессах (два `*sql.DB` на файл) — одно
  сообщение; ошибка забора не валит ход; компакция не забирает.
- DUR-4: задача ребёнка завершается во время последнего шага его хода —
  на освобождении запускается вызов-забор, **ребёнок делает ход над
  уведомлением** (проверяется ход, а не только закрытие делегации),
  делегация родителя закрывается, `rush run` завершается;
  лишняя/потерянная подсказка не даёт лишнего хода; вызов-забор при
  session-lock, занятом другим процессом, и при постоянной ошибке забора
  не зацикливается (счётчик запусков ограничен); у CLI-корня вызов-забор
  не запускается, итог последнего хода цикла попадает в JSON-конверт;
  провайдер не видит уведомление дважды.
- Stop через секунду после естественного завершения задачи — нового хода
  нет.
- Маркер неудачного пробуждения при постоянно отказывающем провайдере не
  порождает цепочку ходов и маркеров.
- Долг реакции: провайдер падает после забора (пустая заготовка
  ассистента уже создана) — повтор хода всё равно обращается к провайдеру;
  провайдер отказывает и после повторов — маркер, долг закрыт неудачей,
  область закрывается; компакция над неотреагированным уведомлением долг
  не гасит; Rerun до уведомления — результат приходит в новую ветку; web-вкладка открывает сессию `rush run` и
  переносит уведомления — корень всё равно отвечает, итог в JSON; слияние
  вызова-забора «только перенести» с «ход разрешён» даёт ход.
- Осиротевший вызов-забор (строка пришла в окно освобождения) не теряет
  пробуждение; `sessions locks/kill/reap`, держащие lock в момент
  проверки, не теряют пробуждение (60-секундная перепроверка).
- Уведомление, вставленное на границе шага 3, видно шагам 4 и далее того
  же хода; ребёнок, у которого тесты упали посреди его правок, передаёт
  родителю итог с учётом падения.
- Финал шага не записан (ошибка `OnStepFinish`) — долг остаётся, ещё
  один вызов-забор, без зацикливания.
- Минутный сбой провайдера не закрывает долг; квота/401 — закрывает с
  маркером; отказ в допуске при shutdown — не закрывает.
- Rerun с живой задачей в удалённом хвосте — ни уведомления, ни хода.
- `sessions inject --interrupt` во время вызова-забора — сообщение
  оператора получает ход провайдера.
- Web без `AutoResumeOnJobDone`: завершение async-задачи будит сессию,
  как сегодня; после Stop — нет, до сообщения человека.
- Быстрая задача, завершившаяся до ack: одно уведомление, после «started».
- DUR-9: Stop сессии с N под-агентами, у которых свои bash — ни одного
  нового хода ни в одной сессии; N фактов; после перезапуска — ни одного
  лишнего.
- Rerun после Stop: уведомления об удалённых вызовах не появляются.
- ASYNC-01: `resume_session_id` при живой делегации — ошибка до
  «started»; при мёртвой — восстановление и старт; повтор того же вызова —
  идемпотентный ответ.
- DUR-5: живой хост не «мёртв» ни при какой пробе; неизвестная ошибка не
  даёт «мёртв»; процесс без задач хост не регистрирует.
- DUR-6: восстановление не создаёт сообщений и ходов.
- Сквозные в `internal/app` (два App на одном каталоге данных):
  (а) A запускает async bash, анонсирует, «падает» (освобождает
  блокировку без close); `rush run --continue` в B получает ровно одно
  «прервано» в первом промпте и завершается; (б) задача завершена и
  доставлена в A — B ничего не добавляет; (в) Ctrl-C `rush run` с живыми
  задачами — ни одного нового хода, после перезапуска — одно «прервано»
  на задачу.
- `job_kill`: итог в ответе инструмента с реальным выводом; второго
  уведомления и хода нет.

## Amendments after review round 1 (2026-09-29)

Историю выше не переписываем: ред. 7 осталась как решение оркестратора.
Раунд 1 ревью кода (`docs/reviews/2026-09-29-async-phase4-round1.md`) и его
починки отклонили реализацию от ред. 7 в перечисленных ниже местах; каждое
отклонение проверено по коду, а не по отчётам. Где сказано «не реализовано» —
это именно так.

**(a) Закрытие долга неудачей пишется после освобождения мейлбокса, а не
«ещё владея сессией» (3.4).** *(учёт попыток и место записи заменены (m): ведёт цикл хода, а не `wakeSession`.)* `wakeSession` вызывает `recordDrainOutcome` после
возврата `agent.Run`, то есть после `onSessionIdle`. Это безопасно, потому что
закрытие ограничено строками `reacted=0` из снимка, снятого до хода, а снимок
содержит только строки `delivery='done'` (`CaptureDebtSnapshot`; анонсированные
для задач): запоздавшее закрытие не может задеть ни реакцию, случившуюся позже,
ни строку, пришедшую после снимка. (Раунд 2, R2A-4/R2A-5: снимок называет строку
по `claim_id` и `notice_message_id`, а счётчик, `MaxWakeAttempts` и закрытие
действуют на неё, только пока она та же — `delivery='done'`, то же сообщение,
`wake=1`, `reacted=0`; раньше текстовое совпадение `tool_call_id` могло задеть
новую строку под переиспользованным id, а Rerun-repend с повторным pull — закрыть
строку, которую модель в этом виде не видела.) Закрытие и маркер `wake_failed` — одна
транзакция (`SettleReactedFailedWithMarker`), маркер пишется, только если что-то
реально закрыто. Причина изменения: «ещё владея сессией» не выражалось без
удержания мейлбокса на время записи, а снимок из `pending` строк закрывал долг,
которого модель не видела (C18/B-dev1).

**(b) Web-вызовы-заборы не идут через повторы и продолжения координатора
(3.4 «после повторов координатора»).** *(счёт, ограничение попыток и повторы заменены (m): один пункт учёта и один гейт запуска.)* `wakeSession` вызывает `agent.Run`
напрямую; компакция внутри хода сохраняет вид вызова-забора
(`drainTurnCommitted`), но повторов `coordinator.Run` нет. Ограничение попыток
даёт: (1) правило (а) распространено на освобождение неудавшегося вызова-забора
(маркер «без хода» + набор перепроверки; немедленного перезапуска нет); (2) набор
перепроверки и 60-секундный проход (только в web-процессе; пробуждения набора
идут отсоединённо — по одному на сессию, не больше четырёх одновременно — и проход
их не ждёт: медленный ход не задерживает обход мёртвых хостов, ретеншн и
перепроверку делегаций следующего тика); (3) счётчик
`wake_attempts` строк снимка, общий для неудачи и для «успех, но реакция не
записана» (`checkStuckDrainProgress`): после K=3 долг закрывается. Отказ в
допуске (session-lock у другого процесса, shutdown) долг не трогает и уводит
сессию в набор перепроверки; отмена, дедлайн, Stop, вопрос агента и не
провайдерские ошибки не считаются неудачей попытки и ничего не закрывают.
Освобождение по такому отказу (B2) тоже не запускает немедленную перепроверку.
Проверка долга на освобождении ограничена 30 с только на чтение; сам вызов-забор
идёт на отсоединённом контексте (B1).

**(c) Предел автоходов web относится только к автовозобновлению по фоновым
shell SDK-вызовов (`AutoResumeOnJobDone`) (таблица политик 3.4).** *(двойной счёт предела заменён (m): один раз при допуске, `claimAutoResume`.)* Пробуждения
async-задач, делегаций, надзора и `wake_only` не ограничены, как и до фазы 4;
промежуточная реализация ограничивала и их (регрессия B7). Состояний два, оба на
сессию: счётчик предела (только автовозобновление по фоновым shell) и
приостановка Stop (`suspendAutoResume`, отдельное состояние `autoTurnsSuspended`),
которая гасит автоходы всех видов до следующего сообщения человека; сообщение
человека (`ResetAutoResumeCounter`) сбрасывает оба. Раньше Stop «ставил счётчик
на предел», и поэтому 5 автовозобновлений по фоновым shell паузили и async-пробуждения
— это исправлено разделением. Предел тратится один раз, при допуске запуска по факту (`claimAutoResume`), независимо от того, дошёл ли вызов-забор до провайдера. *(Снято (x), п. 6: предел считает отправки при допуске, а перепроверка сравнивает его, не тратя.)*

**(d) Политика дочерней сессии ключуется на строке делегации родителя, а не
на «пока строка делегации `running`» (таблица политик).** Без бегущей
делегации `wakeSession` отказывает сессии, для которой существует строка
`async_jobs` ЛЮБОГО вида (`agent`, `agentic_fetch`, …) у её `ParentSessionID` с
этой сессией в `child_session_id` (`isDurableDelegationChild`; долговечно; ретеншн не удаляет строку делегации,
пока у её ребёнка есть running-строка или неотреагированный долг — R2A-10); иначе освобождённый или истёкший ребёнок получал ход на
корневом агенте (`agentFor` возвращал `currentAgent`; B3/C6). Сессии из
`sessions fork --child` тоже ставят `ParentSessionID`, но строки делегации не
имеют — их политика прежняя. Освобождение делегации теперь требует `ScopeOpen`
ребёнка (running-строка на живом хосте или долг), а не только память процесса.

**(e) Долговечный маркер внешнего ведущего и хост у `rush run` (3.4, 3.6).**
Таблица `session_drivers` (миграция `20260929000004`) хранит `session_id →
host_id`; ведущий жив ⇔ жив хост (DUR-5). Пока он жив, другие процессы не
запускают ход реакции (`sessionDrainPolicy`); допущенный вызов-забор лишь
переносит уведомления. Чтобы у `rush run` был хост, он регистрируется при
занятии маркера (`ClaimSessionDriver` → `ensureHost`), даже если задач нет — это
изменяет «процесс без задач хост не регистрирует» (3.6): так остаётся для всех
процессов, кроме занявших сессию. Второй `rush run` на такой сессии получает
`*ErrSessionDrivenElsewhere` до хода и до записи в сессию (разовый
`RunMaintenanceSweep` и регистрация хоста к этому моменту уже выполнены: отказавший
запуск оставляет зарегистрированный хост до своего выхода). Маркер удаляется при
выходе цикла (`defer` цикла `rush run`, до `Shutdown`) и `Close`; при
принудительном завершении App остаётся только маркер, который цикл к тому моменту
не снял (случай встраивающего процесса), до конца процесса. Закон — DUR-10. Причина: маркер в памяти процесса не защищал CLI-корень от web-процесса
(C7).

**(f) Rerun: одна транзакция, `announce_message_id`, void маркера
`wake_failed`, `CancelTurn` вместо полного Stop (3.8).** `session.TruncateForRerun`
удаляет цель и хвост и сверяет реестр по строкам, реально удалённым этой же
транзакцией; любая ошибка откатывает всё, отмена до точки коммита ничего не
меняет. Void идёт по `announce_message_id` (миграция `20260929000003`; заполняет
`AnnounceStarted`), а не по `tool_call_id`, который провайдер может переиспользовать
(B14); для строк без него остаётся старая ветка по `tool_call_id`. Доставленный
маркер `wake_failed` из хвоста получает `void` (он описывал удалённую ветку), остальные
уведомления снова `pending`. Ведущий `Cancel` заменён на `CancelTurn`: полный Stop
останавливал и задачи сохранённой истории и приостанавливал автоходы, что
противоречит §6 «Rerun до уведомления — результат приходит в новую ветку»;
останавливаются только задачи удалённого хвоста (`StopRerunJobs`, после
коммита; чужой хост не останавливается — его завершение запишется как `void`). Остановленная так строка записывается как остановка сессией (Stop), не как `job_kill`: `cancelled`, `notice_kind=session_cancel`, `wake=0`, `delivery` остаётся `void` (R2B-20).

**(g) Ретеншн и глубина Rerun (3.7).** Ретеншн никогда не удаляет невыполненный
долг: `delivery IN ('done','void')` и `NOT (delivery='done' AND wake=1 AND
reacted=0)`; `pending` не удаляется вовсе; `sessions gc --jobs-older-than`
отвергает возраст <= 0 (A5). Ретеншн не удаляет и строку `job_kill` со `delivery='done'` без `notice_message_id`: её чинит восстановление мёртвого хоста (повторное ожидание), удалённой строке чинить нечего (R5A-1, см. (ac)). Следствие для Rerun: он достаёт назад ровно
настолько, насколько ретеншн хранит доставленные строки (7 суток); дальше
результат удалённого хвоста в новую ветку не вернётся.

**(h) Повторное использование `tool_call_id` (3.1/3.8).** Ключ
`(owner, tool_call_id)` не переживает задачу: строка, у которой `state !=
'running'` и `delivery` — `done`/`void`, при повторном id переименовывается в
`<id>#reused#<uuid>` и создаётся новая строка (`ArchiveAsyncJobToolCallID`);
терминальная, анонсированная, но ещё недоставленная строка (`delivery='pending', announced=1`) переименовывается так же (R2A-6: её
уведомление доставится владельцу под id, который видела модель, а повторный
вызов не получает ложный отказ); ключ удерживает только терминальная
строка, чьё «started» ещё не записано (`announced=0`). `Claim` на уровне
хранилища отвечает ей идемпотентно (`Existing`), но `workLedger.Start` для
такой строки без задачи в памяти возвращает ошибку инструмента: «was already
started earlier; not starting it again» (тот же вход) или «is already in use by
an unfinished call with different input» (другой вход; до раунда 3 текст был
«already running with different input» и ложно называл завершённую строку
идущей). Второй исполнитель не запускается. Результат `job_kill` привязан к
убитой строке по её `claim_id`, а не по `tool_call_id` (R3A-2): повторный
`call_0` во время работы `job_kill` архивирует только что убитую строку.
Архивная строка остаётся достижимой по `notice_message_id`/`announce_message_id`
для Rerun. Причина: провайдер, нумерующий вызовы по ответу (`call_0`), иначе
получал отказ на 7 суток (B14/A14b).

**(i) Надзор: половина «перенесённое → `reacted=1`, когда область закрылась»
(3.4) НЕ реализована.** Реализован только `void` при переносе
(`sessionNoticeVoidCondition`: строки `running` на заведомо мёртвых хостах в
область не входят). Надзорное уведомление, перенесённое, пока область была
открыта, остаётся `wake=1, reacted=0`, и если область закрылась до реакции,
получит один настоящий ход реакции над устаревшим «check-in». Это приемлемо, а не
задумано: последствие — не более одного лишнего хода, без зависания и потери
(следующий шаг ставит `reacted=1` обычным путём). Если оператору нужна
«тихая» половина, это отдельная маленькая работа: писать `reacted=1` надзорным
строкам в момент закрытия области.

**(j) `ScopeOpen` решает по `HostNotDead`, которая отвечает через `HostLiveness`
(разделяемая, не захватывающая проба `ProbeHostShared`, как у остальных читателей)
(3.5/3.6).** *(`ScopeOpen` заменён (m): ответ области даёт `CLIScope`.)* Раньше здесь стояла эксклюзивная `ProbeHost`: одновременный читатель
с разделяемой блокировкой давал «жив» на одну оценку. Теперь чисто читающий вопрос
никогда не претендует на блокировку; эксклюзивную пробу сохраняют только пути
восстановления, которым блокировку нужно ВЫИГРАТЬ. Также `ScopeOpen` НЕ проверяет «идёт ход» (вызывается
только между ходами) и НЕ спрашивает политику сессии: долг, на который политика
запретила бы ход, всё равно держит область открытой — это осознанно для
делегации (`childScopeDrained`: пока строка делегации бежит, политика ход
разрешает) и для гейта ревьюера. Цикл CLI `ScopeOpen` не использует, см. (l).

**(k) `async_hosts.label` — `"app"`, а не `'cli'|'web'` (3.6, схема).** Один
`App` ведёт и `rush run`, и web-сервер и не знает при создании, кто он;
значение только для показа в `sessions jobs`. Комментарий в миграции
`20260928000002` с `'cli'|'web'` устарел, миграцию (уже выпущенную) не правим.

**(l) Цикл `rush run` решает «нужен ли ход» той же политикой, что и wake (3.4/3.5).** *(предикат заменён (m): `drainPermitted` = политика, затем гейт; состояния `Owed/Paced/Deferred/Stuck`.)*
Раньше цикл считал «ход нужен» по долгу с `pending` без политики, а
`sessionDrainPolicy` (долг только из `bg_shell_done` при выключенном
`AutoResumeOnJobDone`, освобождённый ребёнок делегации, живой чужой ведущий,
приостановка Stop) ход запрещала: каждый Drain был «без хода», долг не гас, цикл
перечитывал область каждые 5 с до `--timeout`. Теперь цикл вызывает
`coordinator.CLIScope`: строки `running` читаются ПЕРВЫМИ (терминальный переход и
долг фиксируются атомарно, поэтому «не running» гарантирует, что следующее
чтение долга его видит), затем долг с `pending` делится политикой на
`TurnOwed` (ход разрешён — выполнить), `WorkOpen` (есть бегущая работа — ждать) и
`DeferredDebt` (политика ход не разрешит). Отложенный долг цикл не ждёт и не
закрывает: без бегущей работы цикл завершается, уведомление остаётся до
следующего хода человека, причина выхода не меняется, в stderr одна строка.
Ошибка чтения политики (раунд 2, (m)): закрыта для всех — `CLIScope` возвращает ошибку чтения, цикл повторяет её с паузой, а `drainPolicy` не разрешает ход (fail-closed, как и `decideDrainTurn`).

**(m) Раунд 2, «попытки» (2026-09-30): один пункт учёта и один гейт запуска (заменяет (a), (b), (c) в части счёта попыток и предиката, (j) и (l) в части `ScopeOpen`).** Решение: `docs/reviews/2026-09-30-async-phase4-round2-attempts-design.md`. Раньше попытки вызова-забора считали, ограничивали и повторяли разбросанные эвристики (маркеры «без хода»/«отказ в допуске», зонд общей блокировки, псевдо-идентификаторы, двойной счёт предела автоходов, разные предикаты у цикла CLI, освобождения и `wakeSession`), и ни одна не покрывала все исходы (пустой ответ давал горячий цикл, остановка по watchdog повторялась вечно, отказ считался попыткой). Теперь:

1. **Учёт — один раз на ногу вызова-забора, в цикле хода, который эту ногу выполнил** (`sessionAgent.closeDrainAttempt` → `coordinator.accountDrainAttempt`, `internal/agent/drain_attempt.go`), после конца ноги и до освобождения мейлбокса, по вердикту БД над строками снимка, взятого ПОСЛЕ собственного переноса вызова. Запускающие (`wakeSession`, хук освобождения, проход перепроверки, цикл CLI) ничего не считают. Считается нога, дошедшая до провайдера (`agent.Stream` вызван): счётчик `wake_attempts` на строках снимка; 0 непрореагированных — сброс гейта; K=3 или терминальный класс провайдера с первой попытки — закрытие неудачей (`settleDrainDebt`, маркер `wake_failed`); иначе гейт задерживается. Не считаются: чистая отмена/дедлайн (`drainAttemptExempt`), отказ до провайдера (`noteDrainRefused`), вопрос агента (это реакция), пользовательский ход из очереди. Остановка по watchdog и обрыв по `--max-tokens`/`--max-cost` приходят как `context.Canceled`, но это настоящие оплаченные попытки (`drainAttempt.stalled`/`capAbort`).
2. **Запуск — один предикат `drainPermitted`** (`coordinator_drain_policy.go`): политика `drainPolicy` (порядок и закрытое по ошибке чтения поведение: чужой ведущий → rerun → приостановка → делегация → bg-shell), затем гейт `drainGate` сессии (`work_ledger_reaction.go`: открыт, если не задерживался, либо пришёл более новый факт (кроме исхода «оплаченная неудача»: после неё факт не сокращает и не перезапускает паузу), либо серия непрореагированных исходов < 3 и прошло `drainRetryAfterFailure` = 60 с). Три непрореагированных исхода при неудавшемся закрытии — гейт спит до сообщения человека (`resetConsecutiveResume`; новый факт открывает его, только если последний исход не был оплаченной неудачей), одна строка Warn. *(Уточнено (x), п. 4–5: два независимых счётчика сна — у оплаченных попыток новый факт гейт НЕ открывает, только сообщение человека; закрываются лишь строки со своими K попытками.)* Хук освобождения запускает `go afterRelease` и не блокирует освобождающую горутину. Предел автоходов web (5) считается один раз при допуске (`claimAutoResume`).
3. **Вызов-забор — одна попытка провайдера в `runInternal`** (без цикла повторов/продолжений и без круга перестройки при 401); отказ до агента типизирован (`DrainNotAttemptedError`) и задерживает гейт. Повторы CLI-забора координатором отсутствуют осознанно (в web их не было); повторы внутри шага остаются у fantasy.
4. **Реакция пишется до проверок пределов** (`persistStepFinish` раньше `enforceRunawayCaps`/`recheckPeakHours`): шаг, пересёкший предел, всё равно записан. Вопрос `ask_question` в ходе-заборе — реакция (`persistFailureFinish`), он приостанавливает автоходы до сообщения человека; вопрос дочерней сессии доходит до родителя результатом делегации (`subAgentQuestionFromFinish`).
5. **CLI:** `CLIScope` отдаёт `WorkOpen` и `DrainState` (`Owed/Paced/Deferred/Stuck`) из того же `drainPermitted`; цикл `rush run` (`cliLoop`, `internal/app/app_run_async.go`) ничего не считает: `Owed` — запуск, `Paced` — ожидание гейта, `Deferred`/`Stuck` без бегущей работы — выход (Stuck — ошибка со строкой в stderr); итерации-забор без мутаций (`RunRequest.drainTurn`); лимит `--max-cost/--max-tokens` проверяется перед каждым забором и после него; 60-секундный проход перепроверки запускается и в `rush run` (`ClaimExternalDriver`), поэтому упавший ход реакции дочерней сессии повторяется и в CLI. Автоматический проход ревьюера (`reviewerPassBlocked`, для вызывающих без цикла) блокируют только бегущая работа и долг `Owed/Paced/Stuck`; в цикле `rush run` он идёт один раз при выходе из закрытой области, обычным ходом (`RunRequest.reviewerTurn`), на итоговом тексте, а не внутри хода-забора. Итерации-забор не пишут сессию: ни промпт, ни `reasoning effort`, ни слоты моделей, ни флаг отмены, ни бюджет, ни `ended_reason`; первый ход, упавший до запуска, завершает прогон своей ошибкой; забор, успевший зафиксироваться перед Ctrl-C, сохраняет свой ответ.
6. **Дочерняя сессия:** `childScopeDrained` читает тот же `CLIScope`: делегация открыта, пока у ребёнка есть бегущая работа или долг, который он должен/повторяет (`Owed/Paced`); отложенный (вопрос, Stop, чужой ведущий) и зависший (`Stuck`) долг освобождает её. Сессия, которую ведёт свой цикл `rush run`, не считается «бывшим дочерним» для политики.
7. **Rerun** держит автоходы сессии (`HoldAutomaticTurns`, `coordinator_turn_hold.go`) от отмены текущего хода до передачи резервации новому ходу (освобождение идемпотентно, в том числе на любом раннем выходе), а `StopRerunJobs` идёт из отсоединённой горутины и не держит резервацию.

Ограничения, принятые осознанно: приостановка автоходов и темп гейта живут в памяти процесса (как Stop): перезапуск web их снимает; при двух web-процессах на одном каталоге данных темп у каждого свой, а K=3 (`wake_attempts`) долговечен и общий; зависшие (`Stuck`) строки остаются `pending` и видны в `sessions why`. Половина надзора из (i) по-прежнему не реализована.

**Также (сверено по коду).**

- *CLI и 60-секундный проход (3.5, 3.7; изменено (m)).* Тикер стартует при
  `SetPersistentMode(true)` (web) и, с раунда 2, при `ClaimExternalDriver` (`rush run`;
  останавливается при завершении процесса, `CancelAll`): полный проход (обход мёртвых хостов,

  выполняет `RunMaintenanceSweep`; свою область он перечитывает из БД сам, не

- *Закрытие неудачей ограничено и снимается (A1).* `reacted_failed` сбрасывается

- *Принудительное завершение (3.6/3.7).* `CloseKeepLock` держит блокировку
  хоста и маркеры до конца процесса (A12) и позже не отпускает: зависшие

  общего сигнала завершения, поэтому безопасной точки для освобождения нет

2. **Откуда id.** `persistBGShellCompletion` берёт id из вставки (`AsyncJobStore.InsertSessionNoticeReturningID`, `RETURNING *` уже был в запросе) и передаёт его в `claimAutoResume(sessionID, rowID)`. Неудачная вставка даёт id 0: слот решается, как раньше, но в множество ничего не попадает — строки нет, откладывать нечего. Вставка и решение о слоте по-прежнему один шаг под `bgArrival`.
3. **Чтение долга.** `AsyncJobStore.PendingInclusiveDebtRows` (тот же охват, что у `PendingInclusiveDebtSummary`: wake=1, reacted=0, delivery<>'void', announced для строк задач) отдаёт id и вид строк-уведомлений. `bgShellCapDeferred` держит `bgArrival` на время этого чтения и чтения множества: завершение видно целиком или совсем не видно. Недоступность чтения или замка — ошибка, `drainPolicy` отказывает закрыто (как в (aa).3).
4. **Жизненный цикл и рост.** Множество очищается сообщением человека (`resetConsecutiveResume`), освобождается вместе с удалённой сессией (`sweepDeletedSessionState`), теряется при рестарте web (в памяти). Id, которые вышли из долга (строка отреакцирована, закрыта по K=3, void), сбрасываются при каждой проверке (`bgShellCapDeferred`, по ПОЛНОМУ списку строк-уведомлений долга: частичный список забыл бы ещё ждущую строку) и при каждом завершении (`pruneBGShellOverCap`, когда множество не пусто), поэтому множество следует за долгом и не растёт с каждым завершением. Отложить строку, которой уже нет, нельзя: id AUTOINCREMENT не переиспользуется, а решение смотрит только на строки долга. Строка, вернувшаяся в долг после сброса (`RependSessionNoticesByMessageIDs`, Rerun), идёт вместе со сбросом сообщением человека (Rerun вызывает `ResetAutoResumeCounter`). Рестарт: предел снова взведён, множество пусто, строки остаются долгом и идут обычным путём (гейт, K=3), как любой долг.
5. **Проверка на старте хода (R5B-1).** `decideDrainTurn` вызывает `drainPermitted(spent=false)`: поставленный в очередь Drain решает по долгу, которого его решение о запуске не видело (вариант A: завершение сверх предела, пришедшее после последнего пулла Drain пятого слота; вариант B: перепроверка, поставившая Dq за D5, которая владеет слотом). Безопасность в обе стороны: строка слота, которой владеет Drain, не в множестве, поэтому его долг (собственная ещё не отреакцированная строка слота) не откладывается и последний Drain не отказывает сам себе за слот, который держит; после реакции остаётся только строка сверх предела, и Drain в очереди не доходит до провайдера. Drain, поставленный за Drain четвёртого слота для строки пятого, идёт (строка пятого — строка слота). `spent=true` остаётся только у собственного запуска факта (`wakeSession(fact=true)`): слот уже потрачен, сравнивать нечего.
6. **(aa).5 закрыто.** Остаток «пулл не вышел для одной старой строки, пока новые строки забраны и отреакцированы, а сверх предела уже была строка» исчез: старая строка со слотом не в множестве, новая отреакцированная строка из долга ушла и из множества, поэтому перепроверка повторяет старую строку и закрывает её по K=3 (`TestBGShellCap_SlotRowWhosePullFailedIsRetriedBehindAReactedOverCapRow`).
