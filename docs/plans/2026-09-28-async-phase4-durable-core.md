## 1. Диагноз: почему правки не сходились

Находки ревью — следствия трёх решений:

1. **Два источника правды.** Состояние задачи жило в памяти и в SQLite; БД
   догоняла память записью вдогонку.
2. **Историю сессии писали посторонние.** Уведомления вставляли три
   механизма в произвольный момент.
3. **Жизнь хоста по часам.** Сравнение отметок времени разных процессов.

Новая архитектура убирает все три источника: решение живёт в одном месте
(`transition` — для состояния; арбитр — для «давать ли ход»; классификатор —
для «жива ли сессия»; запрос по дереву — для стоимости), история пишется
одним механизмом, жизнь доказывается блокировкой ОС, а не часами.

## 2. Понятия

- **Строка задачи** — `async_jobs`: async-задача (`bash`, `run_command`,
  `agent`, `agentic_fetch`, `bg_shell`, вызванные из CLI/web).
- **Строка уведомления** — `session_notices`: уведомление без строки задачи
  (надзор, маркер неудачного пробуждения, `wake_only`-таймаут,
  `wake_fired`, `child_question`).
- **Ведущий сессии** — держатель её мейлбокса **и** её OS session-lock, то
  есть идущий ход (`Run`), включая вызов-забор (3.3). Только ведущий пишет
  в историю сессии уведомления.
- **Хост** — процесс, исполняющий async-задачи; жив ⇔ держит ОС-блокировку
  своего файла (3.6).
- **Арбитр хода** — единственный решатель «давать ли этой сессии ход и как
  считать попытку»: чистая `decide` над снимком `readTurnFacts` (3.9).
- **Область сессии** — «незавершённая работа открыта»: running-строка на
  живом хосте, идущий ход, разовое wake-расписание или неотреагированный
  долг (ASYNC-02).

## 3. Архитектура

### 3.1 Одна правда: `transition`

Состояние строки задачи меняет **одна функция** `transition`:
транзакция с SQL-CAS `UPDATE … WHERE state='running' AND claim_id=?`, в ней
же — поля доставки (3.2). Единственный вызывающий хранилища —
`workLedger.transition`/`commitTransition`
(`internal/agent/work_ledger_transition.go`).

- Победитель CAS обновляет память из **закоммиченной** строки; проигравший
  читает строку и принимает её состояние. Память сходится к БД, никогда не
  решает исход независимо. Повтор — с нарастающей паузой, до коммита или до
  «строка терминальна/удалена».
- `claim_id` в предикате CAS закрывает ABA «удалили-и-перевзяли» на уровне
  БД; внутрипроцессную половину (abort до ack, повторный Start с тем же
  `tool_call_id`, поздний финиш первого исполнителя) закрывает **личность
  исполнителя**: `finish`, `armDelegation`, `commitTransition`, `setShellID`
  принимают `*asyncJob` исполнителя и игнорируют задачу, которая больше не
  запись своего ключа (бывшая поправка (y)).
- Внешняя причина действует в порядке «снимок вывода → `transition` с
  причиной → остановка исполнителя»; остановленный исполнитель проигрывает
  CAS, причина не подменяется «context canceled». Причину, состояние и
  тройку delivery/wake/reacted считает `causeStateNoticeKindWake` **до**
  вызова — весь терминальный исход пишется одним UPDATE (DUR-2).
- Защёлка «переход идёт» в памяти: другие триггеры её пропускают (не ждут);
  держатель после коммита подаёт сигнал области.
- Защёлка shutdown проверяется внутри `transition`. «Вызван завершением
  процесса» ⇔ защёлка поднята **и** контекст исполнителя отменён самим
  `close()`; такие переходы подавляются (строка остаётся `running` для
  следующего хоста), естественные завершения с вернувшимся исполнителем
  записываются. То же правило в `recheckChild`: ход ребёнка, прерванный
  shutdown, не считается «область ребёнка закрыта», делегация не
  завершается усечённым текстом.
- **Sync-задачи** (SDK-вызовы: результат — ответ самого инструмента) в БД
  не пишутся и живут в памяти. Их `terminate_and_wake`-таймаут завершает их
  в памяти (`transitionSync`, общий с `job_kill`) текстом «timed out after
  Ns and was stopped» с частичным выводом — не «context canceled»
  исполнителя. SDK-делегации не видны `sessions why/list` — принятое
  ограничение библиотечного режима.
- **Окно немедленного ответа (A14):** короткая (до 3 с) CLI/web-задача,
  естественно завершившаяся внутри окна, доставляется **в самом tool
  result** (`async:false, inline:true`): Tx2 `AnnounceInlineResult`
  закрывает `announced=1`, `announce_message_id` и `delivery='done'`
  (четвёртый писатель `reacted=1`) одной транзакцией. События в окне
  («started», ошибка запуска) идут обычным путём; после Tx2 открытой работы
  и долга по этой задаче не существует.

Память (`workLedger`) хранит исполнителей, функции отмены, защёлки и
сигналы и никогда не решает исход async-задачи. Если БД недоступна при
старте async-задачи — инструмент возвращает ошибку и задачу не запускает
(fail-closed; DUR-8). Отказ лимита задач (3.12, ASYNC-12) тоже происходит до
Claim и строки не создаёт.

### 3.2 Исходящий ящик в строке

Поля строки задачи: `delivery` = `none` | `pending` | `done` | `void`,
`notice_message_id`, `announce_message_id`, `wake` (0/1), `reacted`,
`reacted_failed`, `wake_attempts`, причина терминального состояния.
Терминальный `transition` в той же транзакции ставит `delivery='pending'` и
`wake` по причине (3.4). `abort` (ack-транзакция не прошла) удаляет строку
`announced=0` под тем же правилом повтора.

Строки уведомлений (`session_notices`) — тот же ящик: `owner` (внешний
ключ на `sessions` с `ON DELETE CASCADE`), вид (`notice_kind`), текст,
`wake`, `delivery`, `reacted`, необязательный ключ задачи (`job_tool_call_id`)
для условия «задача ещё `running`». Ретеншн — тем же проходом, что и строки
задач (3.7). Ещё один источник строк — фоновый shell (3.10).

### 3.3 Забор: историю пишет только ведущий, только между шагами

Ведущий забирает `pending` своей сессии (строки задач с `announced=1` и
строки уведомлений) в двух точках:

- **в начале хода — до загрузки истории для промпта;**
- **на границе шага** (`PrepareStep` обычного хода, с подмешиванием в
  текущий промпт). Шаги компакции не забирают.

Одна транзакция на уведомление: `UPDATE … SET delivery='done' … WHERE …
AND delivery='pending' [AND announced=1] RETURNING …` → `INSERT` сообщения →
id в строку (`notice_message_id`, DUR-11). 0 строк → откат. Для уведомления
с ключом задачи в той же транзакции проверяется, что задача `running`, иначе
оно `void` (то же условие у `wake_only`-таймаута; у надзора — `running`
строки на заведомо мёртвых хостах в область не входят). События UI
публикуются после коммита. Ошибка забора не валит ход: строки остаются
`pending`.

Уведомление появляется в истории только между шагами. Два ведущих
невозможны (мейлбокс + session-lock); транзакция в любом случае допускает
ровно одного победителя. **Уведомление видно всем последующим шагам хода:**
`PrepareStep` хранит каждую вставку середины хода (уведомления и
пользовательские вставки) с её позицией и заново вставляет её на ту же
позицию в каждом следующем шаге этого хода — до обрезки окна и разметки
кэша. Пользовательская вставка, чьё сообщение уже в истории, в промпт второй
раз не вставляется (ровно один раз, как у мейлбокса). Пользовательские
вставки (`InjectMessage`) этим законом в остальном не охватываются.

**Виды уведомлений** (таблица wake — 3.4): завершение задачи/таймаут, Stop
(`session_cancel`), `job_kill`, надзор (`check_in`), `wake_only`-таймаут,
маркер неудачного пробуждения (`wake_failed`), завершение фонового shell
(`bg_shell_done`), сработавшее расписание (`wake_fired`, стадия 4c), и —
**`child_question`** (#1157): вопрос делегированного ребёнка, заданный
`ask_question` при открытой области. Механика та же: ребёнок приостанавливает
делегацию (hold), родителю вставляется `child_question` (`wake=1`, ключ —
строка делегации); забор делегации с вопросом — прогресс; ответ идёт **в ту
же удерживаемую делегацию** (`resume_session_id` ребёнка перехватывается до
Claim, строки не создаётся, индекс ASYNC-01 не трогается); осушение задач
ребёнка отпускает делегацию с вопросом, если ответа не было — такое
уведомление `void` (как `wake_only`), если строка делегации уже терминальна.

### 3.4 Долг реакции и вызов-забор

**Долг реакции сессии S** — явная отметка, не вывод из порядка сообщений.
Долг S ⇔ есть строка (задачи с `announced=1` или уведомления) с `wake=1`,
`delivery` ∈ {`pending`, `done`} и `reacted=0`. Проверка — индексированный
`EXISTS` по частичным индексам `(owner) WHERE wake=1 AND reacted=0 AND
delivery<>'void'` на обеих таблицах (`ReactionDebtExists`,
pending-включающий; `VisibleReactionDebtExists` — только `done`, для
`sessions why`).

- **Реакция записывается там, где она происходит:** когда шаг хода S
  сохраняется с реальным содержимым (текст, вызовы инструментов или
  рассуждение; завершение не error/canceled/пустое), `persistStepFinish`
  одной транзакцией пишет финал шага и `reacted=1` всем строкам S с
  `wake=1`, `reacted=0`, `delivery='done'`, перенесённым в историю до начала
  этого шага. Это **факт БД**, а не «уведомление было в промпте»: срезанные
  компакцией уведомления тоже отмечаются. Пустая заготовка ассистента,
  неудачный шаг, сводка компакции реакцией не считаются; часы и
  `created_at` не используются. Отметка — «не менее одного раза»: если финал
  шага не записан (ошибка `OnStepFinish`, досрочный выход по лимиту), долг
  остаётся — будет ещё один вызов-забор, допустимо. **Реакция пишется до
  проверок пределов** (`persistStepFinish` раньше `enforceRunawayCaps`/
  `recheckPeakHours`): шаг, пересёкший предел, всё равно записан.
- Шаг только с вызовами инструментов — реакция. Посторонний ход
  пользователя, чей шаг сохранился с содержимым, — тоже реакция.
  Вопрос `ask_question` в ходе-заборе — реакция; он приостанавливает
  автоходы до сообщения человека.
- **Закрытие долга неудачей** — только по попыткам, дошедшим до провайдера
  (учёт — 3.9); отказ в допуске (session-lock занят, shutdown, чужой
  ведущий) долг не трогает. Каждая строка снапшота закрывается **своими**
  K=3 попытками (`wake_attempts` — долговечен и общий для процессов);
  терминальный класс провайдера (квота, 402, прочие 4xx, 401 без
  возможности обновить токен/ключ) закрывает весь снимок с первой попытки;
  переполнение контекста (флаг провайдера, 413 или 400 с сообщением о
  переполнении) даёт маркер с причиной и средством (сжать историю или
  начать новую сессию) вместо «продолжение при следующем ходе». Закрытие и
  маркер `wake_failed` — одна транзакция (`SettleReactedFailedWithMarker`),
  маркер пишется, только если реально закрыто хоть что-то. `reacted_failed`
  сбрасывается реальной реакцией, новой делегацией на ребёнка и повторной
  постановкой строки Rerun. Дочерняя сессия с закрытым неудачей долгом
  завершает делегацию как неудачную и передаёт родителю текст
  неотреагированных уведомлений; `rush run` завершается с неуспешным
  `exit_reason`. Неудачные вызовы-заборы не расходуют предел автоходов web
  и не считаются неудачей запуска.
- **Пустой промпт:** если последнее сообщение промпта не user/tool,
  вызов-забор добавляет несохраняемую подсказку-сообщение пользователя;
  пустую строку пользователя в истории не создаёт никогда.
- Переносить уведомления в историю может любой держатель session-lock
  (в том числе web-вкладка), реагирует только законный ведущий. Повтор хода
  после сбоя провайдера, забор без хода и слияние вызовов долг не стирают.
- Надзорное уведомление — долг, только пока в области есть `running`
  строки; иначе при заборе оно `void`. Проверка политики сессии — до подачи
  вызова-забора: при запрещённом ходе вызов не подаётся (решает арбитр, 3.9).

**Вызов-забор** — отдельный вид `SessionAgentCall` (`Drain`), идущий обычным
путём `Run`/`submit`: одна попытка провайдера в `runInternal` (без циклов
повторов/продолжений координатора; повторы внутри шага остаются у fantasy;
401 обновляется до запуска — `drainCallFor` обновляет OAuth-токен или ключ
из шаблона `$` и пересобирает клиент, в том числе замороженный клиент
ребёнка, а остаточный 401 обновляется в учёте попытки на собственном
контексте 10 с). Очередь: не больше одного вызова-забора на сессию на любом
пути вставки; при слиянии побеждает более сильная политика; «осиротевший»
вызов не отбрасывается — новая проверка долга после освобождения мейлбокса;
в `QueuedPromptsList` не показывается. В начале хода — перенос уведомлений,
затем решение **по долгу реакции**: долга нет или арбитр запретил ход —
завершение без провайдера; долг есть и ход разрешён — ход с **пустым
промптом** и признаками `AutoResumed`/`BackgroundJobNotice`. Вид вызова и
признаки никогда не наследуются (один конструктор сбрасывает). Итерации-
забор CLI-цикла не пишут сессию: ни промпт, ни бюджет, ни `ended_reason` —
пишет только выход цикла (3.5).

**Кто запускает вызов-забор:** подсказка после коммита перехода/уведомления
с `wake=1`; проверка долга на каждом освобождении мейлбокса (в отдельной
горутине, никогда из `defer`); 60-секундный проход перепроверки (3.7);
приход фонового shell (3.10). Против холостого круга — арбитр (3.9): гейт
запуска, набор перепроверки для session-lock чужого процесса и отсрочка
после неудач. **Сессии с внешним ведущим** (CLI-корень) вызов-забор с ходом
не получают — только подсказку циклу (DUR-10); перенос уведомлений в его
историю другим держателем lock долг не стирает.

**Политика сессии «можно ли ход»** (решает арбитр):

| Сессия | Ход по долгу реакции |
|---|---|
| дочерняя под бегущей делегацией | да (правило `RunningDelegation` — раньше предела автоходов и bg-shell-политики); завершение её фонового shell будит её при любом отказе в заявке слота |
| дочерняя без делегации | нет (`isDurableDelegationChild`: существует строка делегации любого вида с этим ребёнком; ретеншн не удаляет её, пока у ребёнка running-строка или долг) |
| CLI-корень | решает цикл `rush run` |
| web, async-задачи и делегации | да, без ограничения |
| web, фоновые shell | только при `AutoResumeOnJobDone` — и в пределах автоходов корня (слоты, ниже) |
| web-вкладка, открывшая сессию | только перенос уведомлений, без хода |

**Предел автоходов (слоты):** 5 на сообщение человека, только для
автовозобновления по фоновым shell **корня** (не ребёнка под делегацией).
Слот тратится один раз, **при допуске завершения** (`claimAutoResumeSlot` в
точке прихода, ДО решения о запуске). Перепроверка (освобождение, тик) и
решение Drain на старте хода **сравнивают предел, не тратя**: отложить можно
только завершения, не получившие слота. Состояние: `consecutiveAutoResumes`
(потраченные слоты) и множество id строк `session_notices` `bg_shell_done`,
пришедших при исчерпанных слотах (over-cap; по id, не по числу — порядок
строк не используется); оба живут в арбитре (3.9), сбрасываются сообщением
человека, теряются при рестарте web (строки остаются долгом и идут обычным
путём K=3). Stop-суспензия (`autoTurnsSuspended`) гасит автоходы всех видов
до следующего сообщения человека и отклоняет их раньше сравнения предела;
счётчики Stop не трогает.

**Политика `wake`:**

| Источник | `wake` |
|---|---|
| естественное завершение задачи, таймаут | 1 |
| Stop, `job_kill`, прерывание | 0 |
| надзор | 1; при заборе — `void`, если область уже закрыта |
| `wake_only`-таймаут | 1; при заборе — `void`, если задача уже не `running` |
| маркер неудачного пробуждения | 0 |
| завершение фонового shell | 1 (`bg_shell_done`; ход — по политике) |
| `wake_fired` (расписание) | 1 |
| вопрос ребёнка | 1 (`child_question`); `void` после осушения без ответа |

Для `job_kill` итог — ответ самого инструмента, строка сразу `done`.
**Stop** в том же проходе ставит `wake=0` всем `pending`/`done` строкам
остановленного дерева (3.8); гонку с естественным завершением закрывает
политика: у отменённой делегации нет права на ход. `recordProgress`
(сброс тишины) вызывается при переносе уведомлений, кроме надзорных;
`pushDeadlineOnTurnEnd` не срабатывает для заборов без хода.

### 3.5 Область, CLI-цикл `rush run`, рецензент, отмена

**Область S открыта** ⇔ у S есть `running` строка на живом хосте, или S
ведёт ход, или у S есть долг и политика разрешает ход, или у S активно
разовое wake-расписание (`wakein`/`wakeon`; активные `loop`-расписания
открытой работой не считаются и снимаются при закрытии области CLI). Ответ
даёт `CLIScope` (арбитр): running-строки читаются первыми (терминальный
переход и долг фиксируются атомарно — «не running» гарантирует, что
следующее чтение видит долг), затем долг; для ребёнка — `childScopeDrained`
по тому же `CLIScope`. Цикл CLI `ScopeOpen` на памяти не держит. Читатели
живости между процессами (все команды `sessions`, web-список) — единый
классификатор `ClassifySessionActivity` (`internal/session/
session_activity.go`) над фактами одного читателя `App.SessionActivity`
(R-ACT): вердикт `in_turn > delegating > between_turns > crashed > ended >
idle`; живая работа выше мёртвого PID; lock — один enum. Слои
`computeSessionStatuses`/`reclassify*`/`promote*` удалены. Пакетный список
— один `LiveWorkForRoots` и одна проба хоста на хост.

**Маркер внешнего ведущего (DUR-10):** `session_drivers(session_id →
host_id)`; ведущий жив ⇔ жив его хост (без часов, unknown = жив). Пока он
жив, другие процессы не запускают ход реакции; допущенный забор лишь
переносит уведомления. `rush run` занимает маркер (`ClaimSessionDriver` →
регистрация хоста, даже без задач) до первой записи в сессию и снимает при
выходе; второй `rush run` получает `*ErrSessionDrivenElsewhere` до хода.
При принудительном завершении маркер остаётся до конца процесса.

**CLI-цикл** — явная машина состояний (`cliLoop`): первый ход → ожидание →
Drain → рецензент → выход. Решение «нужен ли ход» — `DrainState` арбитра:
`Owed` — запуск, `Paced` — ожидание гейта, `Deferred`/`Stuck` без бегущей
работы — выход (Stuck — ошибка; Deferred — уведомление остаётся до
следующего хода человека, причина выхода не меняется). Итерации-забор без
мутаций (`RunRequest.drainTurn`); свою область цикл перечитывает не реже
раза в 5 с.

- **Ожидание:** каждая ветка ожидания (`WorkOpen`, `Paced`) перед сном
  читает `stopError` — лимиты (`--max-cost`/`--max-tokens`) и отмену
  оператора (`sessions cancel` читается при каждом пробуждении, ≤5 с);
  выход `stepCanceled` → `exitPrecheck` (конверт, `ended_reason`,
  `--on-finish`, `Shutdown` снимает дерево). Ожидание не бесплатно: расход
  цепочки Drain ребёнка списывается ребёнком в свою строку мгновенно
  (3.11), и лимит его видит.
- **Занятая сессия:** первый ход при чужом session-lock завершается сразу
  ошибкой; повторяются только собственные ходы-заборы цикла (0,5 с, не
  дольше 30 с подряд, stderr). Сбой подготовки итерации до любого хода идёт
  тем же ограниченным путём (без горячего цикла); сообщение ожидания
  называет задачу и хост (ASYNC-10), не чаще раза в 60 с.
- **Рецензент:** проход ревьюера запускается по предикату области из БД, не
  внутри Drain, один раз при выходе закрытой области, обычным ходом
  (`reviewerTurn`, модель рецензента, подагенты выключены, опции первичного
  вызова копируются кроме `ModelRole`/`DisableSubAgents`). Если ход
  рецензента запустил собственную async-работу, цикл возвращается в
  ожидание: `reviewerDone`, ответ запуска — последний ЗАВЕРШЁННЫЙ ход.
  Проваленный/отказанный замком ход рецензента пропускается (строка на
  stderr) и ответ не подменяет; `reviewer pass skipped` пишется в `Stderr`.
- **`ended_reason`** = `exit_reason` запуска; у запуска `rush run` — пуст,
  пока цикл идёт, пишется один раз на выходе (`persistEndedReason(final)`;
  все выходы через `exit`/`flushed`; сравнение перед записью). Вызовы не из
  цикла (SDK) пишут за ход, как раньше.
- **Отмена — одноразовый запрос:** `cancel_requested` снимается, когда
  исполнен: в начале хода человека (не Drain, без опций вызова), при
  возобновлении ребёнка, при исполненном внутриходовом прерывании (кроме
  сессии под циклом: цикл читает флаг после хода и снимает на выходе
  `canceled` — `clearHonouredCancel`). Drain флаг в своём начале не
  снимает; веб-Drain исполняет флаг один раз и снимает.
- **Лимиты времени:** `--timeout` и потолок 6 ч по умолчанию — мягкий
  контекстный дедлайн с жёсткой отсрочкой 60 с (`installRunDeadline`): цикл
  выходит через `exitWait` (конверт `canceled`), `os.Exit(124)` — только
  для процесса, не вышедшего за отсрочку. Причина дедлайна названа
  (`ErrRunDefaultCap` обёрнут в `context.DeadlineExceeded` — обрыв потока
  транспортом распознаётся). `--idle-timeout` следит только за ходами.
  Запись в закрытый stdout/pipeline не убивает запуск (SIGPIPE
  обрабатывается: EPIPE → обычный `flushErr` → хук и `Shutdown`).
- **Стоимость окна прогона:** `delta_cost_usd`/`RUSH_COST_USD` = разность
  `Sessions.SubtreeSpent` корня между заявкой (claim) и выходом — запрос по
  дереву делегаций, без переносов (3.11). `--max-cost` сравнивает бюджет
  корня (`subtree_spent − cost_base`) везде одинаково (`enforceRunawayCaps`,
  `stopError`, арбитр); `--max-tokens` — по строке корня. `GetLastSession`
  возвращает самую свежую верхнеуровневую сессию.
- **`sessions`-поверхности:** `inject` считает сессию с живой работой
  (замок, маркер цикла, собственная задача, делегация) работающей — между
  ходами тоже; `--interrupt` для цикла между ходами ставит
  `queued-for-interrupt`; `reap` не трогает замок без записанного PID
  (чистый релиз); `locks` ищут пульс по настоящему id (обратная карта основ
  имён файла) и принимают `<id>`/hash; `cancel --all` метит только сессии с
  живой работой; `why`/`list`/`watch`/`tail`/web — вердикты классификатора
  (выше). `Sessions.Get`/`List` несут `ended_reason`, бюджет и
  `CancelRequested`.

### 3.6 Жизнь процесса: хосты, блокировки, без часов

- Хост регистрируется **лениво**: при первом `Claim` async-задачи **или**
  первом `ClaimSessionDriver` (`rush run` регистрирует хост сразу, даже без
  задач). Случайный uuid, файл `<data>/hosts/<host_id>.lock`, эксклюзивная
  ОС-блокировка на всё время жизни процесса, сильная ссылка.
- **Мёртв ⇔ блокировку удалось захватить**, либо файла нет. «Жив» — при
  отказе «занято». Другая ошибка — «неизвестно»: неизвестное считается
  живым. Проба открывает файл без создания; свой host_id и хосты соседних
  `App` не пробуются. Файловая система без блокировок — отказ при
  регистрации; каталог данных — только локальный диск; `hosts/` руками не
  трогать. `RegisterHost` не публикует id, чей файл может быть удалён
  уборщиком (создал-залочил-перепроверил путь). Пробовать и восстанавливать
  может любой процесс; **вердикт для читателей — разделяемая проба
  (`ProbeHostShared`), никогда не претендующая на блокировку**;
  эксклюзивную пробу берут только пути восстановления — которым блокировку
  нужно выиграть (снятие файла, зачистка).
- Файл удаляет владелец при выходе, если строк не осталось; чужие —
  восстановитель/зачистка, выигравший эксклюзивную блокировку на момент
  удаления (POSIX: unlink под блокировкой; Windows: открытый файл не
  удаляется). Один удаляющий: `HostRemoved` = «строку удалил этот вызов»;
  файл без строк, чей удаляющий не определился, убирает
  `purgeOrphanHostLockFiles`; исчезнувший между списком и пробой файл
  сироты — не ошибка и не Warn.
- **`CloseKeepLock`** (принудительное завершение) держит блокировку хоста и
  маркеры до конца процесса и не отпускает позже: у зависших горутин нет
  общего сигнала, и освобождение означало бы, что другой процесс
  восстановит строки под ещё пишущей горутиной. `ShutdownResult.Forced`
  обязывает встраивающий процесс завершиться; до тех пор строки хоста
  остаются `running`, новый App того же процесса их не восстановит.
- `async_hosts` — только для показа; `label` = `"app"` (значение только для
  показа; комментарий выпущенной миграции с `'cli'|'web'` устарел); без
  внешнего ключа из `async_jobs` и без отметок времени для решений о жизни.
- **Подсказка `sessions jobs` останавливает хост целиком:** POSIX —
  `kill -INT <pid>` (штатный выход вызывает `CancelAll`, убивающий группы
  процессов задач); Windows — `taskkill /F /T /PID` (job object с
  kill-on-close, если назначен). `sessions kill` убивает держателя
  блокировки сессии и сам задачу не останавливает.

### 3.7 Восстановление, ретеншн, `sessions reset`, 60-секундный проход

**Единственный межпроцессный запасной путь — 60-секундный проход:**
подсказки живут внутри процесса, поэтому хост раз в 60 с перепроверяет
мёртвые хосты, свои припаркованные делегации, долг дочерних сессий и набор
перепроверки; проход идёт и в `rush run` (тикер с `ClaimExternalDriver`,
плюс один `RunMaintenanceSweep` на старте цикла), и в web
(`SetPersistentMode`). Других опросов нет.

**Восстановление (`RecoverDeadHost`, DUR-6)** выполняется: ведущим для
своей области (при оценке области), хостом при регистрации и проходом — по
всем мёртвым хостам. **Не держит блокировку мёртвого хоста:** вердикт —
разделяемая проба; исключительная блокировка — только внутри
`removeDeadHostFile`. Смерть необратима (uuid не переиспользуется).
Параллельные восстановители допустимы — каждая запись держит личность
строки (`Transition` по `claim_id` из листинга; удаление неанонсированной
по `claim_id`; хост-скоуп только по id мёртвого хоста), проигравший видит 0
строк:

- `running` с `announced=1` → `transition` в `interrupted` (`wake=0`):
  для делегации — с последним сообщением ассистента дочерней сессии; для
  bash/run_command — «вывод не сохранялся; процесс мог остаться запущенным»
  (процессы не убиваются);
- `running` с `announced=0` (включая терминальные неанонсированные) →
  удалить без следа (ASYNC-05);
- безымянная строка `job_kill` (`done`, `notice_message_id IS NULL`) →
  снова `pending` (`RependJobKillRowsWithoutNoticeForHost`);
- строк не осталось → удалить строку хоста и файл.

Восстановление **не пишет историю и не будит сессии**. Корректный выход
процесса = падение: исполнители останавливаются, переходы от отмены при
shutdown подавлены, строки остаются `running`.

**Ретеншн (тем же проходом, DUR-5-совместимо):** `done`/`void` старше
порога, **кроме**: невыполненного долга (`pending` не удаляется вовсе;
`done` с `wake=1, reacted=0` не удаляется), строки делегации, пока у её
ребёнка есть running-строка или долг, и безымянной строки `job_kill`, чей
хост ещё не мёртв. `sessions gc --jobs-older-than` отвергает возраст ≤ 0.
Следствие: Rerun достаёт назад ровно настолько, насколько ретеншн хранит
доставленные строки (7 суток).

**`sessions reset` — чистый лист (R8A-3):** `RecoverOwnerScope` (строки
мёртвого хоста → `interrupted`), затем проверка живой работы (живой маркер
цикла, собственная running-задача на живом хосте, живая делегация;
нечитаемое = живое) — при живой работе **отказ** (остановить чужой процесс
нельзя; `--force` убивает держателя замка сессии, но проверка остаётся).
Затем `ResetOwnerHistory` одной транзакцией: удаление сообщений, `void`
каждой `pending`/`done` строки владельца обеих таблиц (и
`reacted_failed=0`), отмена активных расписаний. Долг исключает `void`,
pull берёт `pending` — ни уведомления, ни долг не переживают стирание.
Стоимость — одна колонка `cost_base = subtree_spent` (3.11).

### 3.8 Stop, Rerun, делегации, ключи, `job_kill`, вопрос ребёнка

- **Stop транзитивен** (`stopTree`): отмена сессии отменяет всё дерево
  через `running` строки делегаций; каждому id — собственный драйвер,
  суспензия автоходов; всем `pending`/`done` строкам дерева — `wake=0`
  (`SetWakeZeroForOwners`, ASYNC-08/DUR-9). После обнуления `stopTree`
  перепроверяет **каждого** ребёнка (`recheckChild`): ребёнок,
  припаркованный на своей задаче, иначе не перепроверяется ничем; то же —
  из `finish` устаревшего исполнителя (Stop, попавший в односекундную
  паузу исполнителя `bash`). Дочерние задачи не будят детей после Stop.
- **Rerun:** `TruncateForRerun` — одна транзакция; реестр сверяется по
  реально удалённым строкам. Void идёт по `announce_message_id` (не по
  `tool_call_id`, который переиспользуется); для строк без него — ветка по
  `tool_call_id`. Доставленный маркер `wake_failed` из хвоста получает
  `void`; остальные уведомления снова `pending` (`reacted=0`). Задачи
  удалённого хвоста останавливаются **после коммита** (`StopRerunJobs`,
  семантика Stop: `cancelled`, `session_cancel`, `wake=0`, `delivery`
  остаётся `void`; чужой хост не останавливается) — `CancelTurn`, а не
  полный Stop. Компакция строки не трогает. Rerun держит автоходы сессии
  (`HoldAutomaticTurns` → в арбитре paced без часов; удержание переживает
  сообщение человека, пока счётчик holds > 0).
- **Claim делегации** пишет `child_session_id` сразу (детерминирован; FK на
  колонку убран). В транзакции claim: идемпотентное чтение, затем
  частичный уникальный индекс `child_session_id WHERE state='running'`
  (ASYNC-01): конфликт с мёртвым хостом → восстановить в той же попытке; с
  живым → ошибка **до** «started» («у под-агента ещё идёт работа прошлой
  делегации»). **Carve-out #1157:** resume ребёнка, чья held-делегация
  приостановлена его вопросом, отвечается В эту делегацию до Claim — строка
  не создаётся. Прочие resume живого ребёнка отклоняются как раньше.
- **Ack gate:** «started» и `announced=1` — одна транзакция без условия на
  состояние (DUR-7); право подтвердить/откатить выдаётся `claimAck` одному
  результату с меткой `claim_id`, пока задача не анонсирована ни в памяти,
  ни в строке; обычный результат с тем же `tool_call_id` задачу не трогает;
  `abort` не трогает анонсированную. Паника между Start и запуском
  исполнителя — `failLaunch` напрямую (не через `recheckChild`).
- **Переиспользование `tool_call_id`:** строка, у которой терминальное
  состояние и `delivery` done/void, при повторном id архивируется в
  `<id>#reused#<uuid>`; то же — терминальная анонсированная, но
  недоставленная (её уведомление достанется владельцу под архивным ключом).
  Ключ удерживает только терминальная строка, чьё «started» не записано —
  ей Claim отвечает идемпотентно; `workLedger.Start` для такой строки без
  задачи в памяти даёт ошибку инструмента. Второй исполнитель не
  запускается. Архивная строка достижима по `notice_message_id`/
  `announce_message_id` для Rerun.
- **`job_kill`:** после выигранной остановки инструмент отвечает
  захваченным текстом и метаданными (`killed_claim_id`); если слитая запись
  результата не состоялась, `persistJobKillResult` возвращает строку в pull
  (`RependJobKillRowWithoutNotice`, отсоединённый ctx, ≤30 с) — адресация
  по `claim_id` остановленной заявки, не по `tool_call_id` (повторный
  `call_0` архивирует только что убитую строку, пока `job_kill` ещё
  работает). Защита слитой записи оборонительная: единственная достижимая
  причина 0 затронутых строк — каскадное удаление сессии-владельца.
- **Читатели между процессами** (`LiveJobs`, `sessions jobs`, web): живость
  = `running` и хост жив (разделяемая проба); один классификатор — 3.5.
- **Итог делегации:** последнее завершённое сообщение без текста → родитель
  получает «завершено без итогового ответа». Вопрос ребёнка, заданный после
  текста, доходит вопросом (текст — преамбула, `IsError=false`).
- **CLI-цикл при отказе «session-lock занят» на своей сессии** повторяет
  ход с ограниченной паузой (3.5).
- **Индексы:** `(host_id)`, `(owner_session_id) WHERE delivery='pending'`,
  `(state) WHERE state='running'`, уникальный частичный по
  `child_session_id`, `WHERE shell_id IS NOT NULL`; для `session_notices` —
  `(owner) WHERE delivery='pending'`; частичные долги — в 3.4.

### 3.9 Арбитр автоматического хода (R-ARB)

Арбитр уточняет политику запуска из 3.4; здесь — его устройство.
Запускающий вердикт принимает ОДНА чистая функция — `decide` над одним
снимком фактов `readTurnFacts` (`internal/agent/turn_arbiter.go`), а всё её
изменяемое состояние живёт в ОДНОЙ структуре `arbiterState` под одним
мьютексом (`internal/agent/turn_arbiter_state.go`): удержание Rerun,
Stop-суспензия, слоты и over-cap-множество bg-shell капы, предохранитель
реакционных цепочек и гейт запуска. Семь бывших map координатора и гейт в
`workLedger` удалены; запись одна на сессию; уборка — `sweepArbiterEntries`
в `RecheckPass` и удаление целиком для удалённых сессий.

- **Порядок — часть закона:** сначала вся БД-половина фактов (running-строки
  и восстановление своего мёртвого хоста, долг `PendingInclusiveDebtRows` —
  единственное чтение строк долга, маркер ведущего, делегация), затем память,
  без DB I/O под мьютексами. `bgArrival` берётся **до** чтения строк долга и
  покрывает связку «строки долга + over-cap-множество», как и сам приход
  завершения (вставка + решение о слоте под тем же гейтом). Подрезка
  over-cap — только в точке прихода; правило капы считает только id, ещё
  входящие в долг.
- **Вердикты:** `VRun{Counted}` (ход), `VDefer{reason, recheckAt}` (paced —
  пауза гейта; deferred — политика не разрешит; stuck — без запуска),
  `VClose(rows, marker)` (закрытие долга неудачей; закрывает арбитр,
  исполняет учёт), `VNone`. Отказ коммита шага при непустом снимке —
  отдельный исход: гейт не трогается, сессия возвращается в recheck-набор.
- **Ключевые правила** (табличный тест — оракул): вопрос/Stop/суспензия →
  defer; чужой живой ведущий → defer + recheck-набор (DUR-10); удержание
  Rerun → paced без часов; выпущенный ребёнок без идущей делегации —
  обычная политика; затем гейт (для всех, включая ребёнка с идущей
  делегацией — пауза после неудачной попытки действует и на него); затем
  bg-shell-политика и капа, которые при `RunningDelegation` пропускаются;
  предохранитель цепочки (ниже) при `ChainOwnsAllDebt=false` не откладывает
  `child_question`. Ошибка чтения входа — fail-closed (deferred) для всех
  координаторов, web и CLI alike.
- **Учёт попытки — один раз на ногу вызова-забора, в цикле хода, который
  эту ногу выполнил** (`accountDrainAttempt`), после конца ноги и до
  освобождения мейлбокса, по вердикту БД над снимком, взятым ПОСЛЕ
  собственного переноса вызова. Запускающие (`wakeSession`, хук
  освобождения, проход перепроверки, цикл CLI) ничего не считают. Считается
  нога, дошедшая до провайдера; не считаются: чистая отмена/дедлайн
  (дедлайн — только если контекст хода сам достиг его: таймаут транспорта
  при живом контексте — считаемая неудача), отказ до провайдера, вопрос
  агента, пользовательский ход из очереди, нога, оборванная сообщением
  человека. Watchdog-остановка и обрыв по лимитам — настоящие оплаченные
  попытки.
- **Два независимых счётчика сна:** `freeStreak` (заборы «без хода» при
  неснимаемом переносе — на третьем гейт спит, открывает более новый факт)
  и `paidStreak` (оплаченные попытки без реакции — спит на третьей, только
  когда закрытие само не удаётся, и открывает ТОЛЬКО сообщение человека или
  перезапуск: факт после оплаченной неудачи паузу не сокращает). Одна
  неудача переноса и две неудачи провайдера — не сон. Запись с истёкшей
  паузой и нулевыми сериями простаивает.
- **Трата слота** — в точке прихода завершения (`claimAutoResumeSlot`),
  утверждено ревью: перенос траты на исполнение `VRun` сломал бы связь
  «завершение при закрытом гейте тратит слот», на которой измеряется
  over-cap-множество.
- **Предохранитель реакционных цепочек (#1113):** цепочка
  «запуск → забор → запуск» без прогресса останавливается: N=3 звеньев на
  факт, звено на другой факт — новая цепочка; `chainGuardMarker` пишет
  маркер. Прогресс — шаг с содержимым; `child_question` и вызов `agent`
  звеньями холостого запуска не считаются.
- **Запускатели** (подсказка, освобождение мейлбокса, recheck-проход,
  приход bg-shell, `CLIScope`, `decideDrainTurn` на старте хода) — все идут
  через один предикат; свойство «у каждого долга Owed ровно один
  запускающий» покрыто; дубли безопасны (один Drain в очереди, решение на
  старте хода).

`drainPolicy`/`drainPermitted`/`decideDrainTurn`/`CLIScope` — тонкие
адаптеры над `decide` с отображением вердикта в перечисления
(`DrainState`: `Owed/Paced/Deferred/Stuck`).

### 3.10 Фоновые shell как строки `async_jobs` (R-BG, ASYNC-13)

Каждый фоновый shell, переживший ответ инструмента и рождённый ВНЕ
async-обёртки (sync-ветка `asyncTool`: SDK-origin и Drain/wake-ходы на
`context.Background()`), получает **ровно одну строку `async_jobs`** kind=
`bg_shell` (`owner_session_id` + `tool_call_id` = id shell'а;
`announced=1` — сам ответ инструмента с id и есть «started»). Claim —
сразу после запуска, до возврата ответа; отказ (БД недоступна) = отказ
фона (fail-closed), никогда shell без строки.

- **Терминальный переход** — единственный durable факт итога: `state` +
  `result_summary` одним CAS (DUR-1), естественный выход `completed/failed`
  с тем же текстом, что строил `backgroundJobSummary`. Строка пишется
  `delivery='done'`, `reacted=1` — никогда не pull'ится и не долг: **wake-долг остаётся на
  `session_notices`** (`bg_shell_done`, вставка + решение о слоте под
  `bgArrival`); перенос долга в строку обошёл бы капу (ASYNC-09).
  Оболочка без строки (легаси/фикстуры) идёт старым notice-путём.
- Path 1 (CLI/web async `bash`) остаётся на строке самой задачи:
  `setShellID` + `awaitShell`, отдельного kind нет; связь строка↔shell —
  колонка `shell_id` (читаема из другого процесса).
- Восстановление: running `bg_shell` на мёртвом хосте → `interrupted`
  («process lost with host»), DUR-6.
- Отдельный лимит bg-shell удалён — политика и капа живут в арбитре (3.9).
  **Удержание завершения сохранено** (`PendingCompletionsOwned`,
  `completionHoldMax` = 10 мин, `detachedAt`;
  `internal/shell/background_completion.go`): `childScopeDrained` считает
  shell ребёнка живым, пока у него есть running-строка `bg_shell` ИЛИ
  незакрытое удержание завершения — окно между выходом процесса и фиксацией
  `bg_shell_done` закрывает удержание, а не строка (R7B-1/R8B-2;
  «убит, но не умерший» shell — ветка `detachedAt`). Отдельного листинга
  фоновых shell нет: строки и есть листинг (`sessions jobs`, web «Команды»).
- Wake-уведомление строится при pull из строки; `job_output` во время
  работы — по-прежнему из памяти менеджера (живой процесс доступен только
  своему хосту).

### 3.11 Стоимость: COST-1 (R-LOOP-2)

Стоимость «включая детей» — всегда **запрос по дереву делегаций**, никогда
не перенос между строками: каждая сессия пишет только свою монотонную
`cost_self` (единственный писатель `IncrementCost`/`IncrementCostIfUnderMax`);
ребро дерева — только делегация (`cost_parent_id`, один раз в
`CreateTaskSession`; fork — собственный корень стоимости); `subtree_spent`
— рекурсивный CTE с `UNION` (`Sessions.SubtreeSpent`/`SubtreeBudget`).
Бюджет узла = `max(subtree_spent − cost_base, 0)`; `sessions reset` пишет
одну колонку `cost_base`; `--max-cost` — бюджет корня; окно прогона —
разность `subtree_spent` на claim и на выходе, сбросы его не трогают.
`--max-tokens` — по строке корня (снимки, не накопления). Траты ребёнка
(шаги его Drain-цепочки, работа между ходами, выход по отмене) видны
бюджету и окну **мгновенно** — класса находок «перенос ребёнок→родитель с
водяным знаком `parent_cost_accounted`» не существует: `decrementCost`,
`owedChildCost`, `TransferChildCostToParent`, `chargeRunningChildren`
удалены. Бывшие поправки (ab).2/(ae).3/(aj).1/(ag).2/(am).2 этим заменены;
детали — `docs/plans/2026-10-01-run-cost.md` и COST-1 в реестре.

### 3.12 Стражи внутри хода

Ортогонально долговечному ядру: **страж внутриходового прогресса**
(#1149) отказывает wait-запускам и повторным чтениям после S шагов без
прогресса и завершает ход после H; **предел async-задач сессии** (ASYNC-12,
A27): не больше 50 нетерминальных задач, отказ до Claim с инструкцией
модели и метаданными `async_cap` (допуск ≠ область). Долговечные законы
фазы 4 их не заменяют и не нарушают.

## 4. Надзор и wake-расписания

Надзор (`supervision.go`) — обычные уведомления `check_in` с таблицей wake
(3.4); интервал — не ниже пола (1 с), переопределение ниже пола
игнорируется. Опции надзора копируются в вызов рецензента, кроме
`ModelRole`/`DisableSubAgents`. Wake-расписания (`wakein`/`wakeon`/`loop`,
стадии 4a–5a) живут в `wake_schedules` (SCHED-01…10 в реестре): один таймер
на процесс, recovery без дублей, разовый таймер держит CLI-область открытой,
`loop` — нет и снимается при закрытии области; их законы — в
`docs/async-invariants.md`, здесь не дублируются.

## 5. Законы (реестр: `docs/async-invariants.md`)

| ID | Закон |
|---|---|
| DUR-1 | Состояние async-задачи меняет только `transition`: одна транзакция с SQL-CAS (по `state='running' AND claim_id`); память сходится к БД; держатель исхода повторяет до коммита; личность исполнителя закрывает внутрипроцессный ABA. |
| DUR-2 | Терминальный переход, `delivery='pending'` и `wake` по причине — одна транзакция (существующий `void` сохраняется). |
| DUR-3 | Уведомления пишет в историю только ведущий сессии, только в начале хода или на границе шага; уведомление и `delivery='done'` — одна транзакция. |
| DUR-4 | Долг реакции — строка с `wake=1`, `delivery` ∈ {pending, done}, `reacted=0`; `reacted=1` ставится только транзакцией шага модели с содержимым, закрытием долга неудачей, inline-Tx2 (A14) или терминальной строкой `bg_shell`. «Нужен ход» решает арбитр по долгу и БД; каждое освобождение мейлбокса проверяет долг и подаёт вызов-забор через `Run`. Подсказка лишь будит. Долг умирает со стиранием истории (`sessions reset` гасит `void`-ом). |
| DUR-5 | Процесс жив ⇔ держит ОС-блокировку своего файла хоста; «мёртв» — только при захвате или отсутствии файла; часы не используются; читатели — разделяемая проба. |
| DUR-6 | Восстановление только переводит `running` мёртвого хоста в `interrupted`/удаляет неанонсированное/возвращает безымянную строку `job_kill`; историю не пишет и сессии не будит; не держит блокировку мёртвого хоста. |
| DUR-7 | «started» и `announced=1` — одна транзакция; неанонсированная задача никогда не даёт уведомления; право ack — по `claim_id` одному результату. |
| DUR-8 | БД недоступна при старте async-задачи — задача не запускается (как и фон shell без строки). |
| DUR-9 | Stop отменяет дерево делегаций и обнуляет `wake` всем строкам дерева; отменённая и прерванная работа не будит никого; после обнуления перепроверяется каждый ребёнок дерева. |
| DUR-10 | Драйвер сессии из другого процесса записан долговечно (`session_drivers`); жив ⇔ жив его хост (без часов, unknown = жив); пока он жив, чужой ход реакции не запускается; второй драйвер не допускается. |
| DUR-11 | `delivery='done'` ⇒ строка называет сообщение истории (`notice_message_id`); «started» назван в `announce_message_id`; Rerun вычисляет множества только по этим id; `job_kill` адресует строку по `claim_id`. |

Смежные: COST-1 (стоимость, 3.11), ASYNC-12 (капа задач, 3.12), ASYNC-13
(bg_shell, 3.10), якорь R-ARB (3.9), SCHED-01…10 (расписания) — все в
`docs/async-invariants.md` с якорями в коде и доказывающими тестами.

## 6. Обязательные тесты (реальная SQLite, где речь о БД)

Перечень — контракт приёмки; каждое имя проверяемо `grep -rn "func <name>("`.
Сводные группы (полные списки — в реестре законов):

- **DUR-1/2:** повтор при занятой БД и коммит; проигравший принимает
  состояние; каждая причина даёт свой state/notice_kind/wake; атомарность
  тройки (триггер-аборт); гонки finish/stop/timeout/job_kill дают один
  исход; shutdown не подавляет естественное завершение; устаревший
  исполнитель не пишет на перевзятый ключ.
- **DUR-3:** уведомление не оказывается между вызовом инструмента и его
  результатами; два ведущих в двух процессах — одно сообщение; ошибка
  забора не валит ход; компакция не забирает; вставка на границе шага 3
  видна шагам 4+; надзорные `void`-условия; `child_question` будит родителя
  и void-ится после осушения.
- **DUR-4/ASYNC-09:** ребёнок делает ход над уведомлением; лишняя/потерянная
  подсказка не даёт лишнего хода; гейт не зацикливается; CLI-корень без
  забора; провайдер не видит уведомление дважды; минутный сбой не закрывает
  долг, квота/401/переполнение контекста — закрывают с маркерами; закрытие
  по K — только строки со своими попытками; два счётчика сна; компакция и
  Rerun долг не гасят; web-вкладка не стирает долг корня; сливание
  «только перенести» с «ход разрешён» даёт ход; `reacted_failed` снимается.
- **Арбитр (R-ARB):** табличный тест `decide` на все правила (включая
  «ребёнок с идущей делегацией + оплаченная пауза → paced»); ровно один
  запускающий у Owed; удержание Rerun переживает сообщение человека;
  over-cap id в шве чтения фактов сохраняется; fail-closed при нечитаемом
  входе; предохранитель цепочки (3 звена, маркер, `child_question` не
  звено).
- **Капа автоходов:** ровно пять автовозобновлений корня; слот тратится при
  допуске; отложенный запуск не тратит; over-cap по id; ребёнок под
  делегацией просыпается при отказе в заявке (ровно один запрос к
  провайдеру); Stop/сообщение человека — сбросы.
- **A14 inline:** быстрая задача до ack — одно уведомление в самом
  tool result; Tx2 атомарен; после Tx2 нет долга и работы; краш в окне —
  обычный путь.
- **Stop/Rerun/ASYNC-01:** Stop с N под-агентами с bash — ни одного нового
  хода; Stop через секунду после завершения — нового хода нет; Rerun до
  уведомления — результат в новую ветку; Rerun с живой задачей в хвосте —
  ни уведомления, ни хода; Rerun после Stop — удалённых вызовов нет;
  resume при живой делегации — ошибка до «started»; при мёртвой —
  восстановление; повтор — идемпотентный ответ; ответ в held-делегацию —
  строка не создаётся; драйвер ребёнка освобождается Stop'ом (включая
  устаревшего исполнителя `bash`).
- **DUR-5/6/10:** живой хост не «мёртв»; неизвестная ошибка — не «мёртв»;
  параллельные восстановители — один эффект на строку; устаревший листинг
  не трогает свежий claim того же id; файл хоста удаляет один; зачистка
  пустого хоста — `HostLiveness=Dead` на всём окне; восстановление не
  создаёт сообщений; маркер ведущего: web-job при живом CLI — отвечает
  CLI; смерть цикла — web перехватывает; второй `rush run` — отказ до
  записи в сессию.
- **Сквозные (два App на одном каталоге):** «падение» A → `--continue` в B
  даёт ровно одно «прервано»; доставленное в A не возрождается в B; Ctrl-C
  — ни одного нового хода, после перезапуска — по одному «прервано»; хост
  убит до ack — строки нет и уведомления нет; `job_kill` — итог в ответе
  инструмента, второго уведомления нет; маркер неудачного пробуждения не
  плодит цепочку; финал шага не записан — долг остаётся.
- **CLI-цикл/ревьюер/отмена (3.5):** ожидание читает отмену и лимиты перед
  каждым сном; `ended_reason` пуст у живого цикла и пишется один раз на
  выходе (включая выходы между ходами); потолок 6 ч — мягкий дедлайн;
  замок ≠ жизнь (watch/tail/locks/inject между ходами); рецензент возвращает
  цикл в ожидание, опции надзора копируются, отказ замка не подменяет ответ;
  исполненная отмена гасит флаг; inject не дублируется; закрытый stdout не
  убивает запуск; `cancel --all` метит только живые.
- **bg_shell (ASYNC-13):** claim до ответа; терминал одной транзакцией с
  итогом; Kill-запрос — терминал по факту запроса; строка не pull'ится;
  долг на `bg_shell_done` под `bgArrival`; мёртвый хост — `interrupted`.
- **Стоимость (COST-1):** трата ребёнка между ходами/на отмене/в Drain-
  цепочке видна бюджету и окну; reset не трогает окно; backfill-инвариант
  миграции; `--max-cost` = бюджет корня.
- **Reset:** стирание гасит уведомления и долг; отказ при живой работе
  (включая `--force`); чужой владелец не тронут; отрицательная дельта не
  существует (нет писателя с уменьшением).
