## Findings, by severity

### F-1 (P1, BLOCKER) — the external-owner predicate treats this process's own just-released lock as a live foreign owner

- `internal/server/handlers_agent.go:117-134` (`externalSessionOwnerRefusalFromConfig`,
  specifically `:122` `if !st.Live`, `:125` `if st.PID != 0 && st.PID == os.Getpid()`,
  `:130` `if st.PID == 0`)
- Call sites: `internal/server/handlers_agent.go:658` (rerun step 1b),
  `internal/server/handlers_messages.go:169` (orphan rescue)
- Contradicted by: `internal/session/lock.go:399-460` (`Release`),
  `:564-628` (`clearHolderMetadata`), `:846-876` (`InspectSessionLock`),
  `:925-948` (`readLockFile`)

**What is wrong.** The predicate's rule 1 ("live lock + PID 0 means owner
alive, identity unreadable") assumes PID 0 can only arise from Windows'
mandatory `LockFileEx` or a failed best-effort sidecar write. It has a third,
far more common source: a *cleanly released* lock.

`SessionLock.Release` (lock.go:399) unlocks, closes, then runs
`clearHolderMetadata` and waits up to `releaseMetadataCleanupBound` (50 ms)
for it — deliberately, so "the PID must actually be cleared from the lock
file BEFORE Release() returns in the overwhelmingly common case" (lock.go:44-46).
`clearHolderMetadata` then:

- `f.Truncate(0)` + `f.Sync()` on the lock file — which **sets its mtime to
  now**, and
- `os.Remove(pidSidecarPath(path))` and `os.Remove(generationSidecarPath(path))`.

The lock file itself is deliberately never unlinked (lock.go:392-394). So the
post-release on-disk state is: **file exists, zero bytes, mtime = release
time, no `.pid` sidecar.**

`InspectSessionLock` on that state returns `Exists: true`, `Age: ~0`,
`Live: true` (because `age < externalOwnerLiveThreshold` = 20 s), and
`PID: 0` — `readLockFile` finds no sidecar, falls back to the now-empty lock
file, and `strconv.Atoi("")` yields 0.

`externalSessionOwnerRefusalFromConfig` then walks: `st.Live` is true → the
`st.PID == os.Getpid()` escape cannot fire (PID is 0, and the `!= 0` guard is
explicit) → `st.PID == 0` → **refuse**.

The "provably ours" branch at `:125` is therefore effectively dead code in
production: the only state in which our own PID is readable in the lock
metadata is while we still *hold* the lock, and in that state
`ReserveExclusive` has already failed at step 1a and this code is never
reached.

**Failure scenario (concrete).** Web UI, single `crush` process, no other
process anywhere:

1. Operator sends a message; a turn runs. `runOwned` takes the session lock
   (`agent_run.go:299`), writing `<pid>` into the lock file and the `.pid`
   sidecar.
2. Operator hits Cancel, or the turn finishes. `drainOrReleaseFinal` calls
   `lk.Release()`; `clearHolderMetadata` truncates the file and deletes the
   sidecar; the mailbox flips to `mbIdle`.
3. Operator hits Rerun on an earlier user message (this is the canonical
   rerun flow, and the exact flow `#614` was written for).
4. `Cancel` / `ClearQueue` / idle-poll succeed immediately; `ReserveExclusive`
   succeeds.
5. Step 1b inspects the lock: `Live: true`, `PID: 0` → **refused** with
   `"session may be owned by another process (live lock, holder PID
   unreadable) — wait for it to finish and retry"`. Nothing is deleted and no
   replacement turn starts.
6. The same refusal blocks `deleteMessageRescuingOrphan`, so deleting a
   just-cancelled, still-streaming assistant row from the UI also fails for
   the same ~20 s.

After 20 s the mtime goes stale, `Live` flips false, and everything works —
so this presents to an operator as an intermittent, unexplained
"another process owns this session" error, which is precisely the wrong
diagnosis.

**Why no test caught it.** Every rerun/delete test builds a fresh temp data
dir in which no session lock has ever been acquired, and the mock coordinators
never call `TryAcquireSessionLock`. The one test that *claims* to cover this
case — `TestHandleRerunMessage_OwnProcessLockDoesNotBlockRerun`
(`internal/server/p622_external_lock_test.go:158`) — forges the "leftover
fresh lock from our own just-finished turn" as a file whose **content is
`os.Getpid()`**. That is the *held* shape, not the *released* shape. The test
is green for a state production never produces after `Release`. This is
defect class 2 (a test green for a reason other than the mechanism it names)
applied to the very fix the ninth review asked for.

**Verification: INFERRED, not executed.** Traced end to end through
`Release` → `clearHolderMetadata` → `InspectSessionLock` → `readLockFile` →
`externalSessionOwnerRefusalFromConfig`. I did not run it: this review is
read-only and confirming needs a new test file. It is cheap to confirm —
acquire a lock in a temp dir, `Release()` it, then assert
`InspectSessionLock(dir, id, 20*time.Second)` reports `Live: true, PID: 0`,
and that `externalSessionOwnerRefusalFromConfig` refuses. There is currently
no test in `internal/session/lock_test.go` that inspects a *released* lock at
all; every `InspectSessionLock` test either holds the lock or back-dates the
mtime with `os.Chtimes`.

**Note on the fix shape** (not a prescription, just so the next round does not
re-derive it): the state "file exists, zero bytes, no sidecar" is
*distinguishable* from "held with unreadable PID" — a released lock is
0 bytes on every platform, whereas a held lock on Windows is unreadable but
non-empty, and on Unix is readable. `Release` also deletes the `.gen`
sidecar. Alternatively, the honest test is the one the OS already answers:
attempt a non-blocking `tryLockFile` and release immediately — but
`clearHolderMetadata`'s own doc (lock.go:539-556) records that this was tried
and reverted for causing false self-contention, so that route needs care.

### F-5 (P2) — task #630 ("cancel mid-rerun leaves the tail half-deleted") understates its own severity

- `internal/server/handlers_agent.go:740-755` (the two `holdCtx.Err()` checks
  straddling step 3's `a.Messages.Delete(holdCtx, targetMsg.ID)`)

The commit records the residual as "a Cancel landing mid-loop can leave the
message tail partially deleted with no rerun to follow". The window is wider
than the tail loop. Step 3 deletes the **target user message itself**, and the
`holdCtx.Err()` check that aborts the handler sits immediately *after* that
delete. If the cancellation lands while step 3's `Delete` is in flight but
after it has committed, the handler returns `"cancelled"` with the user's
prompt row **deleted and never recreated** — `Run()` was supposed to recreate
it and is never called. The prompt text survives only in the handler's local
`text` variable, which is discarded.

This is also a behaviour change, not just a new residual: before `d4e64288`,
these deletes ran under `ctx` and a failure was *logged and the loop
continued*, so a dying context could not truncate history and abort — the
replacement turn still started under `context.WithoutCancel(ctx)`.

Severity assessment requested by the task: **the characterisation is wrong and
P2 is right for the tail case, but the target-message case is data loss of a
user-authored message with no recovery path.** The window is short
(one DB write) but it is a whole DB write, not an instruction boundary. If the
project's bar is "transcript corruption is P1" (which is how F5/#614/#622 were
graded), this deserves re-grading, or at minimum a fix that defers the target
delete until after the last cancellation check.

Verification: INFERRED by reading. Not reachable through any current test —
every mock `ReserveExclusive` returns the caller's `ctx` as `holdCtx` with a
no-op cancel, so **none of the three new `holdCtx.Err()` bail-outs in
`handleRerunMessage` has an observer at all** (see "Coverage gaps" below).

## What I checked and found sound

Recording these so the eleventh round does not re-derive them.

**`dfd20116`'s cold-arm gate `(ledger.anyExecuted || !sawOtherAdmission) &&
!ledger.hasFailures()` is sound**, and the commit's argument for it holds.
`sawOtherAdmission` is set at exactly one place (`run_queue_drain_session.go:703`),
inside the `!admitted` branch and *before* the wait, so every path that
observes a same-pump admission sets it — including the ones that then return
early through `verdictOnCtxDone` or `verdict(true)`, where the flag is
irrelevant. The two arms have genuinely distinct observers
(`TestProcessEntry_RacedLeaseNil_DoesNotFalselyDrainAWaiter` for
`sawOtherAdmission`, the two new `p624` cold-call tests for the relaxed arm),
and the empty-queue control (`TestDrainSessionNow_ColdCall_EmptyQueue_StillNoWork`)
rules out the overzealous direction. The cross-process argument is correct:
`#610` already reports a live foreign lease as `DrainFailed` on the
`anyExecuted` arm (`TestDrainSessionNow_ForeignLeasedRow_NeverReportsComplete`,
5-minute TTL), so the cold arm is not introducing a new reporting class, only
extending an accepted one; and at the sole production consumer both
`originalErr` and `drainErr` are non-nil, so only *which* non-zero error the
operator sees changes. The one thing that is *not* sound is the comment
describing the consumer side — see F-6.

**`dfd20116`'s ledger priority rule is correct.** `mostRecentFailure` walks
`l.order` backwards, returns the first surviving key that is *not*
`__unattributed_`-prefixed (i.e. the freshest surviving tier-1 entry), and
otherwise the freshest surviving tier-2 entry. Freshest-within-tier-1 is
preserved exactly: a re-failed row re-appends its own ID, so the backwards
walk finds the newest occurrence first, and `recordSuccess(rowID)` deletes the
map entry so superseded rows are skipped. I could not construct a case where
"freshest within tier 1" is the wrong choice: tier-1 keys are row IDs, every
row's latest state is what `failed[rowID]` holds, and a row that later
succeeds is removed entirely. Key-space collision (a row ID literally starting
with `__unattributed_`) is not reachable — row IDs are the caller-supplied
idempotency keys, which are `sessionID-LogicalCallID` or
`sessionID-<unixnano>` (`agent_ownership.go:421,425`) and cannot start with an
underscore. The two-tier rule does change what `errors.Is` consumers see on a
ctx-death-after-row-failure; the only production consumer (`drainOutcomeError`)
does not switch on the error's identity, and
`TestDrainSessionNow_OnlyUnattributed_StillReportsIt` pins the fallback half.

**`d4e64288`'s `onHandoff` transfer is correct in both directions.**
`onHandoff()` is invoked at `agent_run.go:209-211`, and the only statement
between it and `runOwned`'s first line is the call itself; `runOwned`'s
`defer abandonOwnershipWithHandoff` is its *first* statement
(`agent_run.go:246-248`). So there is no reachable path where `onHandoff`
fires and the handoff does not happen, and no path where ownership moves
without it firing. The double-release the commit admits *is* benign, though
for a slightly different reason than "epoch-guarded": after an agent-level
early release the mailbox is `mbIdle` with the epoch **unchanged**, so the
handler's second `abandonOwnershipWithHandoff(sessionID, epoch)` does *not*
short-circuit on the epoch check — it is a no-op because the state is already
idle and both queues are empty. It becomes genuinely epoch-guarded only if a
new owner arrived in between, and every route to ownership (`submit`,
`beginCompact`) bumps `mb.epoch`, so a later era can never be clobbered. Net:
safe, but the one-line justification in `agent_run.go:148-151` is doing more
work than it says.
