# Fresh-session reviewer design

**Status:** proposal. This changes reviewer isolation and cost attribution, not the public review contract.

## 1. Current behavior (verified)

`ExecuteRun` has two reviewer entry paths. The in-process candidate path runs after the clean eligible primary turn at `internal/app/app_run.go:645-668`; its attempt closure currently builds the reviewer pass and calls `runTurnPhase(reviewerTurnPrompt(...))` at lines 663-667. The CLI/async loop submits `RunRequest{reviewerTurn: true, reviewBasis: ...}` from `internal/app/app_run_async.go:395-414`; `ExecuteRun` handles that flag early and returns from lines 586-597, before reaching the candidate branch. Both paths currently build the same review turn, but use the original session. The user prompt carries the fixed reviewer instruction including literal `ROLE SWITCH` (`internal/app/apprun/review/outcome.go:243-265`); computed evidence is appended when a basis is available (`internal/app/app_run_reviewer_evidence.go:246-268`).

The reviewer therefore runs within the original session and sees its accumulated conversation, not merely a new prompt: `runTurnPhase` starts a turn against `s.sess.ID`; the reviewer phase re-snapshots existing session message IDs before launching (`internal/app/app_run_reviewer.go:118-150`). The prompt identifies the last assistant message as the final report. Its deterministic `<review_evidence>` summarizes git status/changes, original request, commands/test results, todos, tool calls and final text, with a 6,000-rune cap (`internal/app/app_run_reviewer_evidence.go:35-61,246-295`). The fixed instruction grants read-only `view`, `grep`, `glob`, `ls`, `git_read`, and `read_delegation_transcript`, and forbids shell/edit/test/question tools (`internal/app/apprun/review/outcome.go:274-279`).

The reviewer output is attached as `Review`, parsed by `parseReviewVerdict` into `pass`, `pass_with_notes`, or `fail`; missing/unknown becomes `unparsed`. A passing verdict without reviewer read calls is downgraded to `unverified`. Fail/missing/unverified produce warnings and a stderr line; a reviewer execution error keeps the primary answer and records `error` plus a warning (`internal/app/app_run_reviewer_outcome.go:51-76,124-159,179-209`). `RunResult` exposes `review` and `review_verdict` as optional JSON fields; the review is an opinion and does not itself change the exit code (`internal/app/apprun/review/results.go:20-52`). `rush result --review` prints `verdict: <value>` followed by review text when present; its default readable form prints `review verdict: <value>` (`internal/serve/cmd/admin/reports/result.go:110-117,187-210`).

`--fail-on-review` is a CLI-only mapping: exactly verdict `fail` with the flag set yields code 3; all other verdicts/no review retain code 0, and existing run errors retain their own codes (`internal/serve/cmd/run/finish/run_fail_review.go:6-15,44-57`; dispatch in `internal/serve/cmd/run/run.go:396-402`).

## 2. Proposed fresh-session contract

### Package and assembly

Add a shared `runFreshReviewerPhase` helper in the existing app-level `internal/app/app_run_reviewer_evidence.go` (same package, no new package/directory). It builds the bounded package, creates the fresh child session, runs the reviewer turn in that child, and returns `(childSessionID, reviewText, error)`; callers attach returned review text using the returned child ID. Replace the turn-building/execution at BOTH call sites: the early `req.reviewerTurn` branch in `ExecuteRun` (`internal/app/app_run.go:586-597`, used by CLI/async `runReviewerTurn` at `internal/app/app_run_async.go:395-414`) and the in-process attempt closure (`internal/app/app_run.go:663-667`). Keep stall-retry behavior around the shared phase where applicable. Keep app responsible for orchestration and package assembly; use existing session services for persistence and the agent/coordinator for execution. This respects dependency order kit < store < session < config < agent < app < serve and avoids directory/file-count expansion (including the seven-elements-per-directory constraint).

### Inputs and bounded payload

The package is a standalone prompt, not copied transcript history. Include, in this priority order:

1. **Original task prompt** (highest-priority input; retain verbatim unless it alone exceeds budget, in which case retain its beginning and end with a visible truncation marker).
2. **Task ledger and acceptance text**: current todos plus acceptance criteria explicitly recorded in the task/prompt; do not infer acceptance criteria from the final report.
3. **Orchestrator final report**: final completed assistant text, labeled as claims rather than verified facts.
4. **Changed-files evidence**: computed base-to-run diff/status and file names; prefer changed-file list plus relevant diff hunks. Mark pre-existing dirty files as such using the before/after snapshot.
5. **Run facts**: commands and exit states, relevant warnings, with no full conversation/tool-result replay.

Set a hard **30,000-token** package budget including reviewer instructions and metadata. Estimate with the existing `provauth.ApproxTokenCount` rough estimator (`internal/agent/runtime/policy/provauth/summary_budget.go:56-63`), applied to the assembled textual package. Trim in this explicit order: (a) omit low-priority run facts and verbose command output first; (b) reduce diff to changed-path summary, then retain hunks only for acceptance-relevant files; (c) shorten report while preserving its conclusion and explicit claims; (d) shorten task ledger/acceptance text only after removing completed implementation chatter, retaining criteria; (e) truncate prompt only as last resort, retaining beginning/end and marking loss. Never silently cut; label every truncated/omitted section. If the assembled package still exceeds 30,000 tokens after this order, run with the truncated package and put a warning in the review envelope naming what was cut; never fall back to the legacy full transcript and never silently skip review. The caller adds that warning to `RunResult.Warnings` alongside the attached review. If the task prompt alone exceeds budget, truncate it with a visible marker and warn. This estimator is approximate, not a model tokenizer or exact request accounting.

The existing `buildReviewEvidence` is a source for computed facts, but its current cap is 6,000 runes rather than a token budget and its request/report/todos are not the complete proposed package (`internal/app/app_run_reviewer_evidence.go:35-61,270-295`). Add/adjust package construction there without growing a new package.

### Role, session, parent and cost

Use the configured reviewer model slot and role exactly as the current pass does: reviewer model resolved through existing `buildReviewerPassTurn`/reviewer call options, not a new model selection setting (`internal/app/app_run.go:586-595,663-667`; config's reviewer slot is represented in session model overrides, `internal/session/service/session.go:82-91`). Preserve reviewer-specific read-only tool filtering. Do not execute as `smart` merely because that is the triggering role.

Create a new child session per review attempt without copying parent messages. Derive its deterministic ID from the parent ID plus a reviewer marker and attempt identity (for example, a stable hash of parent ID, primary terminal message ID, and attempt number); this avoids collision with unrelated sessions and makes retries idempotent only for the same attempt. Reuse `CreateTaskSession`-style creation: it sets BOTH `ParentSessionID` and `CostParentID` to `parentSessionID` and returns an existing row on a matching idempotent retry (`internal/session/service/session_lifecycle.go:72-105`). Both links are required: the sessions tree derives children from `ParentSessionID` (`internal/serve/cmd/sessions/view/sessions_tree.go:64-77`), while subtree spend recursively follows `cost_parent_id` (`internal/store/db/sessions.sql.go:233-253`). `Service.SubtreeBudget` and `SubtreeSpent` consume that query (`internal/session/service/session_cost_subtree.go:14-34`). Reviewer usage remains the child's own `cost_self`; the parent's subtree spent/budget includes it once, but the parent's own cost is not incremented a second time. The parent's `budget_max_cost` is a subtree cap in the existing conditional charge path: `IncrementCostIfUnderMax` reads subtree spend and the base, then charges the session ID passed to it (`internal/session/service/session_update.go:64-85`). Thus the fresh child must be given only the remaining parent allowance (parent subtree budget subtracted from the parent's configured cap), while reviewer charges stay on the child; do not rely on the parent cap being implicitly copied to a newly created child. `ResetCostBase` freezes a subtree snapshot without changing `cost_self`, per the #1130 comment and implementation (`internal/session/service/session_cost_subtree.go:1-3,46-65`), so subsequent child spend is charged relative to that base. `TestResetCostBase_AtomicSubtreeSnapshot` creates a task child/grandchild, asserts their spend enters the root base, and later child spend appears in root budget (`internal/session/service/session_cost_subtree_reset_test.go:17-57`); this is the existing roll-up proof to extend with reviewer-child coverage.

`reviewerToolCalls` counts assistant tool-call parts after the LAST user row containing `reviewerPassMarker` (`internal/app/app_run_reviewer_outcome.go:78-121`); `attachReview` calls `env.Messages().List(ctx, sessionID)` using the ID passed to it (`internal/app/app_run_reviewer_outcome.go:124-177`). Therefore the shared fresh-review prompt must retain the same marker (defined as `ReviewerPassMarker` in `internal/app/apprun/review/outcome.go:243-247`), and attachment at both entry paths must receive the CHILD session ID: the in-process `attachReview` calls at `internal/app/app_run.go:673-684`, and the async close-phase call at `internal/app/app_run_async.go:461-470` (also report-recovery attachment at `internal/app/app_run_async_fsm.go:582-590`). Leave `reviewerToolCallCount`/`reviewerToolCalls` unchanged; their transcript read now naturally reads the child. Existing coverage includes `TestAttachReview_PassWithoutToolsIsUnverified` and `TestAttachReview_PassWithAToolCallIsPass` (`internal/app/app_run_reviewer_verdict_test.go:131-159,174-208`): these assert no-read PASS downgrades to unverified and a read after the marker earns PASS. `internal/app/app_run_reviewer_readonly_test.go:83-117` tests offered and behavioral read-only access; `internal/app/app_run_loop_review_warnings_test.go:20-91` covers warning propagation in the async loop. Extend these for child transcript IDs.

## 3. User-visible invariants

- Preserve the first-line `VERDICT: PASS`, `VERDICT: PASS_WITH_NOTES`, `VERDICT: FAIL` output contract and accepted localized variants; keep parsing semantics and lowercase wire verdicts (`internal/app/apprun/review/outcome.go:331-344`; `internal/app/app_run_reviewer_outcome.go:51-76`).
- Keep `review` and `review_verdict` envelope fields and their meanings; `final_text` remains the executor's report (`internal/app/apprun/review/results.go:41-52`).
- Preserve warning strings and stderr lines for fail, missing/unparsed, unverified, and reviewer execution failure (`internal/app/app_run_reviewer_outcome.go:133-158,194-209`). A successful verified pass stays quiet.
- Keep `rush result` readable/`--review` output byte-shape and field selection, and preserve `--fail-on-review`'s exact code-3 mapping; do not turn an ordinary reviewer fail into a failed run without the flag (`internal/serve/cmd/admin/reports/result.go:110-117,187-210`; `internal/serve/cmd/run/finish/run_fail_review.go:6-15,44-57`).
- Preserve no-review behavior for ineligible roles, failed/canceled primary runs, credential-isolated runs, and blocked live work; this proposal changes reviewer session isolation, not the eligibility gate (`internal/app/app_run.go:602-649`).

## 4. Migration, rollback and tests

Introduce a temporary config switch (recommended name `reviewer_session_mode: "legacy" | "fresh"`) with `fresh` as the new default after a compatibility release; retain `legacy` as an immediate rollback. A CLI override may be added for diagnosis, but do not add separate flags with divergent semantics. Recommend fresh-session default: it removes the measured context reread and the reviewer no longer inherits the orchestrator's reasoning history. Initially log package token estimate, truncation, parent/child IDs and reviewer outcome (not package contents). If package construction or child creation fails, keep the primary answer, attach a reviewer-error warning, and do not fall back to running the review in the parent transcript.

Tests to adapt/add, by existing file:

- `internal/app/app_run_reviewer_pass_test.go`: assert separate reviewer child session, parent linkage, prompt contents, no inherited messages, clean/failure/cancel behavior.
- `internal/app/app_run_reviewer_evidence_test.go`, `internal/app/app_run_reviewer_evidence_wire_test.go`, `internal/app/app_run_reviewer_evidence_async_test.go`: package section contents, 30k token enforcement, deterministic truncation order/markers, malformed/unavailable facts.

- `internal/session/service/session_lifecycle_test.go` and/or a new test in that existing directory: child creation, unique IDs, parent relationship and no inherited transcript; `internal/serve/cmd/sessions/view/sessions_tree_regression_test.go`: tree visibility and own-cost display.

## 5. Saving and risks

The orchestrator supplied measurements (not independently verified here): 33 reviewer events read 8.1M fresh input tokens for gpt-6.2-sol; other model switches used 3.9M and 1.1M fresh input tokens. At the proposed cap, reviewer package input is at most 33 × 30,000 = 990,000 (about 1.0M) tokens. Difference on that model: 8.1M − 0.99M = 7.11M fewer fresh input tokens, or about 88% reduction. If the 3.9M and 1.1M switches are likewise context-rereading costs and receive the same bounded package, further savings are possible; do not claim a specific total until their event counts/tokenization are established. The fresh reviewer itself still has inference/tool cost; the savings are from avoiding the entire inherited history at full uncached input price.

Risk: detached context may omit an important instruction, dependency, or rationale, so the reviewer can miss context that the old transcript exposed. Mitigation: include original prompt, acceptance/task ledger, final report, computed changed-files/diff evidence and run facts in a labeled, bounded package; expose read-only repository tools and delegation transcript as an escape hatch. Record truncation prominently, and do not claim a clean pass if required criteria or relevant diffs were truncated/unavailable. A further risk is cost aggregation or duplicate child creation on retries; child identity must be attempt-specific, each spend counted exactly once, and failure/rollback paths tested.

## Orchestrator status and reliability (added when the document landed)

Landed after two lane rounds, the maximum for a design document; the lane's own reviewer returned FAIL both times. Round 1 defects (single entry path, `parent_session_id` without `cost_parent_id`, the verified-pass lookup under the parent id) were confirmed against the code by the orchestrator and are resolved in this version. What the second review still finds is recorded here as open points that the implementation lane must settle before writing code, not as accepted design:

1. Helper return contract. `runFreshReviewerPhase` returning `(childSessionID, reviewText, error)` is not enough for the early `reviewerTurn` branch of `ExecuteRun`, which returns `(*RunResult, error)` today and whose callers (`app_run.go:586-596`, `app_run_async.go:457-468`, `app_run_async_fsm.go:582-589`) accumulate the reviewer `RunResult` before `attachReview`. The implementer must decide which field carries the child session id and the truncation warnings across that boundary (a new `RunResult` field is the likely answer) while the public envelope stays tied to the parent.
2. Exhausted budget. Giving the child "the parent's cap minus the current subtree spend" must have an explicit branch for a remaining budget of zero or less: `MaxCost` 0 means unlimited (`agent_turn_step.go:713-719`, `session_update.go:41-51`), so an exactly exhausted finite parent cap would become an unlimited reviewer allowance. The rule is: a zero or negative remainder skips the fresh reviewer and reports the budget-exhausted reason in the envelope.
3. The 30k token figure is an estimated target (the estimator is a rounded byte-length approximation), not a guaranteed bound; tests and the saving estimate must say so.

Verified by the orchestrator: the call-site claims of the first round (`app_run.go:586-597` and the in-process attempt, `app_run_async.go:395-409`), the cost walk through `cost_parent_id`. Not verified: the token measurements (taken from the lane session stores by the orchestrator, one-off script), the projected saving, any runtime behaviour of the proposal; no implementation was exercised. The expected saving (about 7.1M fresh input tokens of 8.1M for gpt-6.2-sol over the measured period) is an arithmetic projection of 33 events times a 30k package.
