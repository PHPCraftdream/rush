# Структурный рефакторинг async-слоя: убрать классы находок, а не экземпляры

Статус: решение оператора (2026-10-01): «заведи таски по рефакторингу и решай их с
помощью /wrush». Основание — разбор 8 раундов ревью фазы 4
(`docs/reviews/2026-09-2x-async-phase4-round*.md`) и 13 раундов weekly-audit.

## 1. Диагноз

Находки раундов фазы 4: ~70 / 44 / 22 / 12 / 11 / 15 / 12 / 16 — плато, а не
сходимость. В раундах 5–8 около половины находок — прямые последствия фиксов
прошлого раунда (R3C-1→R4C-1→R5C-1/2→R6C-4; R4B-1→R5B-1/2; R5C-5→R6C-2;
R7B-1→R8B-2; R7A-1→R8A-4; R7C-2→R8C-8).

| Класс | ≈ находок | Динамика | Причина |
|---|---|---|---|
| Хранилище (ключи, CAS, транзакции, восстановление) | ~45 | сошёлся к раунду 3 | один писатель `Transition` + CAS |
| Решение «автоматический ход: давать ли, каким агентом, как считать попытку» | ~58 | плато, цепочки | ~20 функций и ~15 независимых кусков состояния |
| CLI-цикл `rush run` (фазы, выходы, `ended_reason`, cancel, ревьюер) | ~34 | плато, цепочки | машина состояний на локальных переменных |
| «Жива ли сессия» (watch/tail/locks/reap/inject/list/why/show/cancel/reset/web) | ~14 | растёт с раунда 5 | каждый читатель вычисляет живость сам, слоями «повышений» |
| Фоновые shell | ~9 (P1 R6B-1, P2 R7B-1, R8B-2) | новая дыра каждый раунд | вторая правда вне `async_jobs` |
| Стоимость прогона | ~6 | цепочка | перенос «ребёнок→родитель» из 5 мест с водяным знаком |

Вывод: находки сходятся там, где решение принимает одна функция с одним
писателем, и выходят на плато там, где решение размазано. Лечение — свести
каждое размазанное решение в одно место с табличным оракулом.

## 2. Работы

### R-ACT — единая модель активности сессии (первым: дёшево, низкий риск)

Одна функция классификации в `internal/session` (чистая, табличный тест) +
один читатель фактов (пакетный для списков) + тонкая обёртка в `internal/app`.
Вердикт: в ходе (PID) / между ходами (кто ведёт и чего ждёт: задачи,
делегация, разовое расписание, отложенный повтор до T) / делегирует / простаивает /
упала (PID) / завершена (причина). Все читатели (`internal/cmd/sessions_*.go`,
`internal/server/handlers_sessions.go`, `handlers_agent.go`) используют её;
слои `mark*`/`promote*`/`reclassify*` в `internal/cmd` удаляются.

Приёмка: (1) один классификатор, нет второго места, решающего «жива ли
сессия»; (2) табличный тест классификатора покрывает все формы, найденные
ревью (R5C-5, R6C-1, R6C-2, R7C-2, R7C-3, R8A-1, R8C-4, R8C-5, R8C-8);
(3) существующие тесты команд `sessions` и сервера проходят без ослабления;
различия вердиктов между читателями, которые были, — устранены в пользу
вердикта `sessions why` и перечислены в отчёте.
Не цели: менять формат вывода команд сверх неизбежного; новые поля протокола web.

### R-ARB — арбитр автоматического хода

Чистая функция `decide(TurnFacts) → Verdict{Run(agent, counted) | Defer(reason,
recheckAt) | Close(rows, marker) | None}`. `TurnFacts` читается одним снимком.
Все пути запуска (подсказка после коммита, освобождение мейлбокса, 60-с проход,
завершение фонового shell, проверка в начале хода, `CLIScope` для CLI-цикла,
предохранитель цепочек) вызывают её; per-session счётчики — в одном месте
(одна строка БД или одна структура под одним мьютексом), а не в ~15 map.
Таблица политики §3.4 дизайна фазы 4 становится табличным тестом; свойство
«каждый вердикт Owed имеет ровно одного запускателя» — property-тест.

Сначала дизайн (R-ARB-D, только документ), затем реализация чистой функции и
чтения фактов (R-ARB-1), затем перевод вызывающих и удаление старого
состояния (R-ARB-2). Рефакторинг: наблюдаемое поведение не меняется; тесты,
проверяющие удаляемое внутреннее состояние, переписываются на наблюдаемые
утверждения (список в отчёте).

### R-LOOP — CLI-цикл как явная машина состояний

Фазы: первый ход → ожидание → Drain → ревьюер → выход; сброс локального
состояния при входе в фазу; побочные эффекты (`ended_reason`, сброс cancel,
`--on-finish`, сводка стоимости) только в фазе выхода. Поведение не меняется
(R-LOOP-1). Отдельно (R-LOOP-2): стоимость прогона выводится запросом по дереву
сессий (окно «от claim до выхода»), а не переносами из 5 мест — это изменение
семантики данных, только после дизайна в задаче.

### R-BG — фоновые shell как строки `async_jobs`

Уход shell в фон = claim строки; завершение = `Transition` (итог и долг одной
транзакцией). Исчезают удержания завершения, `PendingCompletionsOwned`,
отдельный лимит bg-shell (переходит в арбитр). Сначала дизайн (R-BG-D),
реализация (R-BG-1) — после R-ARB-2.

## 3. Правила процесса на время работ

- Ревью: Review Stop Rule из `CLAUDE.md` без исключений — серия заканчивается на
  нуле P0/P1; P2/P3 — в бэклог.
- Фикс P2/P3 не добавляет нового изменяемого состояния (map, флаг, счётчик,
  таймер). Нужно новое состояние — находка идёт в структурную работу.
- Каждая работа — свой worktree и rush-агент; агент не коммитит; оркестратор
  проверяет diff, перезапускает тесты, делает revert-check и коммитит шаг в
  `main`.
